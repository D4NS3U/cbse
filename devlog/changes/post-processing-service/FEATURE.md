# FEATURE.md — PostProcessingService reference component and flow integration

**Program context:** first feature of the post-professionalization roadmap (the former charter's M1 "PostProcessingService integration"); authored per the manager's spec-contract, from the live alpha4 code (`api/alpha4/simulationexperiment_types.go`, `scenario-manager/internal/{subject,nats,persistence,lifecycle,effectivejob}`, `component-templates/translator/` as the component-template archetype, `docs/COMPONENT_DESIGN_GOALS.md`'s post-processing boundary).
**Normative for every worker dispatched under it. Read-only for workers.** On contradiction between this spec and live code that repository inspection cannot resolve: stop and ask via the ask channel.

## 1. Title and mission

This feature completes the scenario end-state: a **reference PostProcessingService (PPS)** plus its integration into the CBSE flow. When a scenario's simulation-runner fleet (one batch/v1 Job) completes and the SM has moved the scenario to `PostProcessing`, the SM publishes one **evaluation request** per scenario to the PPS (NATS/JetStream, namespace-aware subjects). The PPS reads the scenario's result rows from the experiment's Result DB, evaluates the scenario's KPI against the **user-supplied precision threshold** using the paper's criterion — the half-width of a 95% confidence interval for a selected performance metric — and answers with a verdict: **(a) precision met** — the scenario transitions to the new success-terminal `Finished` state (no further runners, results preserved); **(b) precision not met** — the PPS returns the **number of additional runners needed**, the scenario returns to `StartingRunners`, and a new runner round executes (a new round-identified Job with the PPS-provided repetition count), after which evaluation repeats. A user-defined **maximum number of replications** is the additional stopping criterion. The loop is owned by the PPS's stop policy. Products: the reference PPS component (`component-templates/post-processing-service/`, the "Basic Reference Post Processing Service with evaluation logic"), operator provisioning of the PPS Deployment (`spec.postProcessingService` already exists in the alpha4 API and is currently unprovisioned), SM scenario-machine and messaging extensions, and e2e smoke coverage of the full chain. Component ownership: the Operator provisions the PPS Deployment; the SM owns scenario state and messaging; the PPS owns result evaluation and the stop policy. Future work (explicitly out): experiment-level phase aggregation (`Finished`/`Failed` experiments — a separate roadmap feature), Helm-chart-era validation, and non-reference evaluation strategies (any custom PPS images remain free to implement the wire contract).

## 2. Scope

- **In scope:** (a) reference PPS Go module under `component-templates/post-processing-service/` implementing the evaluation wire contract, a read-only Result-DB client, the reference evaluation strategy (§3 D6), and the additional-runner estimator; (b) SM extensions — new `Finished` scenario state, evaluation-request publication pipeline (triggered on entering `PostProcessing`), evaluation-response handler mirroring the translator-ready path, per-round runner semantics (round-identified Jobs, per-round repetition counts, generalized computed-reps bookkeeping), and deletion-cleanup extension for PPS consumers; (c) NATS/JetStream surface — new subjects + stream + durable consumers in the existing `internal/subject`/`internal/nats` grammar; (d) Operator provisioning of the PPS Deployment from the existing `PostProcessingSpec` (image/port/command/args + NATS and Result-DB environment wiring, ownership and deletion semantics consistent with the Translator deployment); (e) harness/smoke integration — the reference PPS image joins the mandatory component set (image lock, build/preflight/self-test extensions), stack manifests gain the PPS deployment; (f) e2e smoke specs covering the met-after-one-round path and the additional-rounds loop.
- **Out of scope:** experiment-level Completed/Finished semantics changes beyond accepting the new scenario terminal (the existing experiment terminal action must keep working verbatim); any change to the runner result-row format or the Result DB schema; any change to the translator contract; CRD field additions (assessment in workflow decision D1 — the base design requires none); production HA/observability tooling.
- **Breaking changes / compatibility:** the scenario "state" vocabulary grows (`Finished`); `PostProcessing` remains a valid state but loses its de-facto terminal role (a deployed SM observing old flows is unaffected — no external consumer of scenario states exists besides the terminal sweep, which is updated with the feature). `scenario_status` gains additive, nullable columns (schema validation policy: no `ALTER` repair, incompatible → startup fails — the extension must be additive-null-safe). Existing runner Jobs keep their names; new Jobs for additional rounds carry a new round suffix (naming in D5). The smoke harness's hard-pinned 6-component invariant becomes a 7-component truth, updated in the same feature wave with the harness self-tests (extend, never weaken).
- **Compatibility boundaries:** Kubernetes >= 1.30; alpha4-only API (served and stored); no feature-gate changes performed by the software; image references remain immutable digests.

## 3. Workflow decisions (concern → decision)

| # | Concern | Decision for this feature |
|---|---|---|
| D1 | Where does the user's required precision come from? | **Per-scenario `confidence_metric`** — the existing `scenario_status` column (documented in CDG as "Optional numeric target for future post-processing", supplied by the EDS batch row, today inserted NULL). Per the paper's criterion (user ruling Q1, 2026-09-25): `confidence_metric` is the desired precision threshold **ε**, the absolute half-width bound of the 95% confidence interval for the selected performance metric (D6), in the metric's units. The SM forwards it in the evaluation request; the PPS interprets it as ε. **No CRD change needed**: the existing `spec.postProcessingService` (`image`, `port`, `command`, `args`) configures the deployment; the PPS-level secondary stopping criterion (maximum replications) and policy defaults ride `args` (D7). An experiment-level ε fallback on the CRD can be added later as pure config surface — not part of this feature. |
| D2 | Messaging surface | Mirror the translator-flow shape: request subject `cbse.<namespace>.<project>.pps.request` (SM-publishes, JetStream stream `cbse_pps`, PPS consumes via a per-experiment durable consumer `pps-<12-char-UID-prefix>` — created and deleted with the experiment like the translator consumer); evaluation reply subject `cbse.<namespace>.<project>.pps.<scenario-id>.evaluation` (PPS-publishes, one stream, SM consumes via its anchored durable). Strict parsers in `internal/subject` (grammar length/domain rules) as for `trans.*`. All templates validated at startup like the others. |
| D3 | When does the SM learn about runner results? | The SM's existing observation scheduler is the trigger: fleet-Job completion already applies the guarded `InProcessing -> PostProcessing` transition. Entering `PostProcessing` now additionally enqueues the evaluation-request publication (exactly-once per scenario+round, guarded by new additive columns using the same attempt-guard pattern as translation publication). **The SM itself does not read the Result DB** — the PPS is the (read-only) Result-DB reader; the SM's request carries the identity context (experiment, scenario, round, `number_of_reps` so far, `confidence_metric`), and the PPS's evaluation response carries back the aggregate it observed (row count, achieved precision, verdict), which the SM may persist for observability. *(Ruling Q2, 2026-09-25: confirmed — the SM stays Result-DB-free; the PPS is the sole Result-DB reader.)* |
| D4 | New scenario states and terminal behavior | Add the success-terminal `Finished`. Transitions: `PostProcessing -> Finished` (verdict met, guarded); `PostProcessing -> StartingRunners` (verdict not-met + additional-runner count, guarded, increments the round counter); rounds flow through the existing `StartingRunners -> InProcessing -> PostProcessing` path. `Finished` joins the terminal set for every consumer of terminality (terminal action sweep, completion/cleanup logic); the failure sweep keeps `PostProcessing` in the non-terminal list (an experiment terminal during evaluation fails its scenarios, as today). A PPS "stop unmet" verdict (D7 cap) fails the scenario through the existing guarded failure path from `PostProcessing`, preserving all results and the last evaluated metrics. *(Ruling Q3, 2026-09-25: confirmed — `Finished` is the scenario success-terminal; experiment-level Finished/Failed phase aggregation stays a separate future feature.)* |
| D5 | Additional rounds: identity, sizes, bookkeeping | New additive columns: a per-scenario monotone `runner_round` counter and a `round_reps` requested-count for the current round (round 1 = the original `number_of_reps`). Additional-round runner Jobs are named `simrun-<UID-prefix>-s<scenario-id>-a<attempt>-r<round>` (today's single-round name reads as `-r1` implicitly — **no renames of existing-job expectations**; new name component only appears from round 2 on, or the label is always present — slice decides against the jobadapter's name-parsing invariants and adds the parse rule). `effectivejob` gains round-suffix and per-round completion-count inputs; `jobadapter` gains the corresponding create/confirm/observe/parse semantics for round-scoped Jobs; the SM generically tracks "current round's Job" only. `number_of_computed_reps` bookkeeping generalizes: for round 1 the existing monotonic clamp applies; for later rounds the observation counts against the per-round target and a new total (e.g., `total_computed_reps`) accumulates — exact column set and invariants are the slice's normative output. |
| D6 | Reference evaluation strategy (paper-exact, user ruling Q1) | **The paper's precision-based stopping criterion, verbatim.** Selected performance metric: **`mean_wait_time`** — the reference model's KPI and exactly the paper's "mean waiting time" example (the result rows also carry `completed_customers` as a secondary metric; the wire contract carries the metric name so custom PPS images can evaluate others). After each replication batch, the PPS updates the **sample mean X̄ and sample variance s²** over all completed replications (pooled across rounds; one observation per replication) and computes the half-width **h = t₀.₉₇₅,ₙ₋₁ · s / √n** of the 95% confidence interval. The user's per-scenario `confidence_metric` is the desired precision threshold **ε**; the requirement is **h ≤ ε** (absolute, in metric units — e.g. ±0.5 minutes in the paper's example; the reference model's time unit is SimPy time, and ε is expressed in that unit). **Additional batch size**: the sequential fixed-width estimate **n_req = ⌈(t₀.₉₇₅,ₙ₋₁ · s / ε)²⌉**, additional runners = max(minimum batch, n_req − n), clamped per D7; when the estimate cannot be formed (n < 2, s = 0) the degenerate rule applies (s = 0 with n ≥ 1 counts as met; n = 0 or 1 counts as not-met with the minimum batch). The t-quantile comes from `gonum.org/v1/gonum/stat/distuv` (Student-t). **Deterministic evaluation policy (ruling Q5, 2026-09-25):** the reference PPS takes an `EVALUATION_POLICY` arg — `statistical` (default; the criterion above) or `deterministic-first-round-not-met` (for tests and demos): round 1 always answers not-met with a fixed additional-runner count from `DETERMINISTIC_ADDITIONAL_RUNNERS` (default 2); round ≥ 2 always answers met. This decouples the loop-machinery test (SM round-trip, messaging, round-Job spawn, verdict application) from the model's randomness; the statistical math itself is conformance-tested off-cluster with hand-computed vectors. Selection is per-experiment via `spec.postProcessingService.args` — boolean-style on/off, no rebuild. The strategy is the **strategy pattern's reference implementation**: the wire contract is the normative interface; custom PPS images may implement any evaluation they want as long as they answer the verdict contract. |
| D7 | Loop bound (user's "indefinitely?" — paper-exact per Q1) | Two stopping criteria per the paper: **(1) precision met** (h ≤ ε) → `Finished`; **(2) user-defined maximum number of replications** (total across all rounds) — the reference PPS takes `MAX_REPLICATIONS` as a deployment arg (default: 10,000 — ruling Q4, 2026-09-25: kept) plus a per-round safety clamp `MAX_RUNNERS_PER_ROUND` (default: 1,000 — ruling Q4: kept). When the maximum is reached with h > ε, the PPS issues the final verdict `stop-unmet` and the scenario fails through the guarded `PostProcessing -> Failed` path with the last X̄/h/n visible in the bookkeeping; **all results remain in the Result DB** (nothing is discarded on stop). The SM never self-limits; it applies verdicts. |
| D8 | Failure and retry taxonomy | Evaluation requests are JetStream-published like translation requests: publish only after a durable PubAck, exactly-once per scenario+round via guarded columns, at-least-once consumer redelivery on the PPS side, poison messages acknowledged-and-dropped per the existing permanent-poison rules. A persistent evaluation failure (PPS unavailable, Result DB unreachable) leaves the scenario in `PostProcessing` (the request consumer re-publishes on the fixed cadence; not an infinite hot loop). PPS evaluation responses handling mirrors translator-ready: identity-checked, gate-checked, guarded transition; poison ACKed with an eventlog record. |
| D9 | Security/identity | Same identity conventions as the translator flow: reserved labels on the PPS Deployment (experiment identity, UID via downward API), per-experiment consumer naming, registry-auth via the existing Secret plumbing; the reference PPS image is a digest-pinned image led by `spec.postProcessingService.image`; the PPS gets the Result DB endpoint and credentials exclusively via operator-provisioned environment (it never receives cluster credentials of its own); result reads use the per-experiment Result DB user. |
| D10 | Deletion/cleanup symmetry | Experiment deletion cleanup extends exactly like the translator's: delete the per-experiment PPS consumer, purge the evaluation subjects, fail/complete any outstanding scenario bookkeeping — owned by the existing deletion-cleanup action, extended in the SM slice; the Operator's deletion of the PPS Deployment rides the established ownership/deletion semantics of translator deployments. |

## 4. Design patterns (Gang of Four)

| # | Concern (from this feature's requirements) | Pattern | Concrete application (types, packages, boundaries) | Why the simpler composition is not enough |
|---|---|---|---|---|
| 1 | Scenario lifecycle extension with round-trip transitions (`PostProcessing -> Finished / StartingRunners`) | **State** | The explicit scenario state machine in `scenario-manager/internal/{lifecycle,persistence}` — guarded SQL transitions as the state-boundary enforcement, `Finished` as new terminal | The machine must stay the single vocabulary; two new edges with guards cannot be free-form flags without breaking terminal semantics |
| 2 | SM ⇄ PPS decoupled evaluation flow | **Observer** | JetStream publication of evaluation requests and verdicts over the `cbse_pps` stream (`internal/nats` adapters; PPS + SM as independent observers), mirroring the translator request/ready flow | Fire-and-forget calls would couple SM to PPS liveness; the stream gives durable at-least-once + redelivery |
| 3 | Evaluation logic interchangeable per PPS image (reference vs user-concrete) | **Strategy** | The wire contract (`scenario-manager/internal/communication` types + the reference implementation in `component-templates/post-processing-service/`) is the strategy interface; the reference CI-based evaluator ships one strategy | Evaluation is the PPS's defining variability; hard-wiring the reference math into the SM or the contract would forbid alternative evaluation policies |
| 4 | Result-DB access from the PPS without a driver leak | **Adapter** | `component-templates/post-processing-service/internal/resultdb` wraps pgx behind an internal read-only interface (same conventions as the translator's `detaildb`/`registryauth` adapters), enabling conformance tests against fakes | A direct pgx dependency in evaluation logic blocks table-driven tests and locks the DB shape |
| 5 | Runner-Job assembly gains round/repetition parameters | **Builder** | `scenario-manager/internal/effectivejob` — existing stepwise merge of template + reserved fields extended with round-suffix and per-round completion counts | Job assembly has grown beyond a constructor: template merge + identity + round identity validation must stay composable and testable |
| 6 | Evaluation responses applied to scenario bookkeeping with poison/stale/gate semantics | **Template Method** | New evaluation handler in `internal/nats`/`internal/ready`-style package reusing the established handler skeleton (validate → gate → guarded transition → ack/naq), with the verdict application as the single varying step | Two parallel hand-rolled handlers would drift; the skeleton already encodes the failure taxonomy and provability |

*Deliberately not used:* Mediator (the SM composition stays explicit pairwise wiring), Singleton, any speculative pattern without a requirement row.

## 5. Global constraints (per worker, verbatim discipline)

- **Obey `AGENTS.md`.** Root test contract and cluster-safety rules incorporated by reference: `make test-fast` is mandatory for every Go/CRD/Dockerfile/harness change; `make test-smoke` additionally for operator reconciliation, API/CRD, SM k8s/NATS/database integration, image, or manifest changes; harness owns its namespace; immutable digest images; no TLS/insecure-registry bypasses; nothing in `default`/`kube-system`.

- **Runtime attestation.** Pi workers run `printf '%s/%s\n' "$PI_PROVIDER" "$PI_MODEL"` at the first checkpoint and repeat the verbatim output in their `worker_done` summary; expected line `ai.forge/qwen3.8-27b-nvfp4`; mismatch → stop, change nothing, report failed.
- **Normative spec.** This FEATURE.md + the assigned slice + `AGENTS.md` are read-only for workers; slice specs cite this file.
- **Idempotency across restarts.** Every new externally-visible effect (evaluation publication, round Jobs, verdict application, PPS consumer lifecycle) survives an SM/PPS restart exactly once per its guard.
- **No commits** (workers leave the tree reviewable; the user or the delegated manager commits).
- **Schema policy.** `scenario_status` extensions are additive and NULL-safe; no ALTER repair; incompatible → `ErrSchemaIncompatible` (startup fail) unchanged.
