# Specification for Alpha4 Simulation Runner Startup and Translator On-Demand Image Creation

This document has the following structure:

1. Mission Statement -- explains the intent and attitude of the work.
2. Scope -- explains the boundaries, goals, and explicitly chosen workflow.
3. Change Location -- identifies the code, API, and manifest areas expected to change.
4. Logic Description -- describes the implementation behavior and ownership boundaries.

## Mission Statement

This branch turns the Scenario Manager (SM) from a component that only advances a scenario to `InProcessing` into the component that starts and observes the scenario's Simulation Runner workload on Kubernetes.

Translator remains an always-on, per-experiment service, provisioned and managed by the Experiment Operator. This branch does not replace it with a Job or change its NATS/JetStream request-consumer model. “On-demand container creation” means that Translator creates the executable simulation model and builds its Simulation Runner image only after it receives a request for a claimed scenario. It then returns the immutable runner image reference through the existing ready-message workflow, from which SM starts the runner on demand.

CBSE cannot provide one universal production Translator because translating a scenario into an executable model is user-defined. Instead, this branch provides a production-quality reference Translator template in `component-templates/translator/`. The template owns the stable NATS/JetStream, BuildKit, registry, digest, acknowledgement, and extension contracts. Its included SimPy generator is an intentionally small example and replacement point, not a production simulation model.

The implementation must make Kubernetes runner Jobs a projection of durable scenario state, not a second source of truth. Database state and guarded transitions decide ownership; workloads perform external work. The coding agent should favor small, explicit, idempotent behavior that is safe across SM restarts and retries while preserving the existing Translator handoff boundary.

The coding agent should favor clarity over cleverness: write small, explicit, modular code that follows nearby patterns. Each component should have one obvious responsibility, explicit dependencies, descriptive errors, and no hidden package-global state. Understand the existing lifecycle, ownership boundaries, and tests first; reuse suitable abstractions, and introduce new ones only to clarify a boundary or enable independent testing.

Work incrementally and stay within scope. Preserve the Translator request and ready-message contracts, durable Scenario Manager state machine, and Kubernetes ownership patterns unless this specification changes them. Avoid redesigns, speculative compatibility layers, and unrelated cleanup. Make retries, restarts, and `AlreadyExists` results deliberate and inspectable: confirm the exact expected resource or return a useful conflict; never silently adopt it. Validate image references, Secret types, namespaces, ownership, and lifecycle state at boundaries. Do not weaken security implicitly, hide privileged requirements, or treat a created Job or pushed image as proof of a successful simulation.

Write clear documentation alongside the code. Explain the lifecycle, ownership, configuration, security and prototype assumptions, operational diagnosis, and deferred hardening. Tests must cover normal behavior, the exact validation groups defined below, stale claims, cancellation, identity collisions, repeated reconciliation, partial external success, and cleanup.

## Scope

This change introduces the only supported `SimulationExperiment` API version: `experiment.cbse.terministic.de/alpha4`. It defines the Translator image-build architecture, starts Simulation Runner Jobs, and observes their terminal result through the `PostProcessing` boundary.

`alpha4` is introduced by this feature as the only served, storage, and reconciled version. It is the active API, not a deprecated or transitional version. Only `alpha2` and `alpha3` are retired. There is no legacy reconciler, conversion webhook, compatibility mode, or automatic migration.

### Upgrade from alpha2 or alpha3

This is a breaking upgrade. Before installing the alpha4-only CRD, operators must export the desired old resources, transform each manifest to alpha4 by supplying every new required Translator registry and Builder field, delete all old `SimulationExperiment` resources, and delete the old CRD. They then install the alpha4 CRD and create the transformed resources. The Operator and SM must never perform these destructive steps.

The shared smoke cluster follows the same alpha4-only contract but does not perform the breaking upgrade. The smoke harness must never delete or migrate the shared CRD. Its preflight requires the installed CRD to serve and store only alpha4. It fails before creating a test namespace when it finds alpha2, alpha3, another storage version, or incompatible `status.storedVersions`. A cluster administrator performs the one-time breaking upgrade outside the test harness. Fast envtest coverage installs the generated alpha4-only CRD in an isolated control plane and verifies that alpha2 and alpha3 are not served.

### In Scope

1. **Alpha4 API, identity, and registry authentication.**
   - Carry the alpha3 user-facing schema into `api/alpha4`, retain required `spec.translator.baseimage`, and add required `spec.translator.registryAuthSecretRef corev1.LocalObjectReference` and `spec.translator.builderImage`. In YAML, the reference is `registryAuthSecretRef: {name: cbse-registry-auth}`; it is never an inline, plain, or base64-encoded credential string. `spec.translator.image` continues to select the Translator container. `builderImage` independently selects its rootless BuildKit sidecar, while `baseimage` selects the runner base from which Translator generates scenario-specific images. The carried `spec.translator.command`, `args`, `serviceType`, `nodePort`, and `port` fields remain creation-time configuration for the always-on Translator Deployment and Service; alpha4 does not treat any of them as a live rollout surface.
   - In alpha4, each `DatabaseSpec` requires exactly one of `image` or `host`. `dbname`, `user`, `password`, and `port` are required for both forms; `dbname`, `user`, and `password` must be non-empty and `port` remains in `1..65535`. A host is trimmed before use and must be exactly one lowercase DNS name, unbracketed IPv4 literal, or unbracketed IPv6 literal, without a URL scheme, path, query, fragment, embedded port, IPv6 zone identifier, or Unix-domain socket path. Exact runtime classification first uses `net/netip.ParseAddr`: an address with no zone selects the IPv4 or IPv6 path according to `Addr.Is4()` or `Addr.Is6()` and is normalized with `Addr.String()`. Otherwise, Kubernetes `validation.IsDNS1123Subdomain` must accept the trimmed value and the DNS path preserves that name. An image value must satisfy the owning image-validation rule. CRD admission rejects selector and structurally expressible host errors, and the Operator repeats the exact classification for descriptive provisioning errors. For either Detail or Result DB in image form, the Operator-created database Deployment's Pod template must contain `imagePullSecrets: [{name: cbse-registry-auth}]` exactly once. The reference is kubelet pull configuration only: the Operator must not mount the Secret, expose it through environment variables, or otherwise inject its contents into a PostgreSQL container. A host-based form must omit `command`, `args`, and `nodePort`, and may only use the absent/default `ClusterIP` value of `serviceType`; those fields configure an Operator-deployed database and have no external-host meaning. A host-based database is not connection-only metadata: the Operator must create or reconcile the same `<experiment-name>-<suffix>-sct` connection Secret produced for an image-based database, using the normalized host as `host` and copying the four other connection fields. It creates no Deployment, Pod, or Service and therefore has no database-workload `imagePullSecrets`. The common endpoint-resolution contract below applies to the Operator availability probe, Translator Detail DB lookup, and generated runner Result DB connection.
   - Add optional `spec.translator.builderResources corev1.ResourceRequirements`. Only CPU and memory entries in `requests` and `limits` are accepted; resource claims, huge pages, extended resources, and every other key are rejected. The Operator computes the effective resources without mutating the CR: missing CPU and memory limits default independently to `1` CPU and `2Gi`, while requests have no defaults and remain absent unless supplied. Every supplied quantity must be positive and each request must not exceed its corresponding effective limit.
   - Add optional `spec.runner.jobTemplate` as a typed Kubernetes `batch/v1.JobTemplateSpec`. When absent, SM uses the minimal built-in runner Job. When present, it provides the permitted Job and Pod customization described below.
   - `spec.detailDatabase`, `spec.resultDatabase`, `spec.translator.image`, `spec.translator.repository`, `spec.translator.baseimage`, `spec.translator.builderImage`, `spec.translator.builderResources`, `spec.translator.command`, `spec.translator.args`, `spec.translator.serviceType`, `spec.translator.nodePort`, `spec.translator.port`, and `spec.runner.jobTemplate` are immutable for the lifetime of an alpha4 `SimulationExperiment`. Immutability begins when the object is admitted to the cluster; changing database image or host selection, connection metadata, credentials, service exposure, command, arguments, Translator image, or any other listed field requires deletion and recreation of the experiment. The generated CRD must enforce this at API admission with separate `oldSelf` transition rules, not through a later Operator reconciliation error. On `spec`, the database rules are `self.detailDatabase == oldSelf.detailDatabase` and `self.resultDatabase == oldSelf.resultDatabase`. On `spec.translator`, the required or API-defaulted scalar rules are `self.image == oldSelf.image`, `self.repository == oldSelf.repository`, `self.baseimage == oldSelf.baseimage`, `self.builderImage == oldSelf.builderImage`, `self.serviceType == oldSelf.serviceType`, and `self.port == oldSelf.port`. The optional-field rules reject addition, removal, or modification: `has(self.builderResources) == has(oldSelf.builderResources) && (!has(self.builderResources) || self.builderResources == oldSelf.builderResources)`, `has(self.command) == has(oldSelf.command) && (!has(self.command) || self.command == oldSelf.command)`, `has(self.args) == has(oldSelf.args) && (!has(self.args) || self.args == oldSelf.args)`, and `has(self.nodePort) == has(oldSelf.nodePort) && (!has(self.nodePort) || self.nodePort == oldSelf.nodePort)` on `spec.translator`, plus `has(self.jobTemplate) == has(oldSelf.jobTemplate) && (!has(self.jobTemplate) || self.jobTemplate == oldSelf.jobTemplate)` on `spec.runner`. Each rule has its own rejection message naming the immutable field and instructing the user to delete and recreate the CR. An update leaving all thirteen immutable fields unchanged passes ordinary supported metadata or status changes. There is no in-place rollout, migration, or reconciliation behavior for changing these fields; in particular, the Operator never rolls out a new Translator image, executable configuration, or Service configuration for an existing alpha4 experiment. The existing SM cleanup finalizer and deletion contract must complete before a replacement with the same namespace/name is created.
   - `registryAuthSecretRef.name` identifies an existing Secret in the `SimulationExperiment` namespace and must equal `cbse-registry-auth`; every other value is invalid. Before provisioning any experiment component, the Operator gets that exact Secret and requires type `kubernetes.io/dockerconfigjson` and a `.dockerconfigjson` key containing valid Docker configuration JSON. Credential lookup uses the same standard Docker config-file resolver semantics as BuildKit, including well-known registry aliases, rather than a CBSE-specific host normalizer. The resolver must return non-empty basic-auth username and password values for the registry authority parsed from `spec.translator.baseimage` and from `spec.translator.repository`; identity tokens and credential-helper-only entries are unsupported, and the implementation must not fall back to unauthenticated access even if either registry is public. This credential-entry validation is limited to those two authorities; the Operator does not preflight entries for unrelated component, Builder, PostgreSQL, EDS, or post-processing image registries. Independently of that validation scope, every Operator-created image-based database Pod uses `cbse-registry-auth` as specified above, and SM adds the same `LocalObjectReference` to the runner Job so the kubelet can pull the generated image. Existing ServiceAccount- or node-level pull configuration may supplement these explicit references but must not replace them. Translator and BuildKit also use the mounted file for authenticated base-image pulls and generated-image pushes.
   - `translator.image`, `baseimage`, `builderImage`, and a ready-message runner image must be OCI digest references in the exact form `name@sha256:<64 lowercase hexadecimal characters>`. Tags alone are invalid.
   - `translator.repository` is the user-provided OCI repository where generated runner images are pushed. It is a repository name without a tag or digest and is not globally hard-coded by the feature implementation. The smoke profile is intentionally fixed: component and shared base images are published under `registry.unibw.de/i31bdase/cbse-test`, the reference Detail DB image is published under `registry.unibw.de/i31bdase/cbse-test/scenario-detail-database`, and generated smoke runner images are published under the dedicated repository `registry.unibw.de/i31bdase/cbse-test-runner`. These repositories need not be pre-provisioned on a fresh registry: Harbor creates a repository implicitly on its first corresponding push, and feature code and the harness must not call a repository-creation API. Existing repositories are also supported. A normal harness image push publishes the canonical tag even when that tag already exists, replacing its tag-to-manifest association when the newly built image differs; it must not require a prior delete or any repository-management API. The rendered smoke experiment must use the exact runner and reference Detail DB repositories, and smoke preflight rejects an override or mismatch. Registry access uses verified TLS. Insecure registries and TLS-verification bypasses are prohibited.
   - Persist each project by the statically defined `project_namespace` and `project_name`, where `project_name` is exactly `SimulationExperiment.metadata.name`; the pair is unique. Apart from the technical primary key used by `scenario_status.project_id`, the project table has no mutable status, component-count, or experiment-UID columns. Existing Core DB tables are validation-only and must not use automatic `ALTER TABLE` repair. This alpha API defines no migration procedure: an incompatible installation fails startup and must independently provide a fresh compatible database or recreate the tables.
   - Do not add namespace, project-name, or experiment-UID columns to `scenario_status`; its existing `project_id` foreign key remains the only project identity stored on a scenario row. Add only the non-identity operational column `translation_publish_started_at TIMESTAMPTZ NULL`, which distinguishes a claim for which NATS publication definitely never began from one whose publication result may be ambiguous. Kubernetes Job reconciliation has no persisted failure counter. The live Kubernetes object, its UID, owner references, and reserved workload labels provide incarnation identity for Kubernetes operations; the Core DB project identity is only namespace/name.
   - Namespace and project name are the routing identity for EDS and Translator communication. Alpha4 experiment names must be lowercase DNS labels of 1 to 63 characters matching `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`; dots are rejected even though Kubernetes otherwise permits them in names. Namespace and project are inserted into NATS subjects without lossy normalization.

2. **Namespace-aware EDS and Translator communication.**
   - Change the alpha4 subjects to carry namespace and project as separate tokens:
     - EDS availability: `cbse.<namespace>.<project>.eds.scenarios.available`
     - EDS scenario batch: `cbse.<namespace>.<project>.eds.scenarios`
     - Translator request: `cbse.<namespace>.<project>.trans.request`
     - Translator ready: `cbse.<namespace>.<project>.trans.<scenario-id>.ready`
   - Preserve the existing EDS availability, scenario-batch, Translator request, and Translator ready JSON payloads. Do not add namespace or UID fields to those payloads. Preserve publish confirmation, ACK/NAK behavior, guarded `Created -> Scheduled`, accepted-ready handling, and exact-attempt recovery.
   - SM parses namespace and project from every EDS and Translator subject and resolves the exact `(project_namespace, project_name)` database row. A payload project field, where the existing payload has one, must exactly equal the project subject token. A subject/payload or subject/database identity mismatch is a permanent poison message and must not mutate scenario state.
   - Before accepting any EDS batch or Translator ready message, SM gets the matching alpha4 experiment and applies the lifecycle gate defined below. Only a live, non-deleting experiment in `InProgress` may consume scenario work. For an admitted non-empty Translator ready image, SM validates the image as a digest reference, normalizes its repository and `spec.translator.repository` with the same OCI reference parser, and requires an exact match. A digest from another repository is a permanent ready-message rejection: SM ACKs it as poison, does not persist the image, and does not create a runner Job.
   - SM is cluster-wide for alpha4 communication. Its experiment informer and NATS subscriptions cover every namespace: `cbse.*.*.eds.scenarios.available`, `cbse.*.*.eds.scenarios`, and `cbse.*.*.trans.*.ready`. Components remain namespace-local Kubernetes workloads, but one SM deployment can communicate with EDS and Translator components belonging to experiments in different namespaces. Alpha4 does not use `SCENARIO_MANAGER_WATCH_NAMESPACE` to narrow subjects or Kubernetes discovery.
   - `InProgress` is the only experiment phase in which SM publishes Translator requests or consumes EDS batches and Translator ready messages. On a transition to `Error` or `Failed`, and from the moment `deletionTimestamp` is present, SM closes the experiment's lifecycle gate before it starts the terminal action defined below. `Completed` also closes the gate, but it does not cancel or delete retained work. Because the SM subscriptions and durable consumers are shared cluster-wide wildcards, SM must not literally unsubscribe them for one project. The closed per-experiment gate is the project-scoped unsubscribe boundary: an inactive EDS availability request receives `status=error` without a batch subject, and an unavoidable EDS batch or Translator-ready delivery is ACKed and discarded without message-handler database mutation, attempt consumption, or Job creation. This transport disposal remains active while the shared consumers serve other projects.
   - Every Operator-managed Pod template carries reserved labels `experiment.cbse.terministic.de/project=<experiment-name>` and `experiment.cbse.terministic.de/experiment-uid=<full-experiment-UID>`. The Operator injects `SIMULATIONPROJECTNAMESPACE`, `SIMULATIONPROJECTNAME`, and `SIMULATIONEXPERIMENTUID` into the per-experiment EDS and Translator through downward-API field references to `metadata.namespace`, `metadata.labels['experiment.cbse.terministic.de/project']`, and `metadata.labels['experiment.cbse.terministic.de/experiment-uid']` respectively. `metadata.name` and `metadata.uid` would identify the Pod rather than the owning experiment and must not be used for these two values. Each component publishes or subscribes only to subjects for that exact namespace/name pair.
   - SM owns the finalizer `scenario-manager.cbse.terministic.de/cleanup`. It adds the finalizer before registering a non-deleting experiment in Core DB. On `Error` or `Failed`, SM stops that incarnation's runner Jobs and marks its unfinished scenarios `Failed`, but retains the project row, scenario rows, per-experiment Translator consumer, and project-scoped stream contents for diagnosis and later deletion cleanup. On deletion, the still-present CR supplies the exact namespace, name, and UID while SM stops runner Jobs, removes the experiment's messaging artifacts, and deletes the project row; only successful cleanup permits SM to remove its finalizer. Kubernetes therefore cannot admit a replacement CR with the same namespace/name until the previous incarnation's durable state is gone. `Completed` closes the lifecycle gate but retains Jobs and durable state until deletion. No phase action deletes a shared stream or an SM consumer.

3. **Reference Translator template and on-demand image creation.**
   - Add a Go reference implementation at `component-templates/translator/`. It is the supported integration template for user-defined Translators and replaces `test/mocks/translator` in the full smoke path.
   - Separate the implementation into three explicit layers: the CBSE-maintained reference framework, a replaceable model-generator module, and the generated scenario-specific runner image. Production-quality guarantees apply to the framework and its integration contracts, not to the example model's semantics.
   - The Operator configures Translator through the same authentication-free environment-based process used by the existing smoke mock: `NATS_URL`, Translator stream, exact request subject, ready-subject template, and UID-specific durable-consumer name. `NATS_URL` contains no user information or credential material. No NATS credential environment variable, Secret, token, NKey, JWT, or credentials-file mount is added in alpha4. The Operator also injects `SIMULATIONPROJECTNAMESPACE`, `SIMULATIONPROJECTNAME`, `SIMULATIONEXPERIMENTUID`, `REPOSITORY`, and `BASEIMAGE`. The template validates all values before connecting to NATS.
   - `BASEIMAGE` is sourced only from `spec.translator.baseimage`. EDS payloads, Scenario Status, and existing Translator request and ready payloads do not carry or persist base-image information.
   - The Operator mounts the existing `<experiment-name>-detaildb-sct` and `<experiment-name>-resultdb-sct` Secrets read-only at `/detaildb-connection` and `/resultdb-connection` respectively for Translator. Each Secret contains `host`, `port`, `dbname`, `user`, and `password`. Database credentials may be literal deployment configuration in this trusted prototype, but the generator does not duplicate them in source code: the framework reads the mounted files and passes typed connection values to the generator. This allowance does not apply to third-party credentials such as registry or robot-account credentials, Kubernetes kubeconfigs, or other externally managed service credentials.
   - SM is the only supported request publisher and marshals requests from the typed four-field request struct after validating positive scenario ID and translation attempt. The template performs the lightweight decoding defined below and handles one request at a time. Its workspace is `/workspace/scenario-<scenario-id>/attempt-<attempt>`. It checks for a retained outcome before removing or recreating build input; only an attempt with no retained outcome and no recoverable registry tag has its build directory recreated.
   - The template uses the official BuildKit Go client over `unix:///run/buildkit/buildkitd.sock`. It submits the generated attempt directory as both the Dockerfile and build context, supplies registry credentials from `/registry-auth/config.json` through the BuildKit session, and requests a registry push to the deterministic tag. Before creating or attaching its JetStream request consumer, Translator waits for that socket and a successful BuildKit `ListWorkers` call as defined by the sidecar readiness contract below.
   - The pushed tag is `<repository>:runner-<12-char-UID-prefix>-s<scenario-id>-a<attempt>`. The UID prefix is the first 12 lowercase hexadecimal characters of the UID after removing hyphens. The framework adds OCI manifest annotations for the full experiment UID, scenario ID, and translation attempt, verifies them after the push, resolves the tag, and publishes only the digest reference.
   - Translator publishes the ready message and waits for publish confirmation before acknowledging the request. A generator, BuildKit, push, or digest-resolution failure persists and publishes the existing ready message with an empty image and is acknowledged only after that publish succeeds. NATS transport or ready-publication failures are retryable and must not manufacture an empty result.
   - A successful push is a durable external effect. If ready publication then fails, Translator retains the resolved digest and retries publication of the same ready message. It must not regenerate, rebuild, or push another image for that scenario and attempt.
   - After a terminal acknowledged outcome, the template removes the attempt workspace. Before generation on redelivery, it validates any retained success or empty-failure outcome for that scenario and attempt and republishes that exact ready message without repeating the failed operation. A retained success reuses its digest without another registry lookup, generator call, build, or push. If a success marker was lost, Translator resolves the deterministic registry tag and reuses it only when its repository and framework-owned identity annotations exactly match the current experiment UID, scenario ID, and attempt. A missing or mismatched annotation is a permanent tag collision: Translator records and publishes an empty-image outcome, does not adopt or overwrite the tag, and does not invoke the generator or BuildKit. It recreates build input only when no marker or registry tag exists.

4. **Mandatory rootless BuildKit sidecar.**
   - Each Translator Pod has exactly two containers: `translator` and rootless `buildkit`.
   - Both containers run as UID and GID `1000`. The Pod sets `fsGroup: 1000`. They share `emptyDir` volumes mounted at `/workspace` and `/run/buildkit`, so generated build input and the BuildKit socket are writable by both containers. BuildKit starts with `--addr unix:///run/buildkit/buildkitd.sock` as well as the required `--oci-worker-no-process-sandbox` flag, listens only on that socket, and exposes no TCP endpoint.
   - The `buildkit` container has a `startupProbe` that executes `buildctl --addr unix:///run/buildkit/buildkitd.sock debug workers`. The probe succeeds only when the socket accepts a BuildKit request. It uses a one-second period and failure threshold `60`; Kubernetes must not regard the sidecar as started before this succeeds. Translator's separate `ListWorkers` check requires at least one worker before it opens the request-consumer admission gate.
   - Translator has a matching application-level admission gate. After its static configuration and mounted files validate, it retries the socket existence check and BuildKit-client `ListWorkers` at `250ms`, `500ms`, `1s`, and then every `2s` until success or context cancellation. It creates or attaches no request consumer and accepts no request delivery before success. This wait is a retryable startup dependency, not a generator or BuildKit request failure, so it creates no outcome marker and consumes no translation attempt. Once a delivery has been accepted, a later BuildKit failure follows the normal confirmed empty-image workflow.
   - BuildKit receives the effective `spec.translator.builderResources`. CPU and memory limits default independently to `1` CPU and `2Gi`; user-supplied values replace those defaults. CPU and memory requests are copied only when supplied and otherwise remain absent.
   - Both containers receive the referenced registry Secret read-only at `/registry-auth/config.json`. The Translator also receives the Scenario Detail DB and Result DB Secrets read-only at `/detaildb-connection` and `/resultdb-connection`; BuildKit does not receive either database Secret.
   - BuildKit runs rootless and non-privileged with the required compatibility exception: `Unconfined` seccomp and AppArmor plus `--oci-worker-no-process-sandbox`. It must not use privilege escalation, privileged mode, host networking, host paths, or host container-runtime sockets. Translator keeps the normal restricted security profile.
   - A namespace that enforces the Kubernetes Baseline or Restricted Pod Security Standard rejects this required BuildKit exception. The smoke harness therefore labels its isolated `cbse-e2e-<run-id>` namespace with `pod-security.kubernetes.io/enforce=privileged`. This admission label does not permit the implementation to set `privileged: true` or weaken any other container restriction. The harness keeps `audit` and `warn` at `restricted` so the exception remains visible.
   - Kubernetes 1.30 or newer is required so the BuildKit container can set `securityContext.appArmorProfile.type: Unconfined`. Cluster installation documentation must call out the namespace admission requirement and the AppArmor prerequisite.
   - Generated source, Dockerfile, and build commands are trusted prototype input. Egress isolation and an untrusted-build sandbox are deferred.

5. **Simulation Runner startup and terminal observation.**
   - For one accepted Translator image, SM creates or confirms one `batch/v1` Job for the scenario and translation attempt. The Job name is `simrun-<12-char-UID-prefix>-s<scenario-id>-a<attempt>`, using the UID-prefix rule above.
   - Runner-start reconciliation is a short-lived, process-local SM control-plane workflow that validates one scenario and creates or confirms its deterministic Job. A runner-start reconciler is not a Kubernetes Job, Pod, worker node, or unit of cluster compute capacity.
   - The default Job has one container named `runner`. A custom template must contain exactly one `runner` container and may use only the explicit public allow-list below for sidecars, init containers, volumes, mounted configuration, resources, metadata, deadlines, and scheduling constraints. Every user-supplied field outside that allow-list is rejected. SM replaces the `runner` image with the accepted Translator image.
   - The Job is indexed. `spec.completionMode` is `Indexed`, and `spec.completions` and `spec.parallelism` both equal `scenario_status.number_of_reps`. Each completion index represents one homogeneous repetition for Kubernetes retry accounting. The runner does not consume the index, and Core DB and Result DB do not persist it as a repetition identity. All repetitions may run concurrently; a user-defined model and durable result sink must support that concurrency.
   - `number_of_reps` is limited to `1..100000`, the Kubernetes Indexed Job maximum when `parallelism` equals `completions`. This branch adds no lower operational cap, separate maximum parallelism, batching, or throttling. The trusted-input prototype accepts Jobs up to that Kubernetes limit. A future EDS template may impose a smaller policy limit.
   - Capacity and fairness follow ordinary Kubernetes Job and scheduler behavior. SM submits the Job without calculating cluster capacity or waiting for free resources. The Job may have at most `number_of_reps` Pods active because `parallelism` equals that value; the configured Kubernetes scheduler creates or binds Pods only as resources and scheduling constraints permit. Pending or unschedulable Pods leave the scenario `InProcessing` and are not Job-reconciliation failures. CBSE adds no custom capacity queue, admission calculation, or cross-Job scheduling policy.
   - Set `restartPolicy: Never`, global `backoffLimit: 4`, no `backoffLimitPerIndex`, no `maxFailedIndexes`, and no TTL-after-finished field. Kubernetes counts failed Pods across the entire Job against this one retry budget and creates replacement Pods while the budget remains. When the budget is exhausted, Kubernetes marks the Job `Failed` and terminates its remaining work. The Job succeeds only when all requested indexes complete, unless an allowed `activeDeadlineSeconds` terminates it earlier. Completed and failed Jobs remain visible unless later removed by the owning experiment's `Error`, `Failed`, or deletion action.
   - The Job has the exact alpha4 experiment owner reference, with `controller: true` and `blockOwnerDeletion: false`, runs in the experiment namespace, and uses the deterministic ServiceAccount `simrunner-<12-char-UID-prefix>`. The false block-owner-deletion value avoids requiring SM to have delete permission on experiments while preserving normal garbage collection. The Operator creates this ServiceAccount, gives it no RoleBinding, and SM sets `automountServiceAccountToken: false` on the Job Pod. Every Pod template created for an experiment by the Operator or SM carries the reserved project and full experiment-UID labels defined above; this includes internal database, EDS, Translator, post-processing, and runner Pods. The Operator and SM copy both label values from the live `SimulationExperiment`; containers that require the UID read the reserved label through the downward API and need no Pod-read permission.
   - Runner, sidecar, and init-container images must support non-root execution. The effective Pod template uses `RuntimeDefault` seccomp, `runAsNonRoot: true`, disabled privilege escalation, and dropped capabilities. The Operator alone validates and normalizes the immutable template before moving the experiment to `InProgress`. SM admits runner work only for a live, non-deleting `InProgress` experiment and treats that template as already validated.
   - SM observes Jobs for scenarios in `InProcessing` and monotonically records successful completion indexes in `scenario_status.number_of_computed_reps`. A successful Job records all requested repetitions before the guarded `InProcessing -> PostProcessing` transition. A failed Job preserves any partial successful count before the guarded `InProcessing -> Failed` transition. This branch does not execute post-processing or perform an ordinary post-processing transition; only the experiment-level `Error` or `Failed` terminal action may move an unfinished `PostProcessing` scenario to `Failed`.

### Immutable image inputs and repository-built outputs

The alpha4 smoke profile is `linux/amd64` only, matching the repository harness's existing `docker buildx build --platform linux/amd64` contract. Every digest below is the platform-specific OCI image-manifest digest, not the digest of a multi-platform image index. Smoke preflight requires at least one Node whose `Ready` condition has status `True`, whose `spec.unschedulable` is absent or `false`, and whose `kubernetes.io/arch` label is exactly `amd64`. Zero Nodes or no matching Node fails preflight. ## Logic Description

### Namespace-aware messaging contract

Alpha4 replaces project-only routing with a single canonical subject grammar. Namespace and project occupy separate subject segments and are copied directly from `SimulationExperiment.metadata.namespace` and `.metadata.name`. Code must validate both tokens before constructing or accepting a subject. It must not pass identity through `subject.NormalizeToken` or any other lossy conversion. Invalid identity is a permanent configuration or message error.

| Flow | Concrete subject | SM subscription or stream subject |
| --- | --- | --- |
| EDS availability request/reply | `cbse.<namespace>.<project>.eds.scenarios.available` | `cbse.*.*.eds.scenarios.available` |
| EDS scenario batch | `cbse.<namespace>.<project>.eds.scenarios` | `cbse.*.*.eds.scenarios` |
| Translator request | `cbse.<namespace>.<project>.trans.request` | JetStream stream subject `cbse.*.*.trans.request`; each Translator consumes its exact subject |
| Translator ready | `cbse.<namespace>.<project>.trans.<scenario-id>.ready` | `cbse.*.*.trans.*.ready` |

SM applies one canonical lifecycle gate before publishing a Translator request or performing domain processing for an EDS availability request, EDS batch, or Translator ready message. It gets the exact alpha4 `SimulationExperiment` identified by the subject and admits work only while the object exists, has no `deletionTimestamp`, and has phase `InProgress`. `Pending`, `Provisioning`, and an empty phase are not yet active: availability returns `status=error` without `batch_subject`, and a JetStream delivery is NAKed for later redelivery. `Error`, `Failed`, `Completed`, and deletion are permanently inactive for messaging: availability returns `status=error` without `batch_subject`, while an unavoidable JetStream delivery through the shared wildcard consumer is ACKed and discarded without database mutation, attempt consumption, or Job creation. By contract, publishers send no NATS or JetStream requests after `Completed`; the defensive terminal rule covers only a late, duplicate, or already-in-flight delivery. In this specification, “SM does not consume messages” for an inactive experiment means that no scenario-work handler runs; the terminal ACK is transport cleanup that prevents an unprocessable delivery from redelivering forever.

EDS continues its request/reply handshake, but publishes availability to its exact namespace/project subject. SM parses the subject, validates the existing availability payload's `project` against it, resolves the exact project row, and applies the lifecycle gate before replying. A successful reply for an active experiment returns the exact namespace-aware batch subject. When the subsequent JetStream batch arrives, SM parses and validates its subject again, applies the lifecycle gate, requires `ScenarioBatch.project` to match, and requires every scenario's `number_of_reps` to be in `1..100000` before beginning the existing all-or-nothing batch insert. A batch containing an invalid repetition count is permanent poison: SM returns an error acknowledgement, ACKs the JetStream delivery, and inserts no rows. A valid batch associates all inserted scenarios with `ProjectIDByNamespaceAndName(namespace, project)`.

SM resolves the candidate's raw project namespace and name and applies the lifecycle gate before claiming `Created -> Scheduled`. The claim atomically increments `translation_attempts` and clears both `translation_publish_started_at` and `translation_request_published_at`. Immediately before publication, SM applies the lifecycle gate again. If that check rejects the experiment or cannot confirm that it remains active, SM does not call NATS and calls `CancelUnpublishedTranslationClaim(scenarioID, attempt)`. That guarded update requires the exact `Scheduled` attempt and both publication timestamps to be null, restores `Created`, decrements `translation_attempts` by one, and updates `updated_at`. A zero-row result is a successful stale no-op. A database error is retryable and leaves the row for the stale-claim recovery described below. This cancellation is compensation for work that never began and is allowed even after the lifecycle gate closes.

After the second gate passes, SM calls `MarkTranslationPublishStarted`, which sets `translation_publish_started_at = NOW()` only for the exact `Scheduled` attempt while both publication timestamps are null. Only a caller that changes that row may invoke NATS publication. From that point the attempt is never decremented or reused because NATS may have accepted the request even when confirmation is lost. A confirmed publish sets `translation_request_published_at = NOW()` for the same attempt and requires a non-null started marker. A publish error or a failure to persist confirmation uses the existing exact-attempt publish-failure path: below `SCENARIO_MANAGER_TRANS_MAX_ATTEMPTS` it returns the row to `Created`, at the limit it moves the row to `Failed`, and it never refunds the attempt.

Stale unpublished-claim recovery runs before ordinary selection and remains active as bookkeeping even when the experiment lifecycle gate is closed. For an old `Scheduled` attempt with both publication timestamps null, it applies `CancelUnpublishedTranslationClaim` and refunds the attempt. For an old attempt with `translation_publish_started_at` set and `translation_request_published_at` null, publication is ambiguous, so recovery applies the existing attempt-consuming `Created`/`Failed` policy. A confirmed request is not recovered. The unavoidable phase change after the final lifecycle check is handled conservatively: the started attempt remains consumed, and any late ready delivery is subject to the terminal ACK-and-discard rule.

The publisher uses namespace and project to construct the exact request subject. The per-experiment Translator template validates its injected namespace and project at startup, subscribes only to that subject, and publishes ready messages only on the corresponding namespace/project ready subject. SM parses both tokens from a ready subject, applies the lifecycle gate, and requires them to match the scenario's persisted project row before applying empty-image recovery or a non-empty ready result. For a non-empty image, SM validates the digest and requires its normalized repository to equal `spec.translator.repository`. A wrong namespace, project, digest, repository, or stale translation attempt is ACKed as poison and cannot consume an attempt or alter the row.

Transport-neutral and persistence projections carry the validated raw identity explicitly. Extend `ScenarioForTranslation` and `TranslatorReadyMessage` with `ProjectNamespace` and `ProjectName`; do not retain a single ambiguous `Project` field in new alpha4 code. EDS may keep the wire field `project`, but after subject parsing its internal `ScenarioBatch` also carries `ProjectNamespace` and `ProjectName` fields excluded from JSON. Core orchestration and database functions receive this explicit identity and never reconstruct a namespace from process configuration or a normalized subject token.

Malformed subject shape, invalid tokens, subject/payload disagreement, and a batch or ready message that identifies no matching project are permanent poison deliveries: respond with an error where request/reply permits it, ACK JetStream messages, and perform no database mutation. A temporary database, Kubernetes lookup, or NATS failure is retryable: return an error for availability so EDS retries its request, or NAK a JetStream delivery. Availability for a valid identity that has not yet been registered or is not yet `InProgress` returns `status=error` with no `batch_subject`; it does not create a project row. The EDS retries availability and publishes no batch until it receives `status=ready`. Terminal and deleting experiments use the permanent lifecycle rejection above rather than this transient path.

The canonical alpha4 subject templates are:

- `SCENARIO_MANAGER_EDS_AVAILABLE_SUBJECT_TEMPLATE=cbse.{namespace}.{project}.eds.scenarios.available`
- `SCENARIO_MANAGER_EDS_BATCH_SUBJECT_TEMPLATE=cbse.{namespace}.{project}.eds.scenarios`
- `SCENARIO_MANAGER_TRANS_REQUEST_SUBJECT_TEMPLATE=cbse.{namespace}.{project}.trans.request`
- `SCENARIO_MANAGER_TRANS_READY_SUBJECT_TEMPLATE=cbse.{namespace}.{project}.trans.{scenario_id}.ready`

These values are fixed for alpha4. If the existing environment variables are retained for deployment compatibility, an explicitly configured value must equal the corresponding canonical value above or startup fails. Alpha4 removes support for `%s`, fixed project-independent subjects, alternate prefixes, and templates missing `{namespace}` or `{project}`. SM derives its cluster-wide stream and subscription wildcards only by replacing the namespace, project, and scenario placeholders with `*`; callers do not configure a narrower namespace wildcard.

In this document, a JetStream stream is a broker-side named store for messages published on configured NATS subjects; it is not a payload and is not created per Kubernetes namespace. SM owns creation and reconciliation of the two shared streams. `cbse_eds_scenarios` uses `WorkQueuePolicy`, `FileStorage`, `DiscardOld`, and subject `cbse.*.*.eds.scenarios`. `cbse_translator` uses the same retention, storage, and discard policies and subjects `cbse.*.*.trans.request` and `cbse.*.*.trans.*.ready`. Namespace and project remain subject tokens inside those shared streams, so one stream of each kind covers all experiments without mixing their identities. Stream fields not listed here retain an existing stream's value; on creation they use the NATS server or client-library zero-value defaults. Stream reconciliation may append these required alpha4 subjects but must not remove unrelated existing subjects. If the legacy stream-name environment variables remain, they must be absent or equal these canonical names.

All SM replicas attach to the same two SM-owned consumers. The EDS batch consumer is durable `scenario-manager-eds-consumer`, queue group `scenario-manager-eds`, exact filter `cbse.*.*.eds.scenarios`, explicit ACK, `DeliverAll`, `AckWait: 2m`, `MaxAckPending: 1024`, and `MaxDeliver: -1`. The Translator-ready consumer uses durable and queue group `scenario-manager-translator-ready`, exact filter `cbse.*.*.trans.*.ready`, and the same ACK, delivery, timing, pending, and redelivery settings. Queue groups distribute a given message among SM replicas; they do not partition by namespace. Per-experiment Translators still use their exact namespace/project request filter and UID-specific durable consumer, so only the owning Translator processes a request.

Because alpha4 is a coordinated breaking upgrade, SM reconciles an existing SM-owned durable to this exact configuration before starting business processing. If the server cannot update an incompatible filter or immutable setting in place, SM deletes and recreates only that named SM-owned durable, then attaches all replicas to the resulting consumer. Startup reconciliation never rewrites or deletes a per-experiment Translator consumer; the only such deletion in this branch is the ownership-verified CR-deletion cleanup below. An `Error`, `Failed`, or `Completed` phase never deletes that consumer. Concurrent SM startups treat an already-created matching stream or consumer as success; a remaining mismatch fails startup with the exact stream or consumer name and setting.

Each Translator uses a durable consumer named `translator-<12-char-UID-prefix>` with its exact request subject as the filter. The UID prefix follows the existing lowercase, hyphen-stripped rule. This keeps consumers distinct across namespaces and across deletion/recreation of an experiment. The consumer uses explicit acknowledgement, `DeliverAll`, `AckWait: 2m`, `MaxAckPending: 1`, and `MaxDeliver: -1` for unlimited redelivery. It also carries exact NATS consumer metadata `experiment.cbse.terministic.de/managed-by=translator`, `experiment.cbse.terministic.de/experiment-uid=<full-UID>`, `experiment.cbse.terministic.de/namespace=<namespace>`, and `experiment.cbse.terministic.de/project=<project>`. These metadata values are part of the consumer identity and make deletion-time ownership verifiable without relying only on the truncated durable name. Consumer metadata requires NATS Server 2.10 or newer, which is the minimum NATS version for alpha4. Translator sends `InProgress` every 30 seconds from request acceptance through generation, build, push, digest resolution, and any ready-publication retry. It publishes the ready message with confirmation and then uses a server-confirmed final acknowledgement for the request. If an in-progress acknowledgement cannot be sent, Translator cancels the active processing context and leaves the request unacknowledged for redelivery.

Translator creates its UID-specific consumer when it is absent. When it already exists, Translator attaches only if its stream, exact filter subject, all four ownership metadata entries, acknowledgement policy, delivery policy, `AckWait`, `MaxAckPending`, and `MaxDeliver` match this contract. An incompatible durable consumer is an identity collision and makes Translator startup fail without updating, deleting, or silently adopting that consumer. The Translator creates neither the shared stream nor an SM consumer.

Alpha4 deliberately retains the authentication-free NATS connection model used by the current smoke deployment. SM connects through `SCENARIO_MANAGER_NATS_URL`, and each per-experiment Translator connects through `NATS_URL`; neither URL may contain user information or credential material. The smoke values point to the in-cluster NATS Service over `nats://`, and the smoke NATS server enables JetStream without configuring users, accounts, tokens, NKeys, JWTs, credentials files, or subject permissions. If the legacy `SCENARIO_MANAGER_NATS_USER` and `SCENARIO_MANAGER_NATS_PASSWORD` variables remain in manifests, both must be empty; the reference Translator defines no corresponding credential settings or mounts.

The NATS server's anonymous client permissions must therefore allow the operations required by this feature. SM creates and inspects the two streams; creates, inspects, updates, and deletes its two consumers; inspects and deletes a per-experiment Translator consumer during CR-deletion cleanup; performs the exact deletion-time subject purges defined below; publishes Translator requests; and consumes and acknowledges EDS batches and Translator-ready messages. Each Translator inspects `cbse_translator`, creates and inspects its named consumer, consumes its exact request subject, and publishes its project-scoped ready subjects. Exact subject construction, consumer ownership metadata, collision checks, and cleanup checks remain application-enforced correctness boundaries; they are not broker-enforced security isolation in this branch. NATS authentication and authorization are deferred and require a later API, Secret, deployment, and operational design before they may be enabled.

### Namespace/name project persistence

The alpha4 project table has this logical schema:

```text
id                    SERIAL PRIMARY KEY
project_namespace     TEXT NOT NULL
project_name          TEXT NOT NULL
UNIQUE (project_namespace, project_name)
```

`scenario_status.project_id` remains a foreign key to `project.id` with `ON DELETE CASCADE`. The schema is a static developer-owned contract, not a user-configurable table shape. No experiment UID or mutable project state is duplicated in either table. Queries obtain namespace and name by joining the project table and obtain the current experiment UID from the live Kubernetes object when a Kubernetes operation needs incarnation identity. The SM cleanup finalizer prevents a replacement object with the same namespace/name from being created before the previous incarnation's project row and scenarios are deleted, so restart-safe incarnation separation does not require a UID column.

Project registration is idempotent for the exact namespace/name pair. `project_name` is copied without normalization from `SimulationExperiment.metadata.name`, and `project_namespace` is copied from `metadata.namespace`. Subject normalization never changes either stored value.

SM adds its cleanup finalizer before inserting or reusing the namespace/name project row, then re-gets the object. If deletion began before that re-get, SM enters deletion cleanup and does not register or reuse a row. When `deletionTimestamp` is set, SM stops accepting new EDS or Translator work for that project, performs deletion cleanup using the still-readable object's namespace, name, and UID, deletes the project row in one transaction, and lets `ON DELETE CASCADE` remove all scenarios. Only then does it remove its finalizer. A subsequently recreated experiment with the same namespace/name therefore registers a fresh row after the old row is gone.

When the project table does not exist, SM creates it with the alpha4 schema. When it already exists, SM validates it without issuing `ALTER TABLE`. Compatibility requires exactly the three columns above with the stated types and nullability, the generated `id` primary key, and the namespace/name uniqueness constraint; legacy `experiment_uid`, `number_of_components`, `status`, or any other extra project column is incompatible. The scenario table additionally requires `translation_publish_started_at TIMESTAMPTZ NULL` with no default. This is an operational workflow field, not identity. A legacy or incompatible table makes startup fail before the informer, NATS consumers, or selector starts. Alpha4 is an unused breaking alpha API and defines no database migration procedure; an affected operator must independently provide a fresh compatible database or recreate the tables.

### Experiment phase actions and deleted-experiment cleanup

The Experiment Operator owns deletion of its Deployments, Services, Secrets, ServiceAccount, and other experiment components through its existing finalizer and owner references. The pre-existing registry Secret referenced by `registryAuthSecretRef` is not owned or deleted by either controller. SM separately owns runner execution: on `Error`, `Failed`, or CR deletion it explicitly deletes the experiment's verified runner Jobs instead of relying only on eventual owner-reference garbage collection. `Completed` retains completed and failed Jobs for diagnosis until the CR is deleted.

For every informer event that may close an incarnation, SM first re-gets the current `SimulationExperiment` and requires the namespace, name, full UID, observed phase, and deletion state to match the event. A stale event for an old UID cannot close or clean a replacement. Once accepted, SM closes the namespace/name/UID lifecycle gate synchronously before queuing any slower action. Closing the gate cancels process-local scenario selection, runner-start, and observation work for that incarnation; every such worker also rechecks the live experiment before an external call or guarded state transition. Shared NATS subscriptions remain attached because they serve all experiments. Deliveries for the closed incarnation follow the ACK-and-discard rule above. If the current object has a `deletionTimestamp`, deletion cleanup takes precedence over its phase: SM queues only deletion cleanup for that event and does not also queue the `Error`/`Failed` or `Completed` phase action.

On an accepted `Error` or `Failed` phase without a `deletionTimestamp`, SM queues one idempotent terminal action for that namespace/name/UID:

1. List Jobs in the experiment namespace using both reserved experiment labels. A candidate is owned by this experiment only when its namespace, full project and UID labels, and exact alpha4 controller owner reference all match the current CR. Any matching-label ownership mismatch is an identity collision: do not delete that Job and fail the terminal-action attempt. Delete every verified Job with foreground propagation and do not declare runner cancellation complete until subsequent named reads report every deleted Job absent.
2. In one Core DB transaction, update scenarios belonging to the exact namespace/name project from `Created`, `Scheduled`, `StartingRunners`, `InProcessing`, or `PostProcessing` to `Failed`. Preserve `number_of_computed_reps`, translation attempts, timestamps other than the ordinary update timestamp, runner image, and diagnostic fields. An absent project row or zero matching unfinished rows is success. Existing `Failed` and `Finished` rows remain unchanged. The Project table has no status column: the live `SimulationExperiment.status.phase` remains the authoritative project-level `Error` or `Failed` state.
3. List and delete verified Jobs again before completing the action. This final pass catches a Job create that crossed the gate-close event. In addition, a runner-start worker whose Job create succeeded but whose guarded `StartingRunners -> InProcessing` update lost to terminal handling must re-read the experiment and delete that verified Job when the gate is closed.

An `Error` or `Failed` terminal action does not delete the project row, scenario rows, per-experiment Translator consumer, or messages already retained on project subjects. Those artifacts remain available for diagnosis and are removed by later CR deletion. A pending Translator request may finish, and external EDS or Translator publishers may continue publishing, but SM never performs scenario-work handling for the closed incarnation. Deleting the Translator consumer here would not be a reliable unsubscribe because the still-running Translator Deployment could recreate it after a Pod restart. The shared lifecycle gate is therefore the only per-project SM subscription boundary before CR deletion.

On an accepted `Completed` phase without a `deletionTimestamp`, SM closes only the lifecycle gate. It does not delete Jobs, change scenario rows, delete the Translator consumer, or purge subjects. By contract, `Completed` is set only after runner execution has already reached its terminal scenario states, and no component publishes new work afterward. Artificially injected late deliveries are still ACKed and discarded.

SM requests deletion cleanup when it observes the current object with `deletionTimestamp`. The still-present object is protected by the SM finalizer and supplies the authoritative namespace, name, and full UID; a replacement with the same name cannot yet exist. After closing the lifecycle gate, SM performs these idempotent operations in order:

1. Delete and confirm absence of all ownership-verified runner Jobs using the same label, owner-reference, foreground-deletion, and collision rules as `Error` and `Failed` terminal handling.
2. Retrieve durable consumer `translator-<12-char-UID-prefix>` from stream `cbse_translator`. A missing consumer is success. Before deletion, require its stream, durable name, exact filter `cbse.<namespace>.<project>.trans.request`, and all four ownership metadata entries to match the deleting CR's full UID, namespace, and project. Any mismatch is an identity collision: do not delete the consumer, fail that cleanup attempt, and retain the finalizer. Delete only a consumer that passes every ownership check.
3. Purge messages matching `cbse.<namespace>.<project>.eds.scenarios` from stream `cbse_eds_scenarios`.
4. Purge messages matching `cbse.<namespace>.<project>.trans.request` from stream `cbse_translator`.
5. Purge messages matching `cbse.<namespace>.<project>.trans.*.ready` from stream `cbse_translator`.
6. Delete the exact `(project_namespace, project_name)` row in Core DB in one transaction; its foreign key removes every scenario belonging to the deleted project.
7. Perform one final verified Job absence check to catch a create that crossed gate closure or the first deletion pass.
8. Remove `scenario-manager.cbse.terministic.de/cleanup` only after all preceding operations succeed.

The availability subject uses Core NATS request/reply and has no durable server artifact to remove. No phase action deletes or recreates a shared EDS or Translator stream, an SM durable consumer, or a queue group. A missing stream, consumer, matching message, project row, verified Job, or finalizer is successful cleanup where the corresponding operation is already satisfied. A message already delivered to a shared SM consumer remains subject to ACK-and-discard even if deletion purge races with that delivery.

SM replicas may request the same terminal action or deletion cleanup. Each namespace/name/UID is an independent idempotent queue key, so duplicate Job deletes, guarded database updates, consumer deletion, and subject purges are safe. One delayed action cannot block another experiment. A failed action retries after a fixed five-second delay until success or shutdown; there is no exponential backoff or retry limit. A runtime Job-delete `Forbidden` or other Kubernetes failure leaves the gate closed, does not affect another project, and retries on that cadence; during CR deletion it also retains the SM finalizer.

This branch performs no startup or periodic orphan sweep and never enumerates consumers to infer ownership from a matching filter. A consumer or project row orphaned because deletion happened before SM installed its finalizer, or because an administrator removed that finalizer, is not automatically recovered; it may block same-name recreation under `WorkQueuePolicy` and requires explicit operator intervention until a future orphan-cleanup feature is implemented. Normal supported deletion after finalizer installation remains fully automated as defined above.

This branch reacts to experiment phases but does not decide them. A future SM lifecycle feature will own scenario aggregation and the experiment transitions from `InProgress` to `Failed` or `Completed`. The Operator continues to own `Pending -> Provisioning -> InProgress` and provisioning failure to `Error`. Regardless of which component set the phase or deletion timestamp, only the current live `InProgress` incarnation admits messaging or runner work; the terminal actions above are lifecycle control, not continued scenario execution.

### Translator template boundary

The reference Translator is production-quality integration code, but it is not a universal production Translator. The stable framework owns request consumption and validation, serial delivery, workspace lifecycle, BuildKit sessions, registry authentication, push and digest verification, ready publication, and request acknowledgement. It must not contain model-specific decisions outside the example generator.

The Operator provides the framework configuration as environment variables, following the existing authentication-free mock Translator process. `NATS_URL` identifies the NATS server and must not contain user information. `TRANSLATOR_STREAM`, `TRANSLATOR_REQUEST_SUBJECT`, `TRANSLATOR_READY_SUBJECT_TEMPLATE`, and `TRANSLATOR_CONSUMER` identify the exact alpha4 JetStream stream, request filter, ready-subject template, and UID-specific durable consumer. `SIMULATIONPROJECTNAMESPACE`, `SIMULATIONPROJECTNAME`, and `SIMULATIONEXPERIMENTUID` identify the owning experiment. `REPOSITORY` is the configured target repository and `BASEIMAGE` is the digest-pinned `spec.translator.baseimage` value. The template accepts no NATS username, password, token, NKey, JWT, credentials file, or credential mount. It fails startup with a descriptive configuration error when any required value is missing, malformed, or inconsistent with the alpha4 subject grammar. It creates neither shared stream nor Scenario Manager consumer.

After static startup validation, Translator applies the mandatory BuildKit admission gate before it creates or attaches its per-experiment request consumer. It checks `/run/buildkit/buildkitd.sock` and invokes BuildKit `ListWorkers`; a successful response with at least one worker opens the gate. Until then it retries at `250ms`, `500ms`, `1s`, and then every `2s`, honoring shutdown cancellation. A Pod may therefore be Running while it is not a request consumer, but a request cannot be accepted and classified as an empty-image outcome solely because the sidecar is still starting. The BuildKit sidecar startup probe is the Kubernetes-level counterpart of this gate. If BuildKit becomes unavailable only after Translator accepted a request, that request follows the normal BuildKit failure and confirmed empty-image workflow.

The framework derives the ready subject from the configured template and the validated request scenario ID. It must publish only within its injected namespace and project. The stream, request subject, ready-subject template, and consumer naming are configuration, not model-generator responsibilities.

Translator consumes the request schema already published by SM: integer `id`, integer `translation_attempt`, object-or-null `recipe_info`, and number-or-null `confidence_metric`. SM validates the two positive identity values before using `encoding/json` on that typed struct; no valid SM-published scenario request can therefore lack recoverable identity. Translator decodes one JSON object, requires positive `id` and `translation_attempt`, and checks the documented types for the two optional fields. Unknown fields are ignored and do not extend the supported contract. A delivery that cannot recover valid identity is external or corrupt poison rather than a request produced by the supported SM publisher: Translator emits one sanitized log and ACKs it without a ready message, and tests for this branch publish raw poison without creating a Core DB scenario. If identity is valid but `recipe_info` cannot be handled by the selected generator, that is a generator failure and follows the confirmed empty-image ready workflow for that scenario.

An empty-image outcome is terminal only after its ready publication is confirmed. Generator, BuildKit, registry push, and digest-resolution failures first atomically persist an empty-failure outcome marker, then retry publication of that same empty-image ready message until confirmation and finally server-ACK the request. If final request acknowledgement fails, redelivery reuses the marker and does not repeat generation, build, push, or resolution. NATS transport, progress-acknowledgement, or ready-publication failures leave the request unacknowledged for JetStream redelivery and never create a second failure classification. This is the same ACK/NAK boundary used by SM for ready messages: malformed or permanent poison is ACKed, while transient transport or persistence failure is retried.

For an active `InProgress` experiment admitted by the lifecycle gate, SM handles a confirmed empty-image ready message through the existing exact-attempt policy, now made canonical here. `SCENARIO_MANAGER_TRANS_MAX_ATTEMPTS` is a positive integer with default `3`. After validating project, scenario ID, state `Scheduled`, and matching `translation_attempt`, SM calls `MarkScenarioTranslationAttemptFailed`: attempts below the configured maximum transition that exact row back to `Created`, while an exhausted attempt transitions it to `Failed`. The recovery update does not increment `translation_attempts`; the next successful `Created -> Scheduled` claim increments it. SM ACKs the empty ready only after the guarded database update succeeds and NAKs transient database failures. For an inactive terminal or deleting experiment, SM instead applies the terminal ACK-and-discard rule and does not call this recovery update.

The replaceable Go generator boundary has this conceptual shape; the implementation may place these types in an internal package, but it must preserve this dependency direction:

```go
type Generator interface {
	Generate(context.Context, GenerationInput) error
}

type GenerationInput struct {
	ScenarioID         int
	TranslationAttempt int
	RecipeInfo         json.RawMessage
	ConfidenceMetric   *float64
	BaseImage           string
	Workspace           string
	DetailDatabase      DatabaseConfig
	ResultDatabase      DatabaseConfig
}

type DatabaseConfig struct {
	Host     string
	Port     int
	DBName   string
	User     string
	Password string
}
```

`Generate` writes a complete Docker build context into `Workspace`: generated model files, scenario configuration, dependencies, an entrypoint, and a Dockerfile. It does not consume NATS messages, call BuildKit, push images, publish ready messages, or acknowledge deliveries. Those remain framework responsibilities so a user can replace model generation without reimplementing the handoff protocol.

The same endpoint-resolution contract applies to exactly three PostgreSQL clients in this feature: the Operator availability probe for both configured databases, the Go Translator lookup client for the Scenario Detail DB, and the generated Python runner client for the Result DB. Their purposes remain distinct. The Operator does not read model parameters, create application tables, write results, or otherwise use a database for experiment work; after it has reconciled an image-based database or recorded an external endpoint, it performs only the provisioning sanity check defined below. Translator performs only the predefined Detail DB parameter query. The runner performs only its Result DB schema-and-insert workflow.

Each client classifies and normalizes the configured host exactly as defined by alpha4 admission. At the start of every new connection attempt, an IPv4 or IPv6 literal produces one normalized address without DNS. A DNS endpoint is resolved anew during that attempt through the client's context-aware system resolver for both A and AAAA records. Results retain resolver order, duplicate normalized addresses are removed by retaining their first occurrence, and an empty result is a resolution failure. The client tries addresses in that order; the first successful PostgreSQL connection owns the operation, and remaining addresses are not contacted. DNS resolution and all candidate connection attempts share one 10-second deadline rather than receiving 10 seconds each. An established connection is never re-resolved or migrated when DNS changes; a later connection attempt performs a fresh lookup. DNS failure, an empty result, or exhaustion of every returned address is a transient connection failure under the owning client's failure policy. Every implementation supplies host and port as separate driver fields and explicitly sets `sslmode=disable`; it must not construct a connection URI through string concatenation.

The Operator implements this contract in its internal database-endpoint package. The Translator template ships independently testable Go modules at `internal/databaseendpoint/dns`, `internal/databaseendpoint/ipv4`, and `internal/databaseendpoint/ipv6`, selected by one dispatcher. The generator also copies equivalent Python modules into every generated runner at `runner/database_endpoint/dns.py`, `runner/database_endpoint/ipv4.py`, and `runner/database_endpoint/ipv6.py`; the Python dispatcher uses `socket.getaddrinfo(..., type=socket.SOCK_STREAM)` and applies the same normalization, stable de-duplication, ordering, shared-deadline, and fallback rules before giving the selected address and separate port to Psycopg. These modules contain no credentials and are shipped code, not separately deployed services.

The intended example remains a small parameterizable SimPy model, but its parameters are stored in the PostgreSQL Scenario Detail Database rather than carried completely in the Translator request. SM continues to send the unchanged `recipe_info` field. For this generator, `recipe_info` must be exactly one JSON object containing one positive integer lookup key and no other fields:

```json
{"parameterset_id": 1}
```

This lookup `parameterset_id` identifies a row in the Scenario Detail Database. It is independent of the positive Core DB scenario ID in the request's top-level `id` field; the generator must not require those two values to be equal and this feature makes no Core DB schema or payload change for the lookup rename. A missing or null `recipe_info`, malformed JSON, a non-object value, a missing, non-integer, zero, or negative `parameterset_id`, or any unknown field is a permanent generator-input failure.

The reference Scenario Detail Database image owns this exact schema-qualified table:

```sql
CREATE TABLE public.simulation_parameters (
    parameterset_id INTEGER PRIMARY KEY CHECK (parameterset_id > 0),
    arrival_rate    INTEGER NOT NULL CHECK (arrival_rate > 0),
    service_rate    INTEGER NOT NULL CHECK (service_rate > 0),
    run_duration    INTEGER NOT NULL CHECK (run_duration > 0),
    seed_policy     INTEGER NOT NULL CHECK (seed_policy >= 0)
);

GRANT USAGE ON SCHEMA public TO CURRENT_USER;
GRANT SELECT ON TABLE public.simulation_parameters TO CURRENT_USER;
```

All five values are PostgreSQL `INTEGER`s. `arrival_rate` is the number of arrivals per SimPy time unit, `service_rate` is the number of services per SimPy time unit, `run_duration` is the number of SimPy time units to execute, and `seed_policy` is non-negative seed material from which each runner derives its own pseudorandom seed. The repository-owned image initialization SQL creates the table and supplies exactly four rows. Their randomly selected values are generated once and checked in as fixed, reproducible image inputs rather than regenerated during image build, container startup, or a smoke run:

```sql
INSERT INTO public.simulation_parameters
    (parameterset_id, arrival_rate, service_rate, run_duration, seed_policy)
VALUES
    (1, 2, 4, 100, 1001),
    (2, 3, 5, 120, 1002),
    (3, 4, 7, 150, 1003),
    (4, 5, 8, 180, 1004);
```

The generator, not `recipe_info`, owns the one predefined parameterized SQL statement:

```sql
SELECT arrival_rate, service_rate, run_duration, seed_policy
FROM public.simulation_parameters
WHERE parameterset_id = $1;
```

The generator passes the validated `recipe_info.parameterset_id` as `$1`; it never executes SQL text received in a message. The query must return exactly one row. No row, more than one row, a `NULL`, a non-integer value, or a value outside the table constraints is a permanent generation failure. The primary key makes duplicate rows invalid schema state, but the adapter still checks cardinality defensively rather than silently selecting one row. All implementation SQL names this table as `public.simulation_parameters`; it must not depend on PostgreSQL `search_path`.

The framework reads the existing `<experiment-name>-detaildb-sct` Secret from `/detaildb-connection`, validates exactly the `host`, `port`, `dbname`, `user`, and `password` files at startup, and passes the resulting `DatabaseConfig` to the generator. This is identical whether the alpha4 `DatabaseSpec` selected an Operator-deployed image or an external `host`; the Operator creates the connection Secret in both cases. There is no additional Translator-specific Detail DB role. `spec.detailDatabase.user` is the exact PostgreSQL login used by Translator, and the Secret's `user` value must equal it. For the reference image form, the Operator also supplies `POSTGRES_USER` from that field, `POSTGRES_PASSWORD` from `spec.detailDatabase.password`, and `POSTGRES_DB` from `spec.detailDatabase.dbname`; therefore, image initialization and Translator use the same `POSTGRES_USER` account. The initialization SQL runs as that account, which owns the reference table under the official PostgreSQL image. Its explicit `GRANT USAGE ... TO CURRENT_USER` and `GRANT SELECT ... TO CURRENT_USER` statements document required access but do not reduce its owner privileges. For an external host, CBSE creates no role: the deployment owner must provision the configured account with at least `CONNECT`, `USAGE` on schema `public`, and `SELECT` on `public.simulation_parameters`; additional privileges are permitted. Database credentials may be literal CBSE deployment configuration, but the generator source contains no duplicated credential constants and the Scenario Detail DB values are not baked into the generated runner image. The reference image initialization owns creation and population of its four rows. Detail DB rows are immutable for this feature: no CBSE component updates or deletes them, and parameter snapshots, versions, or reload-after-translation behavior are not defined.

Each lookup attempt uses a 10-second connection timeout and a 30-second statement timeout. Connection refusal, either timeout, a PostgreSQL connection exception (`08`), transaction rollback (`40`), insufficient-resource error (`53`), or administrative shutdown/crash/cannot-connect-now result (`57P01`, `57P02`, or `57P03`) is transient. After the first transient failure, the generator keeps the request active, continues the framework's 30-second JetStream in-progress acknowledgements, waits exactly 30 seconds with context cancellation, reconnects, and executes the same query once more. Success on the second attempt continues generation. A second transient failure becomes a permanent generation failure. Authentication failures (`28`), insufficient privilege (`42501`), missing relation or other schema errors, invalid recipe input, and invalid query results fail immediately without the delayed retry. Shutdown or failed JetStream in-progress acknowledgement cancels the lookup or wait and leaves the request unacknowledged; it does not create an empty-failure outcome.

Once a lookup has permanently failed, the framework treats it like another generator failure: it atomically persists the empty-failure outcome, publishes the existing empty-image ready message with confirmation, and acknowledges the request only through the normal confirmed-outcome workflow. A successful lookup supplies the four validated integers to the example generator, which packages the checked-in SimPy model and writes the parameterized model into the generated build context. The generated Dockerfile uses the required digest-pinned runner smoke base image, copies only the generated runner files and required Result DB runtime connection configuration, sets a numeric non-root user, and defines the model launcher as its entrypoint. It does not reinstall unversioned dependencies. The generated image starts the baked scenario without command, arguments, or environment variables from SM; it obtains its Pod hostname from the container runtime with Python's `socket.gethostname()`.

The example is a single-server queue implemented with one `simpy.Resource(capacity=1)`. A source process samples interarrival times with `rng.expovariate(arrival_rate)` and creates customers only while their sampled arrival time is less than `run_duration`. Each customer records the time spent waiting for the resource, samples its service time with `rng.expovariate(service_rate)`, and increments the completed count only if service finishes by the simulation horizon. The runner executes `env.run(until=run_duration)`; unfinished customers are neither completed nor included in the mean. `mean_wait_time` is the arithmetic mean for completed customers and is `0.0` when no customer completes.

Each runner container constructs a local Python `random.Random` instance. It requires a non-empty value from `socket.gethostname()` and applies this exact derivation; it must not use module-global random state:

```python
hostname = socket.gethostname()
digest = hashlib.sha256(f"{seed_policy}:{hostname}".encode("utf-8")).digest()
effective_seed = int.from_bytes(digest[:8], "big") & 0x7FFF_FFFF_FFFF_FFFF
rng = random.Random(effective_seed)
```

Kubernetes uses the Pod name as each container's runtime hostname, and replacement Pods receive new names, so repetitions and retries receive independently derived seeds without changing the Core DB, Translator payload, or Job completion-index contract. The derivation is stable for the same `seed_policy` and Pod name and provides practical collision resistance, not a formal uniqueness proof.

The example runner writes one JSONB result with `parameterset_id`, `arrival_rate`, `service_rate`, `run_duration`, `seed_policy`, `effective_seed`, `completed_customers`, and `mean_wait_time`. The first five fields reproduce the lookup input and parameters; `effective_seed` is the derived non-negative 63-bit integer, `completed_customers` is a non-negative integer, and `mean_wait_time` is a non-negative JSON number. The Result DB table remains named from the top-level Core DB scenario ID as `scenario_<scenario-id>_results`; `parameterset_id` does not replace that Core DB identity.

At startup, the template reads exactly `host`, `port`, `dbname`, `user`, and `password` from both `/detaildb-connection` and `/resultdb-connection` and reads the registry configuration mounted at `/registry-auth/config.json`. It rejects missing or malformed values before handling requests, requires basic credentials for the configured base-image and target-repository authorities through the same Docker resolver used by the Operator, and passes the two validated `DatabaseConfig` values only to the generator. Translator opens neither database at startup. The template does not watch, reload, or rotate registry or database credentials while running. Secret updates after startup have no defined effect until the Translator Pod restarts.

The Operator's database connection is an availability-only provisioning probe. After the Deployment and Service for an image form, or the connection Secret for a host form, exist, the Operator creates a fresh client for each Detail and Result database using the common endpoint contract, connects within the shared 10-second resolution-and-connection deadline, executes exactly `SELECT 1` under a 30-second statement timeout, closes the client, and retains no pool or session. It never performs Detail DB parameter lookup, Result DB table creation or inserts, schema validation, DDL, or data mutation through this probe. An invalid connection field is a provisioning error. A syntactically valid endpoint that cannot resolve or connect, times out, is temporarily unavailable, or rejects authentication leaves the experiment in `Provisioning` and requeues the complete probe after five seconds without a fixed attempt limit. Only a successful probe of both databases permits `InProgress`; deletion cancels an active probe or wait. Database transport security and related API fields remain outside this feature, and all three clients explicitly use `sslmode=disable`.

The example generator bakes the Result DB connection configuration and a replaceable result-sink interface into the runner image; it does not bake the Scenario Detail DB configuration because parameter lookup finishes before the image build. This retains the trusted prototype assumption that the generated image contains Result DB credentials: neither the framework, generator, BuildKit progress handling, nor runner may print those values or expose them in image labels or annotations. Database credentials must not be added to NATS messages, Scenario Status, image labels, or annotations.

The configured Result DB role must have `CONNECT` on the configured database, `USAGE` and `CREATE` on its default schema, and permission to create and write the tables it owns; no superuser privilege is required. The example runner uses a 10-second connection timeout and a 30-second statement timeout and performs no inner retry. It connects to PostgreSQL and, in a short transaction, obtains `pg_advisory_xact_lock(0, <scenario-id>)` before creating the scenario table with `IF NOT EXISTS`; the transaction commits immediately after the schema check. This serializes only concurrent first-use table creation by repetitions of the same scenario and prevents catalog races. The runner then performs its result insert in a separate transaction. A timeout or permission failure exits non-zero and consumes the current Kubernetes Pod attempt. The table name and advisory-lock key are derived only from the already validated positive integer scenario ID:

```sql
CREATE TABLE IF NOT EXISTS scenario_<scenario-id>_results (
    id BIGSERIAL PRIMARY KEY,
    result JSONB NOT NULL
);
```

After a successful simulation, each runner appends the JSONB result object defined above. The sequence supplies unique row IDs but does not claim commit-order semantics. Completion indexes are not written to the Result DB, and results have no repetition identifier or uniqueness constraint. A simulation failure performs no result insert. A Result DB connection, advisory-lock, table-creation, or insert failure makes the runner Pod fail and consumes the shared Job retry budget. Kubernetes may create a replacement Pod while that global budget remains.

The result sink is intentionally at-least-once. If PostgreSQL commits an insert but the runner loses the response, the runner exits unsuccessfully and a replacement Pod may run the simulation and append another row. This trusted prototype accepts that an ambiguous commit can therefore produce more result rows than successful completion indexes. The normal no-failure smoke path still requires exactly `number_of_reps` rows. A user-defined generator may replace the per-scenario schema and sink independently, but it must preserve the generated image's ownership of runner startup and result handling.

The namespace-aware subjects above replace the project-only subject names; the existing request and ready JSON payloads remain unchanged. The template uses the exact JetStream consumer contract above and allows at most one active request and build. A successful digest ready message, or a confirmed empty-image failure ready message, is published with JetStream confirmation before the request receives its server-confirmed acknowledgement. NATS transport or publication failures leave the request unacknowledged and retryable; they do not produce an empty-image result.

The BuildKit image exporter adds these credential-free OCI manifest annotations:

- `experiment.cbse.terministic.de/experiment-uid=<full-UID>`
- `experiment.cbse.terministic.de/scenario-id=<decimal-scenario-id>`
- `experiment.cbse.terministic.de/translation-attempt=<decimal-attempt>`

`ready-outcome.json` is the single credential-free durable outcome format. It contains `outcome` (`success` or `empty_failure`), scenario ID, translation attempt, ready subject, and full experiment UID. A success additionally contains deterministic tag and digest; an empty failure contains an empty image and a short non-sensitive failure class. Translator writes the complete file to a temporary file in the same directory and renames it over the marker before publishing ready. It retains the workspace until ready publication and server-confirmed request acknowledgement both succeed.

After BuildKit confirms a successful push, Translator resolves the digest and verifies the repository and all three annotations, then atomically writes the success outcome. A generator, BuildKit, push, digest-resolution, or tag-collision failure atomically writes the empty-failure outcome before its first ready publication. A publish or final-ack retry validates and reuses the exact marker without another generator, build, push, or registry lookup.

On redelivery or process restart, Translator first validates the marker's outcome, experiment UID, scenario ID, attempt, ready subject, and outcome-specific fields. A valid marker is authoritative for that attempt. If the marker was lost because the Pod was replaced, Translator resolves the deterministic registry tag. It treats the tag as the successful build outcome only when the normalized repository and all three manifest annotations exactly match the current request. A missing or mismatched annotation is a permanent identity collision that creates the empty-failure marker; Translator never adopts or overwrites the tag. A registry not-found result permits generation and build; another resolution failure creates the empty-failure marker.

An empty-failure marker is durable across Translator process or container restart while the Pod-local `emptyDir` survives, but there is deliberately no external empty-failure artifact. If Pod replacement loses that marker, redelivery may repeat generation or another failing operation once; SM's exact-attempt handling makes any resulting ready message stale after the first empty outcome was applied. This bounded duplicate work is accepted and must not change a newer scenario attempt. Successful pushes continue to recover externally from their annotated registry tag.

`spec.runner.jobTemplate` is optional. It is a typed `batch/v1.JobTemplateSpec`, not raw YAML and not a ConfigMap containing a Job. The built-in template is used when the field is absent. The public template API is an allow-list against the repository's pinned `k8s.io/api` v0.33 Kubernetes types. A user-supplied field not listed below must be nil, empty, or the Go zero value and is rejected when it has any other value. An explicit JSON value that decodes to the same Go zero value as an omitted field is treated as omitted. The allow-list governs only values users may request; live Job differences are accepted only by the exact, additive-only metadata, and server-derived classification below. This classification changes no alpha4 API field.

Every user field not explicitly allowed by the table is prohibited even when it is not named in this summary. For an accepted template, SM constructs the effective Job by copying only the allowed values and then applying CBSE-owned fields.

The effective Pod sets `restartPolicy: Never`, `automountServiceAccountToken: false`, `runAsNonRoot: true`, and `RuntimeDefault` seccomp. Every runner, auxiliary regular container, and init container receives `privileged: false`, `allowPrivilegeEscalation: false`, and a capability set that drops `ALL`; user-provided positive UID/GID values and `readOnlyRootFilesystem` are retained. The accepted runner digest always replaces the custom template's `runner` image. The image must work with the built-in template; user customization supplies optional integration and scheduling concerns, not missing executable behavior. The Operator's internal `ValidateAndNormalizeJobTemplate` implementation is the sole owner of the allow-list, Kubernetes semantic, non-root security, and template-level normalization checks. It rejects any disallowed field or invalid allowed value and moves the experiment to provisioning `Error` without allowing it to reach `InProgress`. The function is not exposed through a shared package or API, and SM neither imports it nor repeats its policy validation. Because `spec.runner.jobTemplate` is immutable from admission and SM admits runner work only for a live, non-deleting `InProgress` experiment, SM treats the live template as Operator-validated. The Operator's normalized validation copy is not persisted or handed to SM, and this ownership split adds no alpha4 field, status value, annotation, or other handoff artifact.

`JobTemplateSpec.metadata.labels` and `.annotations` become desired Job metadata; `spec.template.metadata.labels` and `.annotations` become desired Pod-template metadata inside the Job specification. As a separate construction concern rather than template policy validation, SM builds the scenario-specific effective Job, normalizes empty user maps and slices to nil, de-duplicates and sorts set-like collections such as image pull Secrets into canonical order, and retains every other list in its defined desired order. SM then applies CBSE's protected overrides and the ordinary Kubernetes defaults from the repository's pinned v0.33 API before final normalization and hashing. For example, the effective Pod contains `schedulerName: default-scheduler`, and that value is exact even though users may not configure `schedulerName`. Job or Pod `name`, `generateName`, namespace, owner references, finalizers, reserved metadata keys, status, and server metadata are never accepted from the template. Reserved metadata means every key under `experiment.cbse.terministic.de/` plus Kubernetes Job controller identity keys `controller-uid`, `job-name`, `batch.kubernetes.io/controller-uid`, and `batch.kubernetes.io/job-name`; non-reserved user labels and annotations remain permitted integration settings.

One shared live-Job classifier compares that desired effective Job with the Job returned by a successful create, a named Job read after `AlreadyExists`, and every later observation. It assigns every live field to exactly one of these classes:

- **Exact.** The live Job must preserve every CBSE-owned value and every user-specified allow-listed value after the pinned v0.33 defaulting and normalization above. This covers the expected namespace and deterministic name, lifecycle fields, the single expected experiment owner reference, absence of finalizers, every desired reserved metadata value, every desired non-reserved metadata key and value, the complete Job and Pod specifications, container and init-container membership and fields, volumes, mounts, environment entries, image pull Secrets, scheduling constraints, probes, resources, and security settings. Prohibited values must remain absent. Admission may not add, remove, or change a container, init container, volume, environment entry, mount, image pull Secret, scheduling field, owner reference, finalizer, or any other `spec` value, even when that value's field category is user-allow-listed. Canonically set-like collections are compared in normalized order; every other list is compared in its defined desired order.
- **Additive-only metadata.** This class applies only to Job labels, Job annotations, Pod-template labels, and Pod-template annotations. Each live map must contain every desired key with its exact desired value. A live map may also contain any additional syntactically valid key and value when the key was absent from the desired map and is not reserved. These additional entries are excluded from the desired hash and protected comparison and are not persisted by CBSE. They are non-authoritative: admission may add them, and they may change or disappear between reconciliations while the desired entries remain immutable. Metadata fields outside these four maps are not additive-only.
- **Server-derived.** TypeMeta, Job status, and ordinary server metadata, including the Job UID, resource version, generation, creation timestamp, and managed fields, are ignored for desired-contract comparison. The classifier instead uses the live Job UID and name to require the canonical API-generated selector and the legacy and `batch.kubernetes.io` controller-UID and Job-name labels on the Pod template. A live `priority` is accepted as API-admission-derived only while the desired `priorityClassName` remains exact, and live RuntimeClass `overhead` is accepted only while the desired `runtimeClassName` remains exact. SM trusts admission for those two derived values and performs no PriorityClass or RuntimeClass read, so they add no RBAC. A deletion timestamp, deletion grace period, or finalizer is not an acceptable server-derived difference; a deleting or finalized Job cannot be confirmed or adopted.

SM computes `experiment.cbse.terministic.de/job-contract-sha256` as lowercase hexadecimal SHA-256 over `encoding/json` output from a typed hash-input struct containing the finalized desired Job labels and annotations and the normalized desired effective Job specification, including desired Pod-template metadata. Go JSON encoding provides sorted string-map keys; the normalization above removes nil-versus-empty and set-ordering ambiguity. The hash excludes Job name, namespace, owner references, status, TypeMeta, server metadata, the hash annotation itself, additive-only live metadata, and the API-server-generated Job selector and controller/job-name labels that cannot be known before creation. It represents the fully defaulted client-side desired contract before API admission. The same effective-Job builder, normalization function, and classifier are used for create-response validation, recovery, and observation.

An `AlreadyExists` result is an expected recovery case when Kubernetes accepted Job creation but SM restarted or lost the subsequent Core DB transition. SM accepts the existing Job only when its stored contract-hash annotation equals the newly computed desired hash and the shared classifier accepts it. Any owner, identity, desired-value, exact-field, or server-derived canonical-value mismatch is a collision. SM never adopts, rewrites, or deletes a mismatching `AlreadyExists` Job.

### Scheduler boundary and RBAC

SM places workload creation and observation behind a small, resource-neutral internal scheduler interface. Core orchestration supplies a validated runner projection and receives successful repetition count, active state, and terminal success or failure without importing `batch/v1` types. This branch provides only the `batch/v1` Kubernetes Job adapter, which owns Job-template merging and Kubernetes-specific identity checks. Alpha4 has no scheduler-provider selection field. A future Volcano or other scheduler adapter must add its own explicit API configuration, template type, resources, third-party integration, and additive RBAC without changing this branch's core state-machine contract or broadening base permissions speculatively.

The default SM ServiceAccount receives only these workload permissions:

- `get`, `list`, `watch`, and `patch` on alpha4 `simulationexperiments`;
- `create`, `delete`, `get`, `list`, and `watch` on `batch/jobs`;
- `get`, but not `list` or `watch`, on the core Secret named `cbse-registry-auth`, enforced with `resourceNames: ["cbse-registry-auth"]`; and
- `get`, but not `list` or `watch`, on core `serviceaccounts`.

Alpha4 SM uses a ClusterRole and ClusterRoleBinding because it discovers experiments and creates, observes, or terminally deletes Jobs across namespaces. Kubernetes RBAC cannot restrict a metadata-finalizer patch to one field or restrict `get` to dynamically named runner ServiceAccounts, so cluster-wide experiment `patch` and ServiceAccount `get` without `list` or `watch` are the narrowest standard RBAC boundaries for those resources. The registry Secret name is fixed, so the Secret rule must use `resourceNames: ["cbse-registry-auth"]`; SM must not receive permission to read another Secret. Application code uses experiment patch only for the exact SM finalizer, performs only direct named reads for `cbse-registry-auth` and the deterministic runner ServiceAccount, and never exposes a generic lookup endpoint. Normal Job deletion is restricted in application code to the exact label-and-owner verification contract above; the rejected-create cleanup defined below instead requires the expected namespace and name and uses the UID returned by that create call as a delete precondition. SM receives no `deletecollection`, Pod, ConfigMap, Job update, Job patch, experiment-status update, experiment update, experiment delete, PriorityClass, RuntimeClass, or RBAC-management permission. ConfigMap and Secret volumes other than the required registry Secret are resolved by Kubernetes and do not require SM to read those objects. Per-experiment runner ServiceAccounts have no RoleBinding and set `automountServiceAccountToken: false`.

Before starting informers, NATS consumers, runner selection, or observation, SM uses Kubernetes authorization checks to verify every required verb and resource above across namespaces, including experiment patch for finalizer management and Job delete for terminal control. A denied startup check is a fatal installation error and prevents startup because the deployment cannot execute its contract. If an operation for an individual scenario later returns HTTP `403 Forbidden`, SM does not terminate the process: it logs the verb, resource, namespace, and scenario, then applies the guarded transition for that scenario to `Failed`. A `Forbidden` during an `Error`, `Failed`, deletion, or rejected-create Job cleanup follows that cleanup's retry contract instead of changing an additional scenario. A later `Forbidden` on the process-wide experiment list/watch has no individual scenario to fail. SM logs the affected resource and operation, keeps the process running, and retries list/watch every five seconds until access succeeds. It performs no domain-state transition and does not stop unrelated scenario keys already available to workers.

### Configuration validation and failure classes

The implementation must not use “invalid configuration” as an undifferentiated error. Validation is grouped and classified as follows:

1. **Alpha4 experiment admission and provisioning.** The Kubernetes API server rejects an update that adds, removes, or changes any immutable alpha4 field listed above, including the Translator image, command, arguments, service type, node port, and port; the rejected update is never persisted, never starts an in-place Translator rollout, and therefore does not cause an Operator-owned phase transition. For an admitted new object, the Operator rejects an invalid namespace or experiment name; an invalid Detail or Result `DatabaseSpec`; a non-digest Translator, Builder, or base image; a tagged or digested `translator.repository`; a `registryAuthSecretRef.name` other than `cbse-registry-auth`; a referenced Secret that does not yet exist in the experiment namespace; a wrong-type or malformed Docker configuration Secret; a missing or invalid basic-auth entry for a required registry host; invalid Builder request or limit quantities; or a runner Job template containing an unlisted field, an invalid allowed value, a protected-field override, or a non-root violation. The Operator reports the exact field or referenced object and moves provisioning to `Error` before creating experiment components.
2. **Translator startup.** Translator refuses readiness for a missing or malformed NATS URL, a NATS URL containing user information, stream, request subject, ready-subject template, consumer name, experiment identity, repository, or base image; missing or malformed registry, Scenario Detail DB, or Result DB Secret files; a non-numeric or out-of-range database port; or an unwritable workspace. The reference template accepts no NATS credential setting or mount. A valid but not-yet-ready BuildKit socket or worker is a retryable startup dependency: Translator waits under the mandatory admission gate without attaching its request consumer. The error names the setting or mounted path without printing its value when it may contain credentials.
3. **Scenario Manager startup.** `SCENARIO_MANAGER_RUNNER_START_WORKERS` is optional; an absent value resolves to `4`, while a present value must be a base-10 integer in `1..64`. A malformed, zero, negative, or greater-than-64 value is a fatal startup configuration error. SM also fails startup for a malformed Core DB DSN, incompatible required table schema, an invalid or credential-bearing NATS URL, a non-empty legacy NATS username or password, invalid NATS subject template, invalid configured stream or consumer name, or a denied required cluster-wide Kubernetes authorization check. It reports the exact setting, schema check, or denied Kubernetes verb/resource before starting informers, consumers, scenario selection, runner-start discovery, or runner observation. After all startup dependencies, informers, consumers, selection, runner-start reconcilers, and observation workers start successfully, SM emits its existing `Scenario Manager is ready` log. The smoke harness continues to use this log as its application-start signal.
4. **Runtime dependencies.** A syntactically valid but unavailable NATS server or Kubernetes API is a retryable dependency failure. A database endpoint resolution or connection failure follows the policy of the client using the common endpoint contract: Operator keeps provisioning and repeats its availability probe, Translator applies its bounded Detail DB lookup retry and confirmed empty-image workflow, and runner exits unsuccessfully so the Result DB failure consumes the shared Job retry budget. Before Translator accepts a request, unavailable BuildKit is the retryable startup dependency governed by the admission gate; after it accepts a request, a registry, BuildKit, generator, push, or digest-resolution failure follows the confirmed empty-image workflow. Except for cleanup operations governed by their own retry contracts, a scenario-specific Kubernetes `Forbidden` or terminal Job failure transitions only that scenario to `Failed`; SM continues other work. None of these failures is relabeled as a startup configuration error.
5. **Messages and scenario work.** Invalid subject shape, payload shape, attempt identity, repository, or scenario-specific generator input follows the poison-message or guarded scenario-failure rules defined by the owning workflow. It is not a process startup configuration failure. A lifecycle rejection is classified separately: pre-`InProgress` work is transient and retryable, while `Error`, `Failed`, `Completed`, and deletion are permanent for message handling and use ACK-and-discard without message-driven scenario mutation. The independent `Error`/`Failed` terminal action may bulk-transition unfinished scenarios to `Failed` as lifecycle control.

### Lightweight scenario observability

Scenario execution uses concise, credential-free logs and Kubernetes' existing Job and Pod diagnostics. SM logs Job creation or adoption and one terminal scenario outcome. Those records include experiment namespace and name, scenario ID, translation attempt, Job name, requested repetitions, computed repetitions, outcome, and a short reason. SM does not log every successful repetition or every unchanged observation poll.

The basic generated runner emits no framework debug stream and no per-simulation-event log. On each runner-controlled failed Pod attempt, it emits one timestamped terminal record containing scenario ID, Pod hostname, failure stage, and a sanitized reason, then exits non-zero. A controlled simulation failure writes no result row; an ambiguous PostgreSQL commit may have written a row before the failure became visible. Kubernetes owns the completion index used for retry accounting, but the Pod hostname and index do not create a repetition identity in the Core DB or Result DB. Failures before the runner starts remain visible through standard Job conditions, Pod status, and Kubernetes events. SM does not gain Pod-read RBAC for logging.

Automatic collection, centralized storage, size limits, retention periods, and deletion of old scenario logs are future operational work. This branch keeps completed and failed Jobs available for inspection while the experiment remains `InProgress` or `Completed`; `Error`, `Failed`, and deletion remove them under the lifecycle contract above. It does not implement time- or age-based log garbage collection.

### State boundary

This branch implements this prefix of the scenario diagram:

```text
Created -> Scheduled -> StartingRunners -> InProcessing
                          | startup failure       | Job success
                          v                       v
                       Failed             PostProcessing

InProcessing --Job failure--> Failed
```

`Scheduled -> StartingRunners` remains owned by accepted Translator ready handling. `StartingRunners -> InProcessing` is owned by SM after a matching Job exists. SM then observes that exact Job. Job success owns `InProcessing -> PostProcessing`; Job failure owns `InProcessing -> Failed`. `PostProcessing` is a normal-execution boundary state in this branch. SM does not invoke the PostProcessingService or move a scenario from `PostProcessing` to `StartingRunners` or `Finished`; only the experiment-level `Error`/`Failed` terminal action may move it to `Failed`.

The experiment diagram remains unchanged. The Operator moves an alpha4 experiment through `Pending`, `Provisioning`, and `InProgress` when components are ready, and may set `Error` for a provisioning problem. The intended future owner of execution-level `Failed` and `Completed` transitions is SM. This branch does not implement those two experiment transitions and never writes `SimulationExperiment.status`. On `Error` or `Failed`, it closes the lifecycle gate, deletes verified runner Jobs, and marks unfinished scenarios `Failed`; on `Completed`, it only closes the gate and retains diagnostic state. None of those three phases deletes or purges NATS artifacts. Deletion closes the gate, deletes verified Jobs, and then runs the destructive messaging and project cleanup defined above. No NATS or JetStream request is expected in `Completed`, and SM performs no scenario-work consumption in `Error`, `Failed`, `Completed`, or during deletion; terminal cleanup is lifecycle control rather than scenario-work consumption.

### Concurrent runner-start reconciliation

Runner start is not processed by the serial BSSL actionable selector. That selector must exclude `StartingRunners` and retain its existing ascending-positive-`scenario_status.id` FIFO behavior for the states it continues to own. The stored `priority` column remains informational and does not affect BSSL selection or runner-start dispatch.

SM starts one runner-start discovery immediately when the runner-start scheduler starts and repeats discovery every five seconds. Each discovery query returns all rows currently in `StartingRunners`, ordered by ascending positive `scenario_status.id`. The process-local scheduler uses the positive scenario-status ID as its de-duplication key. This key is only an internal bookkeeping identity for one scenario reconciliation; it is not a Kubernetes Job, Pod, worker node, or compute-resource reservation. An ID may appear at most once across the scheduler's ready, delayed, and in-flight sets. A process restart intentionally loses that in-memory state and the new process's immediate discovery reconstructs it from the authoritative database rows.

`SCENARIO_MANAGER_RUNNER_START_WORKERS` fixes the number of runner-start reconciler goroutines for the lifetime of the SM process. Its default and validation rules are defined in the startup configuration section above. Whenever a reconciler becomes available, the scheduler dispatches the lowest currently known and eligible positive ID; it does not preempt an in-flight reconciliation if a lower ID is discovered later. Up to the configured number of distinct scenario IDs may be reconciled concurrently. Kubernetes API completion and guarded database-transition order may differ from dispatch order because those workflows run concurrently.

A reconciler loads and validates the fresh runner-start projection, then creates or confirms that scenario attempt's deterministic Job and applies the guarded state transition. A transient failure records a process-local `nextEligibleAt` equal to five seconds after that failed attempt completes, releases the reconciler immediately, and schedules a wake-up without sleeping or occupying a reconciler goroutine. When the delay expires, the ID rejoins the eligible set and again participates in ascending-ID dispatch ahead of any higher eligible ID that has not already been dispatched. There is no persisted retry counter, exponential backoff, or scenario-failure limit. Other eligible IDs continue to use free reconcilers while a low ID is delayed or while another reconciliation is slow.

The scheduler removes an ID after a successful guarded `StartingRunners -> InProcessing` transition, a permanent startup failure, a stale projection or state, or closure of the owning experiment's lifecycle gate. A zero-row guarded update is stale success. Gate closure cancels matching ready, delayed, and in-flight work; every in-flight reconciler still performs the live experiment and gate checks required below. SM shutdown stops discovery, cancels all delayed and in-flight work, and joins every runner-start reconciler before the process exits.

Multiple SM replicas may discover and reconcile the same database ID. Cross-process correctness does not depend on the process-local de-duplication state: every replica uses the same deterministic Job name, accepts `AlreadyExists` only after the full identity and contract verification below, and uses guarded database transitions. At most one guarded transition wins; matching work in another replica converges as stale success.

The worker setting limits only simultaneous SM runner-start validation and Kubernetes API `GET`/`CREATE` workflows. It does not limit the total number of scenario Jobs SM may submit, the number of active Jobs, Job `parallelism`, Pods, Kubernetes worker nodes, or cluster CPU and memory use. A runner-start slot is released once the Job has been created or confirmed and the workflow reaches one of the removal or retry outcomes above. Kubernetes Job controllers and the Kubernetes scheduler exclusively own Pod creation, retry, placement, and resource admission; Pending or unschedulable Pods neither retain a runner-start reconciler nor cause an SM capacity decision.

### Runner-start projection and validation

SM reads one runner-start projection from the Core DB: scenario ID, `number_of_reps`, `number_of_computed_reps`, persisted runner digest, translation attempt, and project namespace and name. It then gets that exact alpha4 experiment from Kubernetes, reads its current UID, and requires phase `InProgress`. It revalidates the runner digest and requires its normalized repository to equal `spec.translator.repository` before creating a Job. The live UID becomes the owner-reference and workload-label identity; it is not loaded from Core DB.

`number_of_reps` must be between `1` and `100000`, and `number_of_computed_reps` must initially be zero for this execution. A larger value is a permanent invalid-repetition failure and no Job create is attempted. The live `InProgress` phase and immutable template establish that the Operator accepted `spec.runner.jobTemplate`; SM does not invoke a template-policy validator. SM performs direct named `GET` operations for the experiment's registry Secret and deterministic runner ServiceAccount. It revalidates the Secret type, key, Docker JSON, and basic credentials for the generated image's registry authority with the same standard resolver used by the Operator; this catches a Secret replaced after provisioning. The Job includes that Secret reference in `imagePullSecrets`; a custom template may add other distinct pull Secrets but cannot remove or replace it. If SM unexpectedly cannot construct and canonicalize the effective Job from an accepted template, it treats that internal contract violation as a permanent scenario startup failure and makes no Job create call; this defensive error path is not a second template-policy validation pass.

The Job and its Pod template must carry these labels:

- `experiment.cbse.terministic.de/project=<experiment-name>`
- `experiment.cbse.terministic.de/experiment-uid=<full-UID>`
- `experiment.cbse.terministic.de/scenario-id=<decimal-scenario-id>`
- `experiment.cbse.terministic.de/translation-attempt=<decimal-attempt>`

The Job also carries `experiment.cbse.terministic.de/job-contract-sha256=<lowercase-SHA-256>` using the effective-contract hashing rules above. Before accepting `AlreadyExists`, SM requires the stored hash to match and runs the shared classifier over the whole live Job, including owner UID, identity labels, runner image and executable fields, indexed completion mode, completions, parallelism, absent `backoffLimitPerIndex`, global `backoffLimit: 4`, absent `maxFailedIndexes`, restart policy, required ServiceAccount and image pull Secret, token setting, and Pod security settings. A mismatch is a collision and is never adopted, rewritten, or deleted.

### Startup result handling

SM runs the shared classifier on the Job returned by a successful create and calls the guarded `StartingRunners -> InProcessing` update only after that returned Job passes. It uses the same classifier to confirm a named Job read after `AlreadyExists`. If the update affects zero rows, SM logs a stale result and does not change the Job. This is expected when another worker confirmed the same Job and won the transition.

If a successful create response fails classification but contains the expected namespace and name and a non-empty UID, SM deletes that exact returned Job with the returned UID as a delete precondition, even when admission changed its owner references or reserved labels. It retains `StartingRunners`, waits until the deterministic Job is absent, and reissues the UID-preconditioned delete every five seconds while the Job remains present, whether the preceding delete succeeded or failed and including after `Forbidden`; this rejected-create cleanup is an explicit exception to the ordinary per-scenario `Forbidden` rule. Only after absence is confirmed does SM apply the guarded `StartingRunners -> Failed` transition. If the create response has an unexpected namespace or name or has no UID, SM treats it as a permanent identity failure, issues no unverified delete, and applies the guarded failure transition.

The following are permanent startup failures. SM calls the guarded `StartingRunners -> Failed` transition: invalid repetition state, image, or image repository; an unexpected effective-Job construction failure; missing or wrong-type pull Secret; a missing experiment outside the supported finalizer lifecycle; a runtime Kubernetes `Forbidden`; and a Job collision. An `Error`, `Failed`, `Completed`, or deleting experiment is not an individual startup failure: the worker makes no state transition or Job create, because the experiment phase action owns cancellation and any bulk scenario update. If a create crossed gate closure and succeeded before the guarded `StartingRunners -> InProcessing` update, the worker applies the verified terminal Job deletion rule instead of leaving the stale Job behind.

Ordinary Kubernetes transport failures and the fixed 10-second deadline on each get or create call are retryable without changing scenario state. An experiment in an empty, `Pending`, or `Provisioning` phase is also retryable. In each case, the concurrent runner-start scheduler applies the fixed five-second delayed-eligibility contract above. Retries always target the same deterministic Job.

### Runner terminal observation

Runner observation is independent of selection and translation. SM performs one discovery immediately after startup and then a discovery tick every five seconds. Each tick lists all `InProcessing` rows and adds their scenario keys to one de-duplicating, process-local work queue. Four fixed workers reconcile keys concurrently. A small process-local keyed state records whether a key is queued or in flight and the first discovery tick at which it is eligible again: a tick never adds a queued or in-flight key, and after an observation completes the key is eligible only at the first strictly subsequent five-second tick. Thus every non-terminal observation, including one following a transport failure, occurs in these five-second slices; observation uses no `AddAfter`, rate limiter, or per-scenario exponential backoff. The keyed state is intentionally lost on SM restart, after which the immediate startup discovery safely resumes observation. Every Kubernetes call made for one key has a 10-second deadline. `InProcessing` is not part of the ordinary lowest-ID actionable query. A missing, forbidden, colliding, slow, or failing Job therefore consumes only its own bounded worker time and cannot prevent discovery or eventual reconciliation of other `InProcessing` scenarios.

The observation projection contains the scenario ID, requested and computed repetition counts, translation attempt, project namespace, project name, and all desired inputs needed to rebuild and hash the deterministic Job contract. The scheduler adapter gets the current experiment to obtain its live UID and phase. It observes the exact Job only for the same live `InProgress` incarnation, then runs the shared classifier before applying progress or a terminal result. Mutation or removal of an exact desired value is a collision; non-reserved extra metadata and legitimate server-derived state remain acceptable. `Pending`, `Provisioning`, and empty phase requeue without scenario mutation. `Error`, `Failed`, `Completed`, and deletion cause a successful observation no-op because the experiment phase action owns any cancellation or bulk state change. SM does not watch Pods.

The result rules are:

- For every observation, SM parses the Kubernetes compressed-index syntax in `job.status.completedIndexes`, validates that every interval is ordered, non-overlapping, and within `0..number_of_reps-1`, and counts the represented indexes without expanding them into a large slice. It atomically sets `number_of_computed_reps` to `GREATEST(current_value, completed_index_count)` while guarding scenario ID and state `InProcessing`. `completedIndexes`, not the aggregate `status.succeeded`, is the authoritative unique-index set. The value never decreases or exceeds `number_of_reps`, so duplicate Pods for one index, informer redelivery, Pod retry, and SM restart cannot double-count an index. A malformed or out-of-range server-owned index string is treated as a Job identity/status collision and fails only that scenario.
- A failed Pod consumes the Job's global retry budget. Kubernetes creates a replacement Pod while that budget remains. A Job with `Failed=True` first preserves the observed partial successful-index count, then causes a guarded `InProcessing -> Failed` update.
- A Job with Kubernetes `Complete=True` first records `number_of_computed_reps = number_of_reps`, then causes a guarded `InProcessing -> PostProcessing` update.
- A Job without either terminal condition remains `InProcessing` without error.
- A missing Job, per-operation deadline, or ordinary Kubernetes transport failure leaves the row `InProcessing` without a scenario-state change. It is observed again only through the first strictly subsequent five-second discovery tick. This cadence is process-local and restarts with the immediate discovery after an SM restart. This branch does not recreate a Job after the scenario entered `InProcessing`.
- A runtime `Forbidden` while getting the experiment or Job is a permanent failure for that scenario. SM preserves the current successful-index count, applies the guarded `InProcessing -> Failed` transition, and continues processing other scenarios.
- A Job that exists under the deterministic name but does not match the observation projection is a collision. SM applies the guarded `InProcessing -> Failed` transition and does not adopt the Job.
- A stale projection or zero-row guarded update is a successful no-op.

A non-terminal active or pending Job for a live `InProgress` experiment is a successful observation and remains eligible only for the first strictly subsequent five-second discovery tick. Kubernetes scheduling delay, `Job.status.active > 0`, and unschedulable Pending Pods are not failures; Kubernetes remains responsible for admitting Pods as resources become available.

If an invalid Job reports both terminal conditions, SM treats `Failed=True` as failure and does not move the scenario to `PostProcessing`. `number_of_computed_reps` records Kubernetes-confirmed successful completion indexes; SM does not derive it from Result DB rows. Completed and failed Jobs remain present for inspection unless the owning experiment later enters `Error` or `Failed`, or is deleted, in which case the experiment phase action removes them.

### Smoke registry cleanup

The smoke test components and shared runner base are published under `registry.unibw.de/i31bdase/cbse-test`, the reference Detail DB image under `registry.unibw.de/i31bdase/cbse-test/scenario-detail-database`, and generated runner images only under `registry.unibw.de/i31bdase/cbse-test-runner`. The rendered alpha4 experiment sets `spec.translator.repository` to the exact runner repository, copies the validated `DETAIL_DB_IMAGE` digest to `spec.detailDatabase.image`, sets `spec.translator.registryAuthSecretRef.name` to `cbse-registry-auth`, copies `TRANS_IMAGE` and `RUNNER_BASE_IMAGE` from generated `images.env`, and copies `BUILDER_IMAGE` and `POSTGRES_IMAGE` from the checked-in source lock. The Operator copies that Secret name into the image-based Detail and Result DB Deployment Pod templates as `imagePullSecrets`; only Translator and BuildKit mount the referenced Docker configuration read-only. Translator uses the configured runner base to generate scenario-specific images on demand; there is no prebuilt scenario-specific runner smoke image. The full smoke path uses the reference Translator's basic SimPy generator and rootless Builder sidecar, not the synthetic Translator mock.

The cleanup adapter is part of the shell harness and uses the already-required `curl` and `jq`; no separate registry CLI or credential store is introduced. Its API base URL is `https://registry.unibw.de/api/v2.0`, and it authenticates with the protected basic credentials resolved from the Docker configuration. It lists runner artifacts through `GET /projects/i31bdase/repositories/cbse-test-runner/artifacts`, resolves a tag or digest and reads its digest, tags, and OCI annotations through `GET /projects/i31bdase/repositories/cbse-test-runner/artifacts/<reference>`, and deletes a verified artifact only by digest through `DELETE /projects/i31bdase/repositories/cbse-test-runner/artifacts/<digest>`. Listing must follow Harbor pagination until all artifacts are examined. The adapter must not call Harbor project, project-metadata, or whole-repository deletion or update endpoints, and it does not use the OCI Distribution deletion endpoint. Registry cleanup removes Harbor artifact records and tags; Harbor's later physical blob garbage collection is external to this feature.

The harness records the full experiment UID and every exact runner tag and digest observed during the smoke run. The deterministic `runner-<UID-prefix>-s<scenario-id>-a<attempt>` prefix may discover a push that completed before the harness recorded its digest, but prefix match alone never authorizes deletion. Before deleting any discovered or recorded manifest, the cleanup adapter resolves the tag and digest, reads the manifest, and requires all three framework OCI identity annotations to match the full experiment UID, scenario ID, and attempt encoded by that exact expected tag. A missing or mismatched annotation fails cleanup for that candidate without deleting it. Harbor artifact deletion by digest removes every tag attached to that digest, so the adapter must inspect the complete tag set before deletion. Any attached tag other than the exact expected deterministic runner tag makes the candidate unsafe: cleanup fails for that candidate and must not issue its DELETE request. An artifact with no additional tag may be deleted after its identity checks pass. If both the expected tag and recorded digest are already absent when cleanup begins, that candidate is already clean and counts as success without a DELETE request; absence is therefore idempotent. If only one reference is absent while the other still resolves, the adapter must inspect the remaining artifact and apply the same annotation and complete-tag-set checks rather than treating it as absent. After deletion, the adapter requires both the exact tag and digest to be absent. An unconditional exit trap attempts every verified candidate whether smoke succeeds, fails, or retains Kubernetes resources and never targets `cbse-test`, `cbse-test/scenario-detail-database`, or any shared Operator, SM, Builder, base, PostgreSQL, EDS, or Translator image.

Smoke preflight requires the built-in cleanup adapter, a readable protected Docker configuration, the `cbse-registry-auth` source Secret, the exact component, reference Detail DB, and runner repository names, at least one qualifying `amd64` Node as defined above, and the exact checked-in source-image lock. It rejects a source-image environment override or lock mismatch. A normal smoke run builds and pushes all three repository-owned outputs and validates `TRANS_IMAGE`, `RUNNER_BASE_IMAGE`, and `DETAIL_DB_IMAGE` from current build metadata; a skip-build run instead requires all three explicitly supplied output values and validates their exact repositories and digest forms. All image validation happens before cluster mutation. Preflight then sends an authenticated Artifact List request for `i31bdase/cbse-test-runner`. HTTP `200` is accepted when the repository already exists; Harbor repository-not-found HTTP `404` is also accepted before the first generated-runner push because `cbse-test-runner` is intentionally not pre-provisioned. HTTP `401`, `403`, or any other result fails preflight. The accepted initial `404` establishes only that the repository is absent, not that Artifact List is authorized. The first generated-runner push must create the repository, after which the harness requires Artifact List to return `200`; this post-push list and the first annotation-verified cleanup are the authoritative verification of Artifact List, Read, and Delete. A denied list, read, or deletion fails cleanup. Credential material is never a source-code or specification input and is supplied only through the protected runtime sources defined above. Cleanup attempts every candidate even when one deletion fails. Cleanup failure is written to run artifacts without request headers, tokens, credential values, or credential paths and fails an otherwise successful smoke run; on an already-failed run it is reported in addition to the original failure. There is no unresolved external image-digest input: the four source digests are fixed by `test/e2e/images.lock.env`, and the three repository-owned output digests are produced by the build or supplied together for a validated skip-build run. Full feature acceptance remains blocked only until the implementation and mandatory smoke suite pass with the protected registry-auth runtime input.

### Verification and shutdown

All Job-template allow-list, Kubernetes semantic, non-root security, zero-value, and template-level normalization fixtures in this section are Operator tests. For every invalid template class, verify that the Operator reports the template error, moves the experiment to `Error` without reaching `InProgress`, and prevents SM runner-start admission. Scenario Manager effective-Job tests use only templates accepted by the Operator validator; they cover merge, pinned defaulting, canonicalization, hashing, create recovery, and observation rather than template-policy validation.
