# Specification for Alpha4 Simulation Runner Startup and Translator On-Demand Image Creation

This document has the following structure:

1. Mission Statement -- explains the intent and attitude of the work.
2. Scope -- explains the boundaries, goals, and explicitly chosen workflow.
3. Change Location -- identifies the code, API, and manifest areas expected to change.
4. Logic Description -- describes the implementation behavior and ownership boundaries.

## Mission Statement

This branch turns the Scenario Manager (SM) from a component that only advances a scenario to `InProcessing` into the component that starts and observes the scenario's Simulation Runner workload on Kubernetes.

Translator remains an always-on, per-experiment service, provisioned and managed by the Experiment Operator. This branch does not replace it with a Job or change its NATS/JetStream request-consumer model. “On-demand container creation” means that Translator creates the executable simulation model and builds its Simulation Runner image only after it receives a request for a claimed scenario. It then returns the immutable runner image reference through the existing ready-message workflow, from which SM starts the runner on demand.

CBSE cannot provide one universal production Translator because translating a scenario into an executable model is user-defined. Instead, this branch provides a production-quality reference Translator template in `component-templates/translator/`. The template owns the stable NATS/JetStream, BuildKit, registry, digest, acknowledgement, and extension contracts. Its included SimPy generator is an intentionally small example and replacement point, not a production simulation model.

The implementation must make Kubernetes runner Jobs a projection of durable scenario state, not a second source of truth. Database state and guarded transitions decide ownership; workloads perform external work. The coding agent should favor small, explicit, idempotent behavior that is safe across SM restarts and retries while preserving the existing Translator handoff boundary.

The coding agent should favor clarity over cleverness: write small, explicit, modular code that follows nearby patterns. Each component should have one obvious responsibility, explicit dependencies, descriptive errors, and no hidden package-global state. Understand the existing lifecycle, ownership boundaries, and tests first; reuse suitable abstractions, and introduce new ones only to clarify a boundary or enable independent testing.

Work incrementally and stay within scope. Preserve the Translator request and ready-message contracts, durable Scenario Manager state machine, and Kubernetes ownership patterns unless this specification changes them. Avoid redesigns, speculative compatibility layers, and unrelated cleanup. Make retries, restarts, and `AlreadyExists` results deliberate and inspectable: confirm the exact expected resource or return a useful conflict; never silently adopt it. Validate image references, Secret types, namespaces, ownership, and lifecycle state at boundaries. Do not weaken security implicitly, hide privileged requirements, or treat a created Job or pushed image as proof of a successful simulation.

Write clear documentation alongside the code. Explain the lifecycle, ownership, configuration, security and prototype assumptions, operational diagnosis, and deferred hardening. Tests must cover normal behavior, the exact validation groups defined below, stale claims, cancellation, identity collisions, repeated reconciliation, partial external success, and cleanup.

## Scope

This change introduces the only supported `SimulationExperiment` API version: `experiment.cbse.terministic.de/alpha4`. It defines the Translator image-build architecture, starts Simulation Runner Jobs, and observes their terminal result through the `PostProcessing` boundary.

`alpha4` is introduced by this feature as the only served, storage, and reconciled version. It is the active API, not a deprecated or transitional version. Only `alpha2` and `alpha3` are retired. There is no legacy reconciler, conversion webhook, compatibility mode, or automatic migration.

### Upgrade from alpha2 or alpha3

This is a breaking upgrade. Before installing the alpha4-only CRD, operators must export the desired old resources, transform each manifest to alpha4 by supplying every new required Translator registry and Builder field, delete all old `SimulationExperiment` resources, and delete the old CRD. They then install the alpha4 CRD and create the transformed resources. The Operator and SM must never perform these destructive steps.

The shared smoke cluster follows the same alpha4-only contract but does not perform the breaking upgrade. The smoke harness must never delete or migrate the shared CRD. Its preflight requires the installed CRD to serve and store only alpha4. It fails before creating a test namespace when it finds alpha2, alpha3, another storage version, or incompatible `status.storedVersions`. A cluster administrator performs the one-time breaking upgrade outside the test harness. Fast envtest coverage installs the generated alpha4-only CRD in an isolated control plane and verifies that alpha2 and alpha3 are not served.

### In Scope

1. **Alpha4 API, identity, and registry authentication.**
   - Carry the alpha3 user-facing schema into `api/alpha4`, retain required `spec.translator.baseimage`, and add required `spec.translator.registryAuthSecretRef corev1.LocalObjectReference` and `spec.translator.builderImage`. In YAML, the reference is an object such as `registryAuthSecretRef: {name: experiment-registry}`; it is never an inline, plain, or base64-encoded credential string. `spec.translator.image` continues to select the Translator container. `builderImage` independently selects its rootless BuildKit sidecar, while `baseimage` selects the runner base from which Translator generates scenario-specific images.
   - Add optional `spec.translator.builderResources corev1.ResourceRequirements`. Only CPU and memory entries in `requests` and `limits` are accepted; resource claims, huge pages, extended resources, and every other key are rejected. The Operator computes the effective resources without mutating the CR: missing CPU and memory limits default independently to `1` CPU and `2Gi`, while requests have no defaults and remain absent unless supplied. Every supplied quantity must be positive and each request must not exceed its corresponding effective limit.
   - Add optional `spec.runner.jobTemplate` as a typed Kubernetes `batch/v1.JobTemplateSpec`. When absent, SM uses the minimal built-in runner Job. When present, it provides the permitted Job and Pod customization described below.
   - `registryAuthSecretRef.name` identifies an existing Secret in the `SimulationExperiment` namespace. Before provisioning any experiment component, the Operator gets that exact Secret and requires type `kubernetes.io/dockerconfigjson` and a `.dockerconfigjson` key containing valid Docker configuration JSON. Credential lookup uses the same standard Docker config-file resolver semantics as BuildKit, including Docker Hub's standard aliases, rather than a CBSE-specific host normalizer. The resolver must return non-empty basic-auth username and password values for the registry authority parsed from `spec.translator.baseimage` and from `spec.translator.repository`; identity tokens and credential-helper-only entries are unsupported, and the implementation must not fall back to unauthenticated access even if either registry is public. This rule does not apply to unrelated Operator, Translator, Builder, PostgreSQL, EDS, or post-processing image registries, which use the cluster's ordinary image-pull configuration. Translator and BuildKit use the mounted file for authenticated base-image pulls and generated-image pushes; SM adds the same LocalObjectReference to the runner Job so the kubelet can pull the generated image.
   - `translator.image`, `baseimage`, `builderImage`, and a ready-message runner image must be OCI digest references in the exact form `name@sha256:<64 lowercase hexadecimal characters>`. Tags alone are invalid.
   - `translator.repository` is the user-provided OCI repository where generated runner images are pushed. It is a repository name without a tag or digest. This feature and its tests must not hard-code a production registry. Registry access uses verified TLS. Insecure registries and TLS-verification bypasses are prohibited.
   - Persist each project by the statically defined `project_namespace` and `project_name`, where `project_name` is exactly `SimulationExperiment.metadata.name`; the pair is unique. Apart from the technical primary key used by `scenario_status.project_id`, the project table has no mutable status, component-count, or experiment-UID columns. Existing Core DB tables are validation-only and must not use automatic `ALTER TABLE` repair. This alpha API defines no migration procedure: an incompatible installation fails startup and must independently provide a fresh compatible database or recreate the tables.
   - Do not add namespace, project-name, or experiment-UID columns to `scenario_status`; its existing `project_id` foreign key remains the only project identity stored on a scenario row. Add the non-identity operational column `runner_reconciliation_failures INTEGER NOT NULL DEFAULT 0` so bounded Job reconciliation survives SM restarts. The live Kubernetes object, its UID, owner references, and reserved workload labels provide incarnation identity for Kubernetes operations; the Core DB project identity is only namespace/name.
   - Namespace and project name are the routing identity for EDS and Translator communication. Alpha4 experiment names must be lowercase DNS labels of 1 to 63 characters matching `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`; dots are rejected even though Kubernetes otherwise permits them in names. Namespace and project are inserted into NATS subjects without lossy normalization.

2. **Namespace-aware EDS and Translator communication.**
   - Change the alpha4 subjects to carry namespace and project as separate tokens:
     - EDS availability: `cbse.<namespace>.<project>.eds.scenarios.available`
     - EDS scenario batch: `cbse.<namespace>.<project>.eds.scenarios`
     - Translator request: `cbse.<namespace>.<project>.trans.request`
     - Translator ready: `cbse.<namespace>.<project>.trans.<scenario-id>.ready`
   - Preserve the existing EDS availability, scenario-batch, Translator request, and Translator ready JSON payloads. Do not add namespace or UID fields to those payloads. Preserve publish confirmation, ACK/NAK behavior, guarded `Created -> Scheduled`, accepted-ready handling, and exact-attempt recovery.
   - SM parses namespace and project from every EDS and Translator subject and resolves the exact `(project_namespace, project_name)` database row. A payload project field, where the existing payload has one, must exactly equal the project subject token. A subject/payload or subject/database identity mismatch is a permanent poison message and must not mutate scenario state.
   - Before accepting any EDS batch or Translator ready message, SM gets the matching alpha4 experiment and applies the lifecycle gate defined below. Only a live, non-deleting experiment in `InProgress` may consume scenario work. For an admitted non-empty Translator ready image, SM validates the image as a digest reference, normalizes its repository and `spec.translator.repository` with the same OCI reference parser, and requires an exact match. A digest from another repository is a permanent ready-message rejection: SM ACKs it as poison, does not persist the image, and does not create a runner Job.
   - SM is cluster-wide for alpha4 communication. Its experiment informer and NATS subscriptions cover every namespace: `cbse.*.*.eds.scenarios.available`, `cbse.*.*.eds.scenarios`, and `cbse.*.*.trans.*.ready`. Components remain namespace-local Kubernetes workloads, but one SM deployment can communicate with EDS and Translator components belonging to experiments in different namespaces. Alpha4 does not use `SCENARIO_MANAGER_WATCH_NAMESPACE` to narrow subjects or Kubernetes discovery.
   - `InProgress` is the only experiment phase in which SM publishes Translator requests or consumes EDS batches and Translator ready messages. In `Error` or `Failed`, and from the moment `deletionTimestamp` is present, SM performs no domain processing for the experiment. No NATS or JetStream request is expected after the experiment reaches `Completed`; a late or in-flight delivery is nevertheless rejected by the same terminal lifecycle gate. Because the two SM JetStream consumers are shared wildcard consumers, the broker may still deliver a project-scoped message after the gate closes. SM ACKs and discards such a terminal delivery without mutating Core DB state, consuming a translation attempt, or creating a Job; this transport-level disposal is not scenario-work consumption. An inactive EDS availability request never receives `status=ready` or a batch subject.
   - Every Operator-managed Pod template carries reserved labels `experiment.cbse.terministic.de/project=<experiment-name>` and `experiment.cbse.terministic.de/experiment-uid=<full-experiment-UID>`. The Operator injects `SIMULATIONPROJECTNAMESPACE`, `SIMULATIONPROJECTNAME`, and `SIMULATIONEXPERIMENTUID` into the per-experiment EDS and Translator through downward-API field references to `metadata.namespace`, `metadata.labels['experiment.cbse.terministic.de/project']`, and `metadata.labels['experiment.cbse.terministic.de/experiment-uid']` respectively. `metadata.name` and `metadata.uid` would identify the Pod rather than the owning experiment and must not be used for these two values. Each component publishes or subscribes only to subjects for that exact namespace/name pair.
   - SM owns the finalizer `scenario-manager.cbse.terministic.de/cleanup`. It adds the finalizer before registering a non-deleting experiment in Core DB. On deletion, the still-present CR supplies the exact namespace, name, and UID while SM removes the experiment's messaging artifacts and project row; only successful cleanup permits SM to remove its finalizer. Kubernetes therefore cannot admit a replacement CR with the same namespace/name until the previous incarnation's durable state is gone. Terminal-but-not-deleted experiments receive messaging cleanup but retain their project and scenario rows. Cleanup never deletes a shared stream or an SM consumer.

3. **Reference Translator template and on-demand image creation.**
   - Add a Go reference implementation at `component-templates/translator/`. It is the supported integration template for user-defined Translators and replaces `test/mocks/translator` in the full smoke path.
   - Separate the implementation into three explicit layers: the CBSE-maintained reference framework, a replaceable model-generator module, and the generated scenario-specific runner image. Production-quality guarantees apply to the framework and its integration contracts, not to the example model's semantics.
   - The Operator configures Translator through the same environment-based process used by the existing mock: `NATS_URL`, Translator stream, exact request subject, ready-subject template, and UID-specific durable-consumer name. It also injects `SIMULATIONPROJECTNAMESPACE`, `SIMULATIONPROJECTNAME`, `SIMULATIONEXPERIMENTUID`, `REPOSITORY`, and `BASEIMAGE`. The template validates all values before connecting to NATS.
   - `BASEIMAGE` is sourced only from `spec.translator.baseimage`. EDS payloads, Scenario Status, and existing Translator request and ready payloads do not carry or persist base-image information.
   - The Operator mounts the existing `<experiment-name>-resultdb-sct` Secret read-only at `/resultdb-connection` for Translator. It contains `host`, `port`, `dbname`, `user`, and `password`.
   - SM is the only supported request publisher and marshals requests from the typed four-field request struct after validating positive scenario ID and translation attempt. The template performs the lightweight decoding defined below and handles one request at a time. Its workspace is `/workspace/scenario-<scenario-id>/attempt-<attempt>`. It checks for a retained outcome before removing or recreating build input; only an attempt with no retained outcome and no recoverable registry tag has its build directory recreated.
   - The template uses the official BuildKit Go client over `unix:///run/buildkit/buildkitd.sock`. It submits the generated attempt directory as both the Dockerfile and build context, supplies registry credentials from `/registry-auth/config.json` through the BuildKit session, and requests a registry push to the deterministic tag.
   - The pushed tag is `<repository>:runner-<12-char-UID-prefix>-s<scenario-id>-a<attempt>`. The UID prefix is the first 12 lowercase hexadecimal characters of the UID after removing hyphens. The framework adds OCI manifest annotations for the full experiment UID, scenario ID, and translation attempt, verifies them after the push, resolves the tag, and publishes only the digest reference.
   - Translator publishes the ready message and waits for publish confirmation before acknowledging the request. A generator, BuildKit, push, or digest-resolution failure persists and publishes the existing ready message with an empty image and is acknowledged only after that publish succeeds. NATS transport or ready-publication failures are retryable and must not manufacture an empty result.
   - A successful push is a durable external effect. If ready publication then fails, Translator retains the resolved digest and retries publication of the same ready message. It must not regenerate, rebuild, or push another image for that scenario and attempt.
   - After a terminal acknowledged outcome, the template removes the attempt workspace. Before generation on redelivery, it validates any retained success or empty-failure outcome for that scenario and attempt and republishes that exact ready message without repeating the failed operation. A retained success reuses its digest without another registry lookup, generator call, build, or push. If a success marker was lost, Translator resolves the deterministic registry tag and reuses it only when its repository and framework-owned identity annotations exactly match the current experiment UID, scenario ID, and attempt. A missing or mismatched annotation is a permanent tag collision: Translator records and publishes an empty-image outcome, does not adopt or overwrite the tag, and does not invoke the generator or BuildKit. It recreates build input only when no marker or registry tag exists.

4. **Mandatory rootless BuildKit sidecar.**
   - Each Translator Pod has exactly two containers: `translator` and rootless `buildkit`.
   - Both containers run as UID and GID `1000`. The Pod sets `fsGroup: 1000`. They share `emptyDir` volumes mounted at `/workspace` and `/run/buildkit`, so generated build input and the BuildKit socket are writable by both containers. BuildKit listens only on `/run/buildkit/buildkitd.sock`; no TCP endpoint is exposed.
   - BuildKit receives the effective `spec.translator.builderResources`. CPU and memory limits default independently to `1` CPU and `2Gi`; user-supplied values replace those defaults. CPU and memory requests are copied only when supplied and otherwise remain absent.
   - Both containers receive the referenced registry Secret read-only at `/registry-auth/config.json`. The Translator also receives the result-database Secret read-only.
   - BuildKit runs rootless and non-privileged with the required compatibility exception: `Unconfined` seccomp and AppArmor plus `--oci-worker-no-process-sandbox`. It must not use privilege escalation, privileged mode, host networking, host paths, or host container-runtime sockets. Translator keeps the normal restricted security profile.
   - A namespace that enforces the Kubernetes Baseline or Restricted Pod Security Standard rejects this required BuildKit exception. The smoke harness therefore labels its isolated `cbse-e2e-<run-id>` namespace with `pod-security.kubernetes.io/enforce=privileged`. This admission label does not permit the implementation to set `privileged: true` or weaken any other container restriction. The harness keeps `audit` and `warn` at `restricted` so the exception remains visible.
   - Kubernetes 1.30 or newer is required so the BuildKit container can set `securityContext.appArmorProfile.type: Unconfined`. Cluster installation documentation must call out the namespace admission requirement and the AppArmor prerequisite.
   - Generated source, Dockerfile, and build commands are trusted prototype input. Egress isolation and an untrusted-build sandbox are deferred.

5. **Simulation Runner startup and terminal observation.**
   - For one accepted Translator image, SM creates or confirms one `batch/v1` Job for the scenario and translation attempt. The Job name is `simrun-<12-char-UID-prefix>-s<scenario-id>-a<attempt>`, using the UID-prefix rule above.
   - The default Job has one container named `runner`. A custom template must contain exactly one `runner` container and may use only the explicit public allow-list below for sidecars, init containers, volumes, mounted configuration, resources, metadata, deadlines, and scheduling constraints. Every user-supplied field outside that allow-list is rejected. SM replaces the `runner` image with the accepted Translator image.
   - The Job is indexed. `spec.completionMode` is `Indexed`, and `spec.completions` and `spec.parallelism` both equal `scenario_status.number_of_reps`. Each completion index represents one homogeneous repetition for Kubernetes retry accounting. The runner does not consume the index, and Core DB and Result DB do not persist it as a repetition identity. All repetitions may run concurrently; a user-defined model and durable result sink must support that concurrency.
   - `number_of_reps` is limited to `1..100000`, the Kubernetes Indexed Job maximum when `parallelism` equals `completions`. This branch adds no lower operational cap, separate maximum parallelism, batching, or throttling. The trusted-input prototype accepts Jobs up to that Kubernetes limit. A future EDS template may impose a smaller policy limit.
   - Capacity and fairness follow ordinary Kubernetes Job and scheduler behavior. SM submits the Job without calculating cluster capacity or waiting for free resources. The Job may have at most `number_of_reps` Pods active because `parallelism` equals that value; the configured Kubernetes scheduler creates or binds Pods only as resources and scheduling constraints permit. Pending or unschedulable Pods leave the scenario `InProcessing` and are not Job-reconciliation failures. CBSE adds no custom capacity queue, admission calculation, or cross-Job scheduling policy.
   - Set `restartPolicy: Never`, `backoffLimitPerIndex: 4`, global `backoffLimit: math.MaxInt32`, no `maxFailedIndexes`, and no TTL-after-finished field. A failed Pod is replaced for the same completion index, giving each repetition five total attempts: the initial Pod plus four retries. Leaving `maxFailedIndexes` unset lets all indexes run to resolution after per-index failures. With no user-supplied `activeDeadlineSeconds`, the Job succeeds only when every index succeeds and fails after all indexes resolve when any index exhausts its retry budget. An allowed active deadline may instead terminate the Job earlier and preserve only the indexes completed by that time. Completed and failed Jobs remain visible. Kubernetes 1.30 or newer with the default-enabled `JobBackoffLimitPerIndex` feature is required.
   - The Job has the exact alpha4 experiment owner reference, with `controller: true` and `blockOwnerDeletion: false`, runs in the experiment namespace, and uses the deterministic ServiceAccount `simrunner-<12-char-UID-prefix>`. The false block-owner-deletion value avoids requiring SM to have delete permission on experiments while preserving normal garbage collection. The Operator creates this ServiceAccount, gives it no RoleBinding, and SM sets `automountServiceAccountToken: false` on the Job Pod. Every Pod template created for an experiment by the Operator or SM carries the reserved project and full experiment-UID labels defined above; this includes internal database, EDS, Translator, post-processing, and runner Pods. The Operator and SM copy both label values from the live `SimulationExperiment`; containers that require the UID read the reserved label through the downward API and need no Pod-read permission.
   - Runner, sidecar, and init-container images must support non-root execution. The effective Pod template uses `RuntimeDefault` seccomp, `runAsNonRoot: true`, disabled privilege escalation, and dropped capabilities. The Operator validates the template before moving the experiment to `InProgress`; SM validates it again before creating a Job.
   - SM observes Jobs for scenarios in `InProcessing` and monotonically records successful completion indexes in `scenario_status.number_of_computed_reps`. A successful Job records all requested repetitions before the guarded `InProcessing -> PostProcessing` transition. A failed Job preserves any partial successful count before the guarded `InProcessing -> Failed` transition. This branch does not execute post-processing or move a scenario out of `PostProcessing`.

### Workflow Decisions

| Concern | Decision for this branch |
| --- | --- |
| Active API | Alpha4 only; alpha2 and alpha3 are retired through a manual breaking upgrade. |
| Messaging identity | Namespace and project are separate NATS subject tokens and resolve one exact project row. |
| Messaging payloads | Existing EDS and Translator JSON payloads remain unchanged. |
| Project incarnation | Namespace/name in Core DB; SM cleanup finalizer prevents same-name recreation until old durable state is deleted. |
| Translator lifetime | Existing always-on Deployment and Service per experiment. |
| Translator implementation | Go reference framework in `component-templates/translator/`; user-defined model generation is plugged into it. |
| Example model | Scenario-specific SimPy runner generated from validated `recipe_info`; illustrative rather than production simulation logic. |
| Build engine | One serial, rootless BuildKit sidecar per Translator Pod. |
| Build handoff | Shared `/workspace` and `/run/buildkit` `emptyDir` volumes, UID/GID `1000`, `fsGroup: 1000`, and a Unix socket. |
| BuildKit resources | Optional `corev1.ResourceRequirements`; CPU and memory limits default independently to `1` CPU and `2Gi`, while requests are user-configurable and have no defaults. |
| Build result | Deterministic attempt tag, then immutable digest in the existing ready message. |
| Ready publish retry | Reuse the successful pushed digest; never regenerate, rebuild, or repush that scenario attempt. |
| Empty translation outcome | Persist and publish an empty ready; retry from `Created` until `SCENARIO_MANAGER_TRANS_MAX_ATTEMPTS` (default `3`), then fail the scenario. |
| Credential lifetime | Registry and Result DB credentials are loaded at Translator startup; live rotation and reload are out of scope. |
| Runner unit | One customizable, indexed Job per scenario and translation attempt; one completion index per required repetition. |
| Runner concurrency | `parallelism = completions = number_of_reps`. |
| Runner concurrency limit | `number_of_reps <= 100000`, the Kubernetes Indexed Job limit; no smaller feature-specific cap. |
| Runner retry | Each completion index receives an initial Pod plus four retries through `backoffLimitPerIndex: 4`; all indexes run to resolution. |
| Job API retry | Persisted consecutive-failure count; initial attempt plus five retries at `1s`, `2s`, `4s`, `8s`, and `16s`. |
| Runner completion | Job success moves the scenario to `PostProcessing`; Job failure moves it to `Failed`. |
| Post-processing boundary | `PostProcessing` is reached but not processed in this branch. |
| Experiment terminal phases | Only `InProgress` admits messaging work. SM publishes or consumes no scenario work in `Error`, `Failed`, or while deleting; no requests are expected in `Completed`. SM observes all three terminal phases for cleanup but does not produce them in this branch. |
| Example result sink | Each successful generated runner appends one JSONB result to a PostgreSQL table dedicated to its scenario. Writes are at-least-once; completion indexes are not persisted as result identities. |
| Scenario logging | Log scenario-level creation and terminal outcome plus one runner-controlled failure record per failed Pod attempt; do not log each successful repetition. |
| Durable authority | PostgreSQL guarded transitions; Jobs are idempotent external effects. |

### Out of Scope

This branch must not add:

- alpha2 or alpha3 serving, reconciliation, conversion, or migration automation;
- a per-scenario Translator Job or a change to Translator lifetime;
- new EDS or Translator JSON payload fields, or a new JetStream acknowledgement model beyond the namespace-aware subject change defined here;
- a universal production model generator or production simulation semantics;
- runner result ingestion, confidence calculation, PostProcessingService invocation, or any scenario transition out of `PostProcessing`;
- aggregation of scenario states into `SimulationExperiment.status.phase`, including SM-owned transitions to experiment phase `Failed` or `Completed`;
- a later execution/run identity for a repeated scenario after post-processing;
- PostProcessingService-driven `n+m` repetitions or any increase of `number_of_reps` after the original EDS batch;
- workload replacement, cancellation recovery, or self-healing beyond the fixed per-index Pod retry budget and the bounded Job-API reconciliation budget defined here;
- a second scheduler implementation or alpha4 scheduler-provider selection field;
- concurrent Translator builds, object-storage/PVC build handoff, or remote BuildKit TCP access;
- automatic registry or Result DB credential rotation, file watching, or live credential reload;
- production lifecycle deletion or garbage collection of generated runner images;
- centralized scenario-log storage, retention limits, or automatic deletion of past logs;
- privileged containers, host networking, host paths, container-runtime socket mounts, or insecure registry/TLS settings;
- untrusted Dockerfile isolation or build egress controls;
- an EDS template, EDS-side repetition policy, runner parallelism cap below Kubernetes' Indexed Job limit, or SM-side runner throttling; or
- deployment of test workloads in `default` or `kube-system`.

## Logic Description

### Namespace-aware messaging contract

Alpha4 replaces project-only routing with a single canonical subject grammar. Namespace and project occupy separate subject segments and are copied directly from `SimulationExperiment.metadata.namespace` and `.metadata.name`. Code must validate both tokens before constructing or accepting a subject. It must not pass identity through `subject.NormalizeToken` or any other lossy conversion. Invalid identity is a permanent configuration or message error.

| Flow | Concrete subject | SM subscription or stream subject |
| --- | --- | --- |
| EDS availability request/reply | `cbse.<namespace>.<project>.eds.scenarios.available` | `cbse.*.*.eds.scenarios.available` |
| EDS scenario batch | `cbse.<namespace>.<project>.eds.scenarios` | `cbse.*.*.eds.scenarios` |
| Translator request | `cbse.<namespace>.<project>.trans.request` | JetStream stream subject `cbse.*.*.trans.request`; each Translator consumes its exact subject |
| Translator ready | `cbse.<namespace>.<project>.trans.<scenario-id>.ready` | `cbse.*.*.trans.*.ready` |

SM applies one canonical lifecycle gate before publishing a Translator request or performing domain processing for an EDS availability request, EDS batch, or Translator ready message. It gets the exact alpha4 `SimulationExperiment` identified by the subject and admits work only while the object exists, has no `deletionTimestamp`, and has phase `InProgress`. `Pending`, `Provisioning`, and an empty phase are not yet active: availability returns `status=error` without `batch_subject`, and a JetStream delivery is NAKed for later redelivery. `Error`, `Failed`, `Completed`, and deletion are permanently inactive for messaging: availability returns `status=error` without `batch_subject`, while an unavoidable JetStream delivery through the shared wildcard consumer is ACKed and discarded without database mutation, attempt consumption, or Job creation. By contract, publishers send no NATS or JetStream requests after `Completed`; the defensive terminal rule covers only a late, duplicate, or already-in-flight delivery. In this specification, “SM does not consume messages” for an inactive experiment means that no scenario-work handler runs; the terminal ACK is transport cleanup that prevents an unprocessable delivery from redelivering forever.

EDS continues its request/reply handshake, but publishes availability to its exact namespace/project subject. SM parses the subject, validates the existing availability payload's `project` against it, resolves the exact project row, and applies the lifecycle gate before replying. A successful reply for an active experiment returns the exact namespace-aware batch subject. When the subsequent JetStream batch arrives, SM parses and validates its subject again, applies the lifecycle gate, requires `ScenarioBatch.project` to match, and requires every scenario's `number_of_reps` to be in `1..100000` before beginning the existing all-or-nothing batch insert. A batch containing an invalid repetition count is permanent poison: SM returns an error acknowledgement, ACKs the JetStream delivery, and inserts no rows. A valid batch associates all inserted scenarios with `ProjectIDByNamespaceAndName(namespace, project)`.

SM's translation claim projection carries raw project namespace and name. Before claiming `Created -> Scheduled` and again immediately before publication, the Translator request publisher applies the lifecycle gate and publishes only for a live `InProgress` experiment. It uses namespace and project to construct the exact request subject. The per-experiment Translator template validates its injected namespace and project at startup, subscribes only to that subject, and publishes ready messages only on the corresponding namespace/project ready subject. SM parses both tokens from a ready subject, applies the lifecycle gate, and requires them to match the scenario's persisted project row before applying empty-image recovery or a non-empty ready result. For a non-empty image, SM validates the digest and requires its normalized repository to equal `spec.translator.repository`. A wrong namespace, project, digest, repository, or stale translation attempt is ACKed as poison and cannot consume an attempt or alter the row.

Transport-neutral and persistence projections carry the validated raw identity explicitly. Extend `ScenarioForTranslation` and `TranslatorReadyMessage` with `ProjectNamespace` and `ProjectName`; do not retain a single ambiguous `Project` field in new alpha4 code. EDS may keep the wire field `project`, but after subject parsing its internal `ScenarioBatch` also carries `ProjectNamespace` and `ProjectName` fields excluded from JSON. Core orchestration and database functions receive this explicit identity and never reconstruct a namespace from process configuration or a normalized subject token.

Malformed subject shape, invalid tokens, subject/payload disagreement, and a batch or ready message that identifies no matching project are permanent poison deliveries: respond with an error where request/reply permits it, ACK JetStream messages, and perform no database mutation. A temporary database, Kubernetes lookup, or NATS failure is retryable: return an error for availability so EDS retries its request, or NAK a JetStream delivery. Availability for a valid identity that has not yet been registered or is not yet `InProgress` returns `status=error` with no `batch_subject`; it does not create a project row. The EDS retries availability and publishes no batch until it receives `status=ready`. Terminal and deleting experiments use the permanent lifecycle rejection above rather than this transient path.

The canonical alpha4 subject templates are:

- `SCENARIO_MANAGER_EDS_AVAILABLE_SUBJECT_TEMPLATE=cbse.{namespace}.{project}.eds.scenarios.available`
- `SCENARIO_MANAGER_EDS_BATCH_SUBJECT_TEMPLATE=cbse.{namespace}.{project}.eds.scenarios`
- `SCENARIO_MANAGER_TRANS_REQUEST_SUBJECT_TEMPLATE=cbse.{namespace}.{project}.trans.request`
- `SCENARIO_MANAGER_TRANS_READY_SUBJECT_TEMPLATE=cbse.{namespace}.{project}.trans.{scenario_id}.ready`

These values are fixed for alpha4. If the existing environment variables are retained for deployment compatibility, an explicitly configured value must equal the corresponding canonical value above or startup fails. Alpha4 removes support for `%s`, fixed project-independent subjects, alternate prefixes, and templates missing `{namespace}` or `{project}`. SM derives its cluster-wide stream and subscription wildcards only by replacing the namespace, project, and scenario placeholders with `*`; callers do not configure a narrower namespace wildcard.

In this document, a JetStream stream is a broker-side named store for messages published on configured NATS subjects; it is not a payload and is not created per Kubernetes namespace. SM owns creation and reconciliation of the two shared streams. `cbse_eds_scenarios` uses `WorkQueuePolicy`, `FileStorage`, `DiscardOld`, and subject `cbse.*.*.eds.scenarios`. `cbse_translator` uses the same retention, storage, and discard policies and subjects `cbse.*.*.trans.request` and `cbse.*.*.trans.*.ready`. Namespace and project remain subject tokens inside those shared streams, so one stream of each kind covers all experiments without mixing their identities. Stream fields not listed here retain an existing stream's value; on creation they use the NATS server or client-library zero-value defaults. Stream reconciliation may append these required alpha4 subjects but must not remove unrelated existing subjects. If the legacy stream-name environment variables remain, they must be absent or equal these canonical names.

All SM replicas attach to the same two SM-owned consumers. The EDS batch consumer is durable `scenario-manager-eds-consumer`, queue group `scenario-manager-eds`, exact filter `cbse.*.*.eds.scenarios`, explicit ACK, `DeliverAll`, `AckWait: 2m`, `MaxAckPending: 1024`, and `MaxDeliver: -1`. The Translator-ready consumer uses durable and queue group `scenario-manager-translator-ready`, exact filter `cbse.*.*.trans.*.ready`, and the same ACK, delivery, timing, pending, and redelivery settings. Queue groups distribute a given message among SM replicas; they do not partition by namespace. Per-experiment Translators still use their exact namespace/project request filter and UID-specific durable consumer, so only the owning Translator processes a request.

Because alpha4 is a coordinated breaking upgrade, SM reconciles an existing SM-owned durable to this exact configuration before starting business processing. If the server cannot update an incompatible filter or immutable setting in place, SM deletes and recreates only that named SM-owned durable, then attaches all replicas to the resulting consumer. It never rewrites or deletes a per-experiment Translator consumer. Concurrent SM startups treat an already-created matching stream or consumer as success; a remaining mismatch fails startup with the exact stream or consumer name and setting.

Each Translator uses a durable consumer named `translator-<12-char-UID-prefix>` with its exact request subject as the filter. The UID prefix follows the existing lowercase, hyphen-stripped rule. This keeps consumers distinct across namespaces and across deletion/recreation of an experiment. The consumer uses explicit acknowledgement, `DeliverAll`, `AckWait: 2m`, `MaxAckPending: 1`, and `MaxDeliver: -1` for unlimited redelivery. Translator sends `InProgress` every 30 seconds from request acceptance through generation, build, push, digest resolution, and any ready-publication retry. It publishes the ready message with confirmation and then uses a server-confirmed final acknowledgement for the request. If an in-progress acknowledgement cannot be sent, Translator cancels the active processing context and leaves the request unacknowledged for redelivery.

Translator creates its UID-specific consumer when it is absent. When it already exists, Translator attaches only if its stream, exact filter subject, acknowledgement policy, delivery policy, `AckWait`, `MaxAckPending`, and `MaxDeliver` match this contract. An incompatible durable consumer is an identity collision and makes Translator startup fail without updating, deleting, or silently adopting that consumer. The Translator creates neither the shared stream nor an SM consumer.

The existing NATS connection configuration remains the credential source; alpha4 adds no credential field. The SM identity must be authorized to create and inspect the two streams, create, inspect, update, and delete its two consumers, delete per-experiment Translator consumers during cleanup, purge only the exact subjects defined above, publish Translator requests, and consume and acknowledge EDS batches and Translator-ready messages. The per-experiment Translator identity must be authorized to inspect `cbse_translator`, create and inspect only its named consumer, consume and acknowledge its exact request subject, and publish its project-scoped ready subjects. Missing required NATS authorization is a startup or cleanup error according to the owning workflow; implementations must not silently broaden subjects to work around it.

### Namespace/name project persistence

The alpha4 project table has this logical schema:

```text
id                    SERIAL PRIMARY KEY
project_namespace     TEXT NOT NULL
project_name          TEXT NOT NULL
UNIQUE (project_namespace, project_name)
```

`scenario_status.project_id` remains a foreign key to `project.id` with `ON DELETE CASCADE`. The schema is a static developer-owned contract, not a user-configurable table shape. No experiment UID or mutable project state is duplicated in either table. Queries obtain namespace and name by joining the project table and obtain the current experiment UID from the live Kubernetes object when a Kubernetes operation needs incarnation identity. The SM cleanup finalizer prevents a replacement object with the same namespace/name from being created before the previous incarnation's project row and scenarios are deleted, so restart-safe incarnation separation does not require a UID column.

Project registration is idempotent for the exact namespace/name pair. `project_name` is copied without normalization from `SimulationExperiment.metadata.name`, and `project_namespace` is copied from `metadata.namespace`. Subject normalization never changes either stored value.

SM adds its cleanup finalizer before inserting or reusing the namespace/name project row, then re-gets the object. If deletion began before that re-get, SM enters deletion cleanup and does not register or reuse a row. When `deletionTimestamp` is set, SM stops accepting new EDS or Translator work for that project, performs deletion cleanup using the still-readable object's namespace, name, and UID, deletes the project row in one transaction, and lets `ON DELETE CASCADE` remove all scenarios. Only then does it remove its finalizer. A subsequently recreated experiment with the same namespace/name therefore registers a fresh row after the old row is gone.

When the project table does not exist, SM creates it with the alpha4 schema. When it already exists, SM validates it without issuing `ALTER TABLE`. Compatibility requires exactly the three columns above with the stated types and nullability, the generated `id` primary key, and the namespace/name uniqueness constraint; legacy `experiment_uid`, `number_of_components`, `status`, or any other extra project column is incompatible. The scenario table additionally requires `runner_reconciliation_failures INTEGER NOT NULL DEFAULT 0`; it is an operational retry counter, not identity. A legacy or incompatible table makes startup fail before the informer, NATS consumers, or selector starts. Alpha4 is an unused breaking alpha API and defines no database migration procedure; an affected operator must independently provide a fresh compatible database or recreate the tables.

### Terminal and deleted experiment cleanup

The Experiment Operator owns Kubernetes deletion reconciliation. Its existing finalizer and owner references remove only the experiment's Operator-created Deployments, Services, Secrets, ServiceAccount, and other owned components when a `SimulationExperiment` is deleted, including deletion during scenario execution. The pre-existing user-supplied registry Secret referenced by `registryAuthSecretRef` is not owned or deleted by the Operator. Runner Jobs carry the experiment owner reference and are removed by Kubernetes garbage collection. Component deletion is idempotent and does not depend on SM deleting Kubernetes resources.

SM requests messaging cleanup when the experiment informer adds an object already in `Error`, `Failed`, or `Completed`, or observes a transition into one of those phases. It requests deletion cleanup when it observes an object with `deletionTimestamp`; normal deletion is completed before the informer can emit the final delete event because the SM finalizer remains present. `Error` is included even though an experiment that fails during provisioning will normally have no per-experiment messaging artifacts. Before closing the lifecycle gate, terminal handling re-gets the current object and requires its UID and terminal phase to match the event; a stale event for an old UID cannot close the gate for a replacement. A confirmed phase or deletion observation closes the current incarnation's gate before cleanup is queued, so SM immediately stops publishing Translator requests and performing EDS or Translator-ready domain handling while cleanup retries independently.

Terminal cleanup uses the event namespace, name, and UID and re-gets the current object before purging namespace/name subjects. A different live UID makes an old terminal event stale. Deletion cleanup uses the deleting object protected by the SM finalizer; a replacement with the same name cannot yet exist.

For an accepted terminal, deletion, or orphan-cleanup event, SM performs these idempotent messaging operations:

1. Delete durable consumer `translator-<12-char-UID-prefix>` from stream `cbse_translator` when the event UID is available. For an orphan sweep without a UID, enumerate only Translator consumers whose exact filter is `cbse.<namespace>.<project>.trans.request` and delete those matching consumers.
2. Purge messages matching `cbse.<namespace>.<project>.eds.scenarios` from stream `cbse_eds_scenarios`.
3. Purge messages matching `cbse.<namespace>.<project>.trans.request` from stream `cbse_translator`.
4. Purge messages matching `cbse.<namespace>.<project>.trans.*.ready` from stream `cbse_translator`.

For deletion cleanup only, SM then deletes the exact `(project_namespace, project_name)` row in Core DB; its foreign key removes every scenario belonging to the deleted project. After all messaging and database operations succeed, SM removes `scenario-manager.cbse.terministic.de/cleanup`. A terminal phase without CR deletion retains the finalizer, project, and scenario rows.

The availability subject uses Core NATS request/reply and has no durable server artifact to remove. Once the lifecycle gate is closed it cannot return `status=ready`; there is therefore no availability artifact to purge. Cleanup never deletes or recreates the shared EDS or Translator streams. It never deletes SM durable consumers or queue groups. A missing stream, consumer, or matching message is successful cleanup. A message already delivered to a shared SM consumer is still subject to the terminal ACK-and-discard rule even if the stream purge races with that delivery.

SM replicas may request the same cleanup. Each namespace/name/UID is an independent idempotent queue key, so duplicate work is safe and one delayed cleanup cannot block another experiment. Failures retry after `1s`, `2s`, `4s`, `8s`, `16s`, `32s`, and then `60s` until success or shutdown; removing an already-absent finalizer or messaging artifact is success.

As a defensive path for rows or Translator consumers created before SM could add its finalizer, every SM replica performs an orphan sweep at startup and every five minutes. A sweep may classify or delete orphans only after one complete, successful cluster-wide experiment list; an authorization, timeout, pagination, or transport failure aborts that sweep without cleanup. It compares Core DB project rows and per-experiment Translator consumers with that authoritative list. A missing CR enqueues the parsed namespace/project key; that key deletes consumers whose exact filter equals the project's request subject, purges the exact project subjects, and deletes any project row. For a live namespace/project, the sweep computes the current `translator-<UID-prefix>` durable name and deletes only consumers on that exact request filter whose durable name differs; this removes an early-deletion consumer that would otherwise overlap and block the replacement Translator, without purging the live project's subjects or database row. The operations and guarded row deletion remain idempotent across replicas. Administrative removal of the SM finalizer after project registration violates the supported lifecycle and is not made recoverable without an experiment-UID database column.

This branch reacts to terminal experiment phases but does not decide them. A future SM lifecycle feature will own scenario aggregation and the experiment transitions from `InProgress` to `Failed` or `Completed`. The Operator continues to own `Pending -> Provisioning -> InProgress` and provisioning failure to `Error`. The lifecycle gate is independent of transition ownership: regardless of which component set the phase or deletion timestamp, SM admits messaging work only while the current object is live and `InProgress`.

### Translator template boundary

The reference Translator is production-quality integration code, but it is not a universal production Translator. The stable framework owns request consumption and validation, serial delivery, workspace lifecycle, BuildKit sessions, registry authentication, push and digest verification, ready publication, and request acknowledgement. It must not contain model-specific decisions outside the example generator.

The Operator provides the framework configuration as environment variables, following the existing mock Translator process. `NATS_URL` identifies the NATS server. `TRANSLATOR_STREAM`, `TRANSLATOR_REQUEST_SUBJECT`, `TRANSLATOR_READY_SUBJECT_TEMPLATE`, and `TRANSLATOR_CONSUMER` identify the exact alpha4 JetStream stream, request filter, ready-subject template, and UID-specific durable consumer. `SIMULATIONPROJECTNAMESPACE`, `SIMULATIONPROJECTNAME`, and `SIMULATIONEXPERIMENTUID` identify the owning experiment. `REPOSITORY` is the configured target repository and `BASEIMAGE` is the digest-pinned `spec.translator.baseimage` value. The template fails startup with a descriptive configuration error when any required value is missing, malformed, or inconsistent with the alpha4 subject grammar. It creates neither shared stream nor Scenario Manager consumer.

The framework derives the ready subject from the configured template and the validated request scenario ID. It must publish only within its injected namespace and project. The stream, request subject, ready-subject template, and consumer naming are configuration, not model-generator responsibilities.

Translator consumes the request schema already published by SM: integer `id`, integer `translation_attempt`, object-or-null `recipe_info`, and number-or-null `confidence_metric`. SM validates the two positive identity values before using `encoding/json` on that typed struct; no valid SM-published scenario request can therefore lack recoverable identity. Translator decodes one JSON object, requires positive `id` and `translation_attempt`, and checks the documented types for the two optional fields. Unknown fields are ignored and do not extend the supported contract. A delivery that cannot recover valid identity is external or corrupt poison rather than a request produced by the supported SM publisher: Translator emits one sanitized log and ACKs it without a ready message, and tests for this branch publish raw poison without creating a Core DB scenario. If identity is valid but `recipe_info` cannot be handled by the selected generator, that is a generator failure and follows the confirmed empty-image ready workflow for that scenario.

An empty-image outcome is terminal only after its ready publication is confirmed. Generator, BuildKit, registry push, and digest-resolution failures first atomically persist an empty-failure outcome marker, then retry publication of that same empty-image ready message until confirmation and finally server-ACK the request. If final request acknowledgement fails, redelivery reuses the marker and does not repeat generation, build, push, or resolution. NATS transport, progress-acknowledgement, or ready-publication failures leave the request unacknowledged for JetStream redelivery and never create a second failure classification. This is the same ACK/NAK boundary used by SM for ready messages: malformed or permanent poison is ACKed, while transient transport or persistence failure is retried.

For an active `InProgress` experiment admitted by the lifecycle gate, SM handles a confirmed empty-image ready message through the existing exact-attempt policy, now made canonical here. `SCENARIO_MANAGER_TRANS_MAX_ATTEMPTS` is a positive integer with default `3`. After validating project, scenario ID, state `Scheduled`, and matching `translation_attempt`, SM calls `MarkScenarioTranslationAttemptFailed`: attempts below the configured maximum transition that exact row back to `Created`, while an exhausted attempt transitions it to `Failed`. The recovery update does not increment `translation_attempts`; the next successful `Created -> Scheduled` claim increments it. SM ACKs the empty ready only after the guarded database update succeeds and NAKs transient database failures. For an inactive terminal or deleting experiment, SM instead applies the terminal ACK-and-discard rule and does not call this recovery update.

The replaceable Go generator boundary has this conceptual shape; the implementation may place these types in an internal package, but it must preserve this dependency direction:

```go
type Generator interface {
	Generate(context.Context, GenerationInput) error
}

type GenerationInput struct {
	ScenarioID         int
	TranslationAttempt int
	RecipeInfo         json.RawMessage
	ConfidenceMetric   *float64
	BaseImage           string
	Workspace           string
	ResultDatabase      ResultDatabaseConfig
}

type ResultDatabaseConfig struct {
	Host     string
	Port     int
	DBName   string
	User     string
	Password string
}
```

`Generate` writes a complete Docker build context into `Workspace`: generated model files, scenario configuration, dependencies, an entrypoint, and a Dockerfile. It does not consume NATS messages, call BuildKit, push images, publish ready messages, or acknowledge deliveries. Those remain framework responsibilities so a user can replace model generation without reimplementing the handoff protocol.

The included example generator uses the smoke EDS recipe shape already established in this repository. It requires `recipe_info` to be a JSON object with a non-empty string `scenario` and a non-negative integer `seed`; unknown fields are ignored so the example remains usable with richer user recipes. Missing fields, wrong types, an empty `scenario`, or a negative `seed` are generation failures and follow the empty-image ready workflow.

The example generator writes the validated values to `scenario.json` in the build context and packages a small, checked-in SimPy model from the template source. That model initializes its pseudo-random input from `seed`, executes five deterministic timeout events, and reports the scenario name, seed, event count, and final simulated time. The generated Dockerfile uses the required digest-pinned runner smoke base image, which already contains Python 3.14.6, SimPy 4.1.2, and Psycopg 3.3.4, copies only the generated runner files and connection configuration, sets a numeric non-root user, and defines the model launcher as its entrypoint. It does not reinstall unversioned dependencies. The generated image therefore starts the baked scenario without command, arguments, or environment variables from SM.

At startup, the template reads exactly `host`, `port`, `dbname`, `user`, and `password` from the files mounted at `/resultdb-connection` and reads the registry configuration mounted at `/registry-auth/config.json`. It rejects missing or malformed values before handling requests, requires basic credentials for the configured base-image and target-repository authorities through the same Docker resolver used by the Operator, and passes a validated `ResultDatabaseConfig` only to the generator. Translator does not open a Result DB connection at startup. After the Result DB Service or external endpoint and connection Secret exist, Operator provisioning attempts a connection with a 10-second timeout and `SELECT 1` with a 30-second statement timeout. Invalid connection fields are provisioning errors; a well-formed but refused, timed-out, unavailable, or authentication-failed connection leaves the experiment in `Provisioning` and requeues after five seconds without a fixed attempt limit. Only a successful check permits `InProgress`, and deletion preempts the check or wait. The template does not watch, reload, or rotate either credential set while running. Secret updates after startup have no defined effect until the Translator Pod restarts.

The example generator bakes the connection configuration and a replaceable result-sink interface into the runner image. This retains the trusted prototype assumption that the generated image contains credentials: neither the framework, generator, BuildKit progress handling, nor runner may print those values or expose them in image labels or annotations. Credentials must not be added to NATS messages, Scenario Status, image labels, or annotations.

The configured Result DB role must have `CONNECT` on the configured database, `USAGE` and `CREATE` on its default schema, and permission to create and write the tables it owns; no superuser privilege is required. The example runner uses a 10-second connection timeout and a 30-second statement timeout and performs no inner retry. It connects to PostgreSQL and, in a short transaction, obtains `pg_advisory_xact_lock(0, <scenario-id>)` before creating the scenario table with `IF NOT EXISTS`; the transaction commits immediately after the schema check. This serializes only concurrent first-use table creation by repetitions of the same scenario and prevents catalog races. The runner then performs its result insert in a separate transaction. A timeout or permission failure exits non-zero and consumes the current Kubernetes Pod attempt. The table name and advisory-lock key are derived only from the already validated positive integer scenario ID:

```sql
CREATE TABLE IF NOT EXISTS scenario_<scenario-id>_results (
    id BIGSERIAL PRIMARY KEY,
    result JSONB NOT NULL
);
```

After a successful simulation, each runner appends one JSONB `result` containing exactly `scenario`, `seed`, `events_processed`, and `simulated_time`. The sequence supplies unique row IDs but does not claim commit-order semantics. Completion indexes are not written to the Result DB, and results have no repetition identifier or uniqueness constraint. A simulation failure performs no result insert. A Result DB connection, advisory-lock, table-creation, or insert failure makes the runner exit unsuccessfully and consumes one Pod attempt for that completion index. Kubernetes may then create a replacement Pod for the same index until its four-retry budget is exhausted.

The result sink is intentionally at-least-once. If PostgreSQL commits an insert but the runner loses the response, the runner exits unsuccessfully and a replacement Pod may run the simulation and append another row. This trusted prototype accepts that an ambiguous commit can therefore produce more result rows than successful completion indexes. The normal no-failure smoke path still requires exactly `number_of_reps` rows. A user-defined generator may replace the per-scenario schema and sink independently, but it must preserve the generated image's ownership of runner startup and result handling.

The namespace-aware subjects above replace the project-only subject names; the existing request and ready JSON payloads remain unchanged. The template uses the exact JetStream consumer contract above and allows at most one active request and build. A successful digest ready message, or a confirmed empty-image failure ready message, is published with JetStream confirmation before the request receives its server-confirmed acknowledgement. NATS transport or publication failures leave the request unacknowledged and retryable; they do not produce an empty-image result.

The BuildKit image exporter adds these credential-free OCI manifest annotations:

- `experiment.cbse.terministic.de/experiment-uid=<full-UID>`
- `experiment.cbse.terministic.de/scenario-id=<decimal-scenario-id>`
- `experiment.cbse.terministic.de/translation-attempt=<decimal-attempt>`

`ready-outcome.json` is the single credential-free durable outcome format. It contains `outcome` (`success` or `empty_failure`), scenario ID, translation attempt, ready subject, and full experiment UID. A success additionally contains deterministic tag and digest; an empty failure contains an empty image and a short non-sensitive failure class. Translator writes the complete file to a temporary file in the same directory and renames it over the marker before publishing ready. It retains the workspace until ready publication and server-confirmed request acknowledgement both succeed.

After BuildKit confirms a successful push, Translator resolves the digest and verifies the repository and all three annotations, then atomically writes the success outcome. A generator, BuildKit, push, digest-resolution, or tag-collision failure atomically writes the empty-failure outcome before its first ready publication. A publish or final-ack retry validates and reuses the exact marker without another generator, build, push, or registry lookup.

On redelivery or process restart, Translator first validates the marker's outcome, experiment UID, scenario ID, attempt, ready subject, and outcome-specific fields. A valid marker is authoritative for that attempt. If the marker was lost because the Pod was replaced, Translator resolves the deterministic registry tag. It treats the tag as the successful build outcome only when the normalized repository and all three manifest annotations exactly match the current request. A missing or mismatched annotation is a permanent identity collision that creates the empty-failure marker; Translator never adopts or overwrites the tag. A registry not-found result permits generation and build; another resolution failure creates the empty-failure marker.

An empty-failure marker is durable across Translator process or container restart while the Pod-local `emptyDir` survives, but there is deliberately no external empty-failure artifact. If Pod replacement loses that marker, redelivery may repeat generation or another failing operation once; SM's exact-attempt handling makes any resulting ready message stale after the first empty outcome was applied. This bounded duplicate work is accepted and must not change a newer scenario attempt. Successful pushes continue to recover externally from their annotated registry tag.

### Runner Job customization contract

`spec.runner.jobTemplate` is optional. It is a typed `batch/v1.JobTemplateSpec`, not raw YAML and not a ConfigMap containing a Job. The built-in template is used when the field is absent. A supplied template must contain exactly one regular container named `runner`; other regular containers and init containers have unique names. The public template API is an allow-list against the repository's pinned `k8s.io/api` v0.33 Kubernetes types. A user-supplied field not listed below must be nil, empty, or the Go zero value and is rejected when it has any other value. An explicit JSON value that decodes to the same Go zero value as an omitted field is treated as omitted. API-server defaults and admission-added values are recovery-time live-object state, not an expansion of the user allow-list; protected live fields must still equal the canonical CBSE contract.

| Object area | Allowed user fields | Required validation and merge behavior |

SM constructs the effective Job by copying only these allowed values and then applying CBSE-owned fields. Users cannot set or override the Job name, namespace, owner references, metadata finalizers, reserved metadata, `selector`, `manualSelector`, `managedBy`, `ttlSecondsAfterFinished`, `completionMode`, completions, parallelism, `backoffLimitPerIndex`, global `backoffLimit`, `maxFailedIndexes`, `podFailurePolicy`, `podReplacementPolicy`, `successPolicy`, `suspend`, the Pod restart policy, Pod-level active deadline, ServiceAccount fields, token automounting, runner image, runner command or arguments, or required security settings. Also reject ephemeral containers, Pod resource claims or Pod-level resources, readiness gates, scheduling gates, `overhead`, custom `schedulerName`, direct `nodeName`, hostname/subdomain overrides, `hostNetwork`, `hostPID`, `hostIPC`, `hostUsers`, shared process namespace, sysctls, SELinux or Windows security options, custom seccomp or AppArmor profiles, privileged mode, privilege escalation, capability additions, custom process masks, and projected service-account tokens. Every user field not explicitly allowed by the table is prohibited even when it is not named in this summary.

The effective Pod sets `restartPolicy: Never`, `automountServiceAccountToken: false`, `runAsNonRoot: true`, and `RuntimeDefault` seccomp. Every runner, auxiliary regular container, and init container receives `privileged: false`, `allowPrivilegeEscalation: false`, and a capability set that drops `ALL`; user-provided positive UID/GID values and `readOnlyRootFilesystem` are retained. The accepted runner digest always replaces the custom template's `runner` image. The image must work with the built-in template; user customization supplies optional integration and scheduling concerns, not missing executable behavior. The Operator rejects any disallowed field or invalid allowed value and moves the experiment to provisioning `Error`; SM repeats the same validation before any Job create call and treats a conflict that escapes provisioning as a permanent scenario startup failure.

`JobTemplateSpec.metadata.labels` and `.annotations` become user Job metadata; `spec.template.metadata.labels` and `.annotations` remain Pod-template metadata inside the Job specification. Empty user maps and slices are normalized to nil before hashing, set-like name lists such as image pull Secrets are de-duplicated and sorted, and CBSE applies all defaults and protected overrides before normalization. Job or Pod `name`, `generateName`, namespace, owner references, finalizers, reserved metadata keys, status, and server metadata are never accepted from the template. Reserved metadata means every key under `experiment.cbse.terministic.de/` plus Kubernetes Job controller identity keys `controller-uid`, `job-name`, `batch.kubernetes.io/controller-uid`, and `batch.kubernetes.io/job-name`; other user annotations remain permitted integration settings.

SM computes `experiment.cbse.terministic.de/job-contract-sha256` as lowercase hexadecimal SHA-256 over `encoding/json` output from a typed hash-input struct containing finalized client-side Job labels, user Job annotations, and the normalized effective Job specification. Go JSON encoding provides sorted string-map keys; the normalization above removes nil-versus-empty and ordering ambiguity. The hash excludes Job name, namespace, owner references, status, TypeMeta, server metadata, the hash annotation itself, and the API-server-generated Job selector and controller/job-name labels that cannot be known before creation. It represents the client-side desired contract before API admission. The same effective-Job builder and normalization function are used at creation and recovery.

An `AlreadyExists` result is an expected recovery case when Kubernetes accepted Job creation but SM restarted or lost the subsequent Core DB transition. SM accepts the existing Job only when its stored contract-hash annotation equals the newly computed desired hash and its experiment owner UID, identity labels, and normalized protected live fields match. The API-server-generated selector must select exactly the live Job's controller UID, and the corresponding legacy and `batch.kubernetes.io` controller-UID and Job-name labels on the live Pod template must agree with the live Job UID and name; these canonical server-generated values are verified separately rather than hashed. Recovery accepts Kubernetes defaults within allow-listed fields, `schedulerName: default-scheduler`, `priority` derived from an allowed `priorityClassName`, and `overhead` derived from an allowed `runtimeClassName`. Admission-added metadata or values composed entirely from allow-listed fields do not alter the stored desired hash, but they are still checked for reserved metadata, supported volume kinds, non-root security, and every protected field. Any other admission-added field, a noncanonical value for one of the live-only defaults above, or any protected-field mutation is a collision. SM never adopts or rewrites a mismatch.

### Scheduler boundary and RBAC

SM places workload creation and observation behind a small, resource-neutral internal scheduler interface. Core orchestration supplies a validated runner projection and receives successful repetition count, active state, and terminal success or failure without importing `batch/v1` types. This branch provides only the `batch/v1` Kubernetes Job adapter, which owns Job-template merging and Kubernetes-specific identity checks. Alpha4 has no scheduler-provider selection field. A future Volcano or other scheduler adapter must add its own explicit API configuration, template type, resources, third-party integration, and additive RBAC without changing this branch's core state-machine contract or broadening base permissions speculatively.

The default SM ServiceAccount receives only these workload permissions:

- `get`, `list`, `watch`, and `patch` on alpha4 `simulationexperiments`;
- `create`, `get`, `list`, and `watch` on `batch/jobs`;
- `get`, but not `list` or `watch`, on core `secrets`; and
- `get`, but not `list` or `watch`, on core `serviceaccounts`.

Alpha4 SM uses a ClusterRole and ClusterRoleBinding because it discovers experiments and creates or observes Jobs across namespaces. Kubernetes RBAC cannot restrict a metadata-finalizer patch to one field or dynamically restrict `get` to arbitrary Secret and ServiceAccount names supplied by many CRs, so cluster-wide experiment `patch` and cluster-wide Secret and ServiceAccount `get` without `list` or `watch` are the narrowest standard RBAC boundaries that implement this contract. Application code uses experiment patch only for the exact SM finalizer, performs only direct named reads for the current experiment's `registryAuthSecretRef.name` and deterministic runner ServiceAccount, and never exposes a generic lookup endpoint. SM receives no Pod, ConfigMap, Job update, Job patch, Job delete, experiment-status update, experiment update, experiment delete, or RBAC-management permission. ConfigMap and Secret volumes other than the required registry Secret are resolved by Kubernetes and do not require SM to read those objects. Per-experiment runner ServiceAccounts have no RoleBinding and set `automountServiceAccountToken: false`.

Before starting informers, NATS consumers, runner selection, or observation, SM uses Kubernetes authorization checks to verify every required verb and resource above across namespaces, including experiment patch for finalizer management. A denied startup check is a fatal installation error and prevents startup because the deployment cannot execute its contract. If an operation for an individual scenario later returns HTTP `403 Forbidden`, SM does not terminate the process: it logs the verb, resource, namespace, and scenario, then applies the guarded transition for that scenario to `Failed`. A later `Forbidden` on the process-wide experiment list/watch has no single scenario to fail; SM marks readiness false, keeps liveness true, and retries after `1s`, `2s`, `4s`, `8s`, `16s`, and then `30s` until a successful list/watch resets the delay and readiness. It exits neither the process nor any domain state. Neither path may stop unrelated scenario keys already available to workers.

### Configuration validation and failure classes

The implementation must not use “invalid configuration” as an undifferentiated error. Validation is grouped and classified as follows:

1. **Alpha4 experiment provisioning.** The Operator rejects an invalid namespace or experiment name; a non-digest Translator, Builder, or base image; a tagged or digested `translator.repository`; an empty `registryAuthSecretRef.name`; a referenced Secret that does not yet exist in the experiment namespace; a wrong-type or malformed Docker configuration Secret; a missing or invalid basic-auth entry for a required registry host; invalid Builder request or limit quantities; or a runner Job template containing an unlisted field, an invalid allowed value, a protected-field override, or a non-root violation. The Operator reports the exact field or referenced object and moves provisioning to `Error` before creating experiment components.
2. **Translator startup.** Translator refuses readiness for a missing or malformed NATS URL, stream, request subject, ready-subject template, consumer name, experiment identity, repository, or base image; missing or malformed registry or Result DB Secret files; a non-numeric or out-of-range Result DB port; or an unwritable workspace. The error names the setting or mounted path without printing its value when it may contain credentials.
3. **Scenario Manager startup.** SM fails startup for a malformed Core DB DSN, incompatible required table schema, invalid NATS subject template, invalid configured stream or consumer name, or a denied required cluster-wide Kubernetes authorization check. It reports the exact setting, schema check, or denied verb/resource before starting informers, consumers, scenario selection, or runner observation.
4. **Runtime dependencies.** A syntactically valid but unavailable NATS server or Kubernetes API is a retryable dependency failure. A registry, BuildKit, generator, push, or digest-resolution failure while handling a Translator request follows the confirmed empty-image workflow. A Result DB failure makes the current indexed runner Pod fail and consumes one attempt for that index. A scenario-specific Kubernetes `Forbidden` or exhausted bounded Job-reconciliation retry transitions only that scenario to `Failed`; SM continues other work. None of these failures is relabeled as a startup configuration error.
5. **Messages and scenario work.** Invalid subject shape, payload shape, attempt identity, repository, or scenario-specific generator input follows the poison-message or guarded scenario-failure rules defined by the owning workflow. It is not a process startup configuration failure. A lifecycle rejection is classified separately: pre-`InProgress` work is transient and retryable, while `Error`, `Failed`, `Completed`, and deletion are permanent for messaging and use ACK-and-discard without scenario mutation.

### Lightweight scenario observability

Scenario execution uses concise, credential-free logs and Kubernetes' existing Job and Pod diagnostics. SM logs Job creation or adoption and one terminal scenario outcome. Those records include experiment namespace and name, scenario ID, translation attempt, Job name, requested repetitions, computed repetitions, outcome, and a short reason. SM does not log every successful repetition or every unchanged observation poll.

The basic generated runner emits no framework debug stream and no per-simulation-event log. On each runner-controlled failed Pod attempt, it emits one timestamped terminal record containing scenario ID, Pod hostname, failure stage, and a sanitized reason, then exits non-zero. A controlled simulation failure writes no result row; an ambiguous PostgreSQL commit may have written a row before the failure became visible. Kubernetes owns the completion index used for retry accounting, but the Pod hostname and index do not create a repetition identity in the Core DB or Result DB. Failures before the runner starts remain visible through standard Job conditions, Pod status, and Kubernetes events. SM does not gain Pod-read RBAC for logging.

Automatic collection, centralized storage, size limits, retention periods, and deletion of old scenario logs are future operational work. This branch keeps completed and failed Jobs available for inspection and does not implement log garbage collection.

### State boundary

This branch implements this prefix of the scenario diagram:

```text
Created -> Scheduled -> StartingRunners -> InProcessing
                          | startup failure       | Job success
                          v                       v
                       Failed             PostProcessing

InProcessing --Job failure--> Failed
```

`Scheduled -> StartingRunners` remains owned by accepted Translator ready handling. `StartingRunners -> InProcessing` is owned by SM after a matching Job exists. SM then observes that exact Job. Job success owns `InProcessing -> PostProcessing`; Job failure owns `InProcessing -> Failed`. `PostProcessing` is a boundary state in this branch. SM does not invoke the PostProcessingService or move a scenario from `PostProcessing` to `StartingRunners` or `Finished`.

The experiment diagram remains unchanged. The Operator moves an alpha4 experiment through `Pending`, `Provisioning`, and `InProgress` when components are ready, and may set `Error` for a provisioning problem. The intended future owner of execution-level `Failed` and `Completed` transitions is SM. This branch does not implement those two experiment transitions. It observes `Error`, `Failed`, and `Completed` to close the messaging lifecycle gate and run terminal artifact cleanup; deletion closes the same gate as soon as `deletionTimestamp` is observed. No NATS or JetStream request is expected in `Completed`, and SM performs no scenario-work consumption in `Error`, `Failed`, `Completed`, or during deletion.

### Runner-start projection and validation

SM reads one runner-start projection from the Core DB: scenario ID, `number_of_reps`, `number_of_computed_reps`, persisted runner digest, translation attempt, and project namespace and name. It then gets that exact alpha4 experiment from Kubernetes, reads its current UID, and requires phase `InProgress`. It revalidates the runner digest and requires its normalized repository to equal `spec.translator.repository` before creating a Job. The live UID becomes the owner-reference and workload-label identity; it is not loaded from Core DB.

`number_of_reps` must be between `1` and `100000`, and `number_of_computed_reps` must initially be zero for this execution. A larger value is a permanent invalid-repetition failure and no Job create is attempted. The runner digest and template must be valid before Job creation. SM performs direct named `GET` operations for the experiment's registry Secret and deterministic runner ServiceAccount. It revalidates the Secret type, key, Docker JSON, and basic credentials for the generated image's registry authority with the same standard resolver used by the Operator; this catches a Secret replaced after provisioning. The Job includes that Secret reference in `imagePullSecrets`; a custom template may add other distinct pull Secrets but cannot remove or replace it.

The Job and its Pod template must carry these labels:

- `experiment.cbse.terministic.de/project=<experiment-name>`
- `experiment.cbse.terministic.de/experiment-uid=<full-UID>`
- `experiment.cbse.terministic.de/scenario-id=<decimal-scenario-id>`
- `experiment.cbse.terministic.de/translation-attempt=<decimal-attempt>`

The Job also carries `experiment.cbse.terministic.de/job-contract-sha256=<lowercase-SHA-256>` using the effective-contract hashing rules above. Before accepting `AlreadyExists`, SM compares the owner UID, identity labels, contract hash, runner image and executable fields, indexed completion mode, completions, parallelism, `backoffLimitPerIndex`, global backoff limit, absent `maxFailedIndexes`, restart policy, required ServiceAccount and image pull Secret, token setting, pod security settings, and every other protected field. A mismatch is a collision and is never adopted.

### Startup result handling

SM creates or confirms the Job before calling the guarded `StartingRunners -> InProcessing` update. If the update affects zero rows, SM logs a stale result and does not change the Job. This is expected when another worker confirmed the same Job and won the transition.

The following are permanent startup failures. SM calls the guarded `StartingRunners -> Failed` transition: invalid repetition state, image, image repository, or runner template; missing or wrong-type pull Secret; missing, deleting, or terminal-phase experiment; a runtime Kubernetes `Forbidden`; and a Job collision.

Ordinary Kubernetes transport failures and the fixed 10-second deadline on each get or create call are retryable for that scenario. For each qualifying failure, SM atomically increments `runner_reconciliation_failures` while guarding scenario ID and `StartingRunners`. Counts `1` through `5` requeue that key after `1s`, `2s`, `4s`, `8s`, and `16s`; count `6` exhausts the initial attempt plus five retries and causes the guarded `StartingRunners -> Failed` transition. A successful create or matching `AlreadyExists` atomically resets the counter to zero before or with `StartingRunners -> InProcessing`. Process shutdown cancellation does not increment the counter. An experiment in an empty, `Pending`, or `Provisioning` phase requeues after five seconds without consuming the failure budget. This retries reconciliation of one deterministic Job and never creates differently named replacement Jobs; the database counter preserves the bound across SM restarts, and delayed retries never sleep a worker or block another key.

### Runner terminal observation

Runner observation is independent of selection and translation. SM performs one discovery immediately after startup and every five seconds thereafter, listing all `InProcessing` rows and adding their scenario keys to one de-duplicating, process-local, rate-limited work queue. Four fixed workers reconcile keys concurrently; delayed retries use the queue's `AddAfter` mechanism and never sleep a worker. Every Kubernetes call made for one key has a 10-second deadline. `InProcessing` is not part of the ordinary lowest-ID actionable query. A missing, forbidden, colliding, slow, or failing Job therefore consumes only its own retry state and bounded worker time and cannot prevent discovery or eventual reconciliation of other `InProcessing` scenarios.

The observation projection contains the scenario ID, requested and computed repetition counts, translation attempt, project namespace, project name, and the fields needed to verify the deterministic Job identity. The scheduler adapter gets the current experiment to obtain its live UID, then gets the exact Job and confirms its owner UID, reserved UID label, and protected contract before applying progress or a terminal result. SM does not watch Pods.

The result rules are:

- For every observation, SM parses the Kubernetes compressed-index syntax in `job.status.completedIndexes`, validates that every interval is ordered, non-overlapping, and within `0..number_of_reps-1`, and counts the represented indexes without expanding them into a large slice. It atomically sets `number_of_computed_reps` to `GREATEST(current_value, completed_index_count)` while guarding scenario ID and state `InProcessing`. `completedIndexes`, not the aggregate `status.succeeded`, is the authoritative unique-index set. The value never decreases or exceeds `number_of_reps`, so duplicate Pods for one index, informer redelivery, Pod retry, and SM restart cannot double-count an index. A malformed or out-of-range server-owned index string is treated as a Job identity/status collision and fails only that scenario.
- A failed Pod attempt does not increment the counter. Kubernetes replaces it for the same index until that index succeeds or exhausts four retries. Because `maxFailedIndexes` is absent, other indexes continue to resolution. A Job with Kubernetes `Failed=True` first preserves the observed partial successful-index count, then causes a guarded `InProcessing -> Failed` update.
- A Job with Kubernetes `Complete=True` first records `number_of_computed_reps = number_of_reps`, then causes a guarded `InProcessing -> PostProcessing` update.
- A Job without either terminal condition remains `InProcessing` without error.
- A missing Job, per-operation deadline, or ordinary Kubernetes transport failure atomically increments `runner_reconciliation_failures` while leaving the row `InProcessing` and requeues only that scenario after the same `1s`, `2s`, `4s`, `8s`, and `16s` sequence. Count `6` preserves the current successful-index count and applies the guarded `InProcessing -> Failed` transition. Process shutdown cancellation does not consume an attempt. This branch does not recreate a Job after the scenario entered `InProcessing`.
- A runtime `Forbidden` while getting the experiment or Job is a permanent failure for that scenario. SM preserves the current successful-index count, applies the guarded `InProcessing -> Failed` transition, and continues processing other scenarios.
- A Job that exists under the deterministic name but does not match the observation projection is a collision. SM applies the guarded `InProcessing -> Failed` transition and does not adopt the Job.
- A stale projection or zero-row guarded update is a successful no-op.

A successful observation atomically resets `runner_reconciliation_failures` to zero, including for a non-terminal active or pending Job. Kubernetes scheduling delay, `Job.status.active > 0`, and unschedulable Pending Pods are successful observations rather than transport failures; Kubernetes remains responsible for admitting Pods as resources become available.

If an invalid Job reports both terminal conditions, SM treats `Failed=True` as failure and does not move the scenario to `PostProcessing`. `number_of_computed_reps` records Kubernetes-confirmed successful completion indexes; SM does not derive it from Result DB rows. Completed and failed Jobs remain present for inspection.
