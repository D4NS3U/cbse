# Slice 01: Alpha4 API and CRD

## Goal

Define the alpha4-only API and generated CRD foundation used by every later slice.

## Dependencies

None.

## Contracts consumed

This slice consumes the root [Kubernetes compatibility](../FEATURE.md#kubernetes-compatibility), [upgrade](../FEATURE.md#upgrade-from-alpha2-or-alpha3), [identity](../FEATURE.md#identity-and-lifecycle-invariants), and [cutover](../FEATURE.md#alpha4-cutover-checkpoint) contracts.

## Files and components owned

1. `experiment-operator/api/alpha4/`, CRD manifests, schemes, samples, and tests -- define alpha4 only, retain required `baseimage`, make both complete database specifications and all Translator Deployment/Service-shaping fields listed above immutable, add `registryAuthSecretRef` as `corev1.LocalObjectReference`, add `builderResources` as `corev1.ResourceRequirements`, and define the optional typed runner Job template with a complete structural schema and no unknown-field preservation, UID environment value, BuildKit sidecar, and runner ServiceAccount.

## Required behavior

1. **Alpha4 API, identity, and registry authentication.**
   - Carry the alpha3 user-facing schema into `api/alpha4`, retain required `spec.translator.baseimage`, and add required `spec.translator.registryAuthSecretRef corev1.LocalObjectReference` and `spec.translator.builderImage`. In YAML, the reference is `registryAuthSecretRef: {name: cbse-registry-auth}`; it is never an inline, plain, or base64-encoded credential string. `spec.translator.image` continues to select the Translator container. `builderImage` independently selects its rootless BuildKit sidecar, while `baseimage` selects the runner base from which Translator generates scenario-specific images. The carried `spec.translator.command`, `args`, `serviceType`, `nodePort`, and `port` fields remain creation-time configuration for the always-on Translator Deployment and Service; alpha4 does not treat any of them as a live rollout surface.
   - Add optional `spec.runner.jobTemplate` as a typed Kubernetes `batch/v1.JobTemplateSpec`. Its generated CRD subtree has a complete structural OpenAPI schema and does not use `x-kubernetes-preserve-unknown-fields`. When absent, SM uses the minimal built-in runner Job. When present, it provides the permitted Job and Pod customization described below.
   - `spec.detailDatabase`, `spec.resultDatabase`, `spec.translator.image`, `spec.translator.repository`, `spec.translator.baseimage`, `spec.translator.builderImage`, `spec.translator.builderResources`, `spec.translator.command`, `spec.translator.args`, `spec.translator.serviceType`, `spec.translator.nodePort`, `spec.translator.port`, and `spec.runner.jobTemplate` are immutable for the lifetime of an alpha4 `SimulationExperiment`. Immutability begins when the object is admitted to the cluster; changing database image or host selection, connection metadata, credentials, service exposure, command, arguments, Translator image, or any other listed field requires deletion and recreation of the experiment. The generated CRD must enforce this at API admission with separate `oldSelf` transition rules, not through a later Operator reconciliation error. On `spec`, the database rules are `self.detailDatabase == oldSelf.detailDatabase` and `self.resultDatabase == oldSelf.resultDatabase`. On `spec.translator`, the required or API-defaulted scalar rules are `self.image == oldSelf.image`, `self.repository == oldSelf.repository`, `self.baseimage == oldSelf.baseimage`, `self.builderImage == oldSelf.builderImage`, `self.serviceType == oldSelf.serviceType`, and `self.port == oldSelf.port`. The optional-field rules reject addition, removal, or modification: `has(self.builderResources) == has(oldSelf.builderResources) && (!has(self.builderResources) || self.builderResources == oldSelf.builderResources)`, `has(self.command) == has(oldSelf.command) && (!has(self.command) || self.command == oldSelf.command)`, `has(self.args) == has(oldSelf.args) && (!has(self.args) || self.args == oldSelf.args)`, and `has(self.nodePort) == has(oldSelf.nodePort) && (!has(self.nodePort) || self.nodePort == oldSelf.nodePort)` on `spec.translator`, plus `has(self.jobTemplate) == has(oldSelf.jobTemplate) && (!has(self.jobTemplate) || self.jobTemplate == oldSelf.jobTemplate)` on `spec.runner`. Each rule has its own rejection message naming the immutable field and instructing the user to delete and recreate the CR. An update leaving all thirteen immutable fields unchanged passes ordinary supported metadata or status changes. There is no in-place rollout, migration, or reconciliation behavior for changing these fields; in particular, the Operator never rolls out a new Translator image, executable configuration, or Service configuration for an existing alpha4 experiment. The existing SM cleanup finalizer and deletion contract must complete before a replacement with the same namespace/name is created.

## Failure and retry behavior

API admission failures are permanent request failures. Provisioning-time classification is owned by [Slice 03](03-operator-provisioning.md).

## Security boundaries

Credential values remain outside the CRD; the cross-cutting boundary is defined in [Registry Credential Boundary](../FEATURE.md#registry-credential-boundary).

## Acceptance tests

Test alpha4-only CRD guidance; retained required `baseimage`; the exact `corev1.LocalObjectReference` registry-reference shape; the CPU/memory-only `corev1.ResourceRequirements` shape; 1-to-63-character DNS-label project validation; namespace/name-only project registration and lookup; deletion cascade; and required Core DB schema failure for missing, wrongly typed, obsolete, or extra project columns. Verify that the project table contains only its technical ID, namespace, and name, while `scenario_status` adds only the non-identity `translation_publish_started_at TIMESTAMPTZ NULL` column. Test independently defaulted limits, optional requests, request-not-greater-than-limit validation, and rejection of claims or non-CPU/memory resources for the separate Translator Builder contract. Exercise CRD admission updates that independently change `detailDatabase`, `resultDatabase`, `translator.image`, `translator.repository`, `translator.baseimage`, `translator.builderImage`, `translator.builderResources`, `translator.command`, `translator.args`, `translator.serviceType`, `translator.nodePort`, `translator.port`, and `runner.jobTemplate`; require API-server rejection with the immutable field named, including each individual database subfield, each Translator Deployment/Service-shaping field, and addition or removal of every optional field or object. Verify an update that leaves all thirteen fields unchanged can modify otherwise supported metadata or status, and verify that every rejected Translator update leaves the existing Deployment and Service generation and observed configuration unchanged. Require `registryAuthSecretRef.name` to equal `cbse-registry-auth` and reject an empty or different name. Require that same-named Secret to exist in the experiment namespace before provisioning; test the standard Docker resolver's host-alias behavior, missing references, wrong Secret type, a missing `.dockerconfigjson` key, malformed Docker JSON, missing basic credentials, unsupported token/helper-only credentials, replaced-Secret revalidation by SM without logging credentials or credential-file paths, preservation of the user-owned Secret during experiment deletion, and removal of the copied Secret before a retained smoke namespace is returned. Require the source Secret and `CBSE_REGISTRY_AUTH_FILE` to resolve to the same `registry.unibw.de` username and password; test equivalent differently serialized Docker configurations, a username mismatch, a password mismatch, and secret-safe mismatch diagnostics before mutation. Verify the exact smoke repositories, rejection of repository overrides, no repository-creation API call, support for both pre-existing repositories and implicit creation on a first push, and ordinary canonical-tag replacement without a preliminary delete. Test authenticated Harbor Artifact List preflight with both an existing-repository `200` response and the accepted initial repository-not-found `404`, then require a post-push `200`; verify that `401`, `403`, or another preflight result fails without mutating the cluster. Test denied Artifact List, Read, and Delete after the runner repository exists and require the smoke result to fail without attempting a project or whole-repository deletion. Verify that cleanup targets only `cbse-test-runner` even though the robot credential's Artifact Delete capability applies project-wide and can delete artifacts in `cbse-test` and `cbse-test/scenario-detail-database`. Test that an already-absent expected tag and recorded digest count as successful idempotent cleanup without DELETE, that a remaining reference prevents the absent shortcut, and that any additional tag attached to an otherwise verified digest fails cleanup without DELETE. Test the absent default runner template and at least one valid value from every allow-list row and every validation-matrix row: Job and Pod metadata, active deadline, regular sidecar, ordinary init container, native sidecar, every supported volume source, additional pull Secret, each scheduling field, Pod runtime and DNS fields, Pod numeric identity, runner environment/resources/ports/mounts/devices/probes/pull policy/termination fields, auxiliary executable fields, and allowed container identity/filesystem settings. For runner resources, accept valid standard compute, ephemeral-storage, `hugepages-*`, and extended-resource examples; reject invalid huge-page names, quantities, request/limit relationships, and every other violation of the pinned Kubernetes 1.30 resource rules. Verify regular-sidecar and native-sidecar completion behavior and retention of the experiment registry pull Secret. Test the zero-value-as-omitted rule and the complete field-census default-deny behavior for fields present in the repository's build-time Kubernetes structs but absent from the Kubernetes-1.30-based alpha4 surface. Reject `suspend`, every prohibited Job policy field, every unsupported Pod control or volume field, projected service-account tokens, resource claims, missing or duplicate `runner` containers, runner executable overrides, reserved metadata, protected Pod annotations, zero or negative identities, and every privileged or otherwise protected security override.
