# Slice 02: Job-template policy

## Goal

Define and validate the complete, default-deny alpha4 runner Job-template surface against Kubernetes 1.30 behavior.

## Dependencies

[Slice 01](01-alpha4-api-and-crd.md) supplies the typed `batch/v1.JobTemplateSpec` API and structural CRD subtree.

## Contracts consumed

This slice consumes the root [Kubernetes compatibility](../FEATURE.md#kubernetes-compatibility), [security](../FEATURE.md#registry-credential-boundary), and [successful CREATE](../FEATURE.md#successful-kubernetes-job-create) contracts.

## Files and components owned

The Operator-internal `ValidateAndNormalizeJobTemplate` policy and its fixtures are the canonical implementation boundary. The surrounding controller ownership is described by [Slice 03](03-operator-provisioning.md#files-and-components-owned).

## Required behavior

### Runner Job customization contract

`spec.runner.jobTemplate` is optional. It is a typed `batch/v1.JobTemplateSpec`, not raw YAML and not a ConfigMap containing a Job. The built-in template is used when the field is absent. A supplied template must contain exactly one regular container named `runner`; other regular containers and init containers have unique names. The public template API is the explicit alpha4 allow-list below, defined for the Kubernetes 1.30-or-newer support range rather than by a particular `k8s.io/api` module version. A user-supplied field not listed below must be nil, empty, or the Go zero value and is rejected when it has any other value, including when the repository's current Go types expose that field. An explicit JSON value that decodes to the same Go zero value as an omitted field is treated as omitted. The allow-list governs values users may request through the persisted template. Kubernetes admission is the trusted owner of the final live Job and may default or mutate its specification and non-identity metadata after SM submits it. SM does not repeat template validation, compare the admitted Job with the submitted effective Job, or classify the object returned by a successful create.

The generated alpha4 CRD publishes the complete structural OpenAPI schema for this typed subtree and must not set `x-kubernetes-preserve-unknown-fields` on it or an ancestor that would preserve unknown Job-template fields. Unknown and duplicate request fields follow the Kubernetes `fieldValidation` contract: `Strict` rejects them, while `Warn` or `Ignore` permits the API server to drop unknown fields and retain only the last occurrence of a duplicated field before persistence. The Operator validates only the persisted typed object it receives. It never reconstructs, guesses, or corrects request data discarded during admission, and alpha4 does not claim guaranteed rejection of the original unknown or duplicate input for a non-strict request.

The Operator validator enforces the following ownership boundary. Users cannot set or override the Job name, namespace, owner references, metadata finalizers, reserved metadata, `selector`, `manualSelector`, `managedBy`, `ttlSecondsAfterFinished`, `completionMode`, completions, parallelism, `backoffLimitPerIndex`, global `backoffLimit`, `maxFailedIndexes`, `podFailurePolicy`, `podReplacementPolicy`, `successPolicy`, `suspend`, the Pod restart policy, Pod-level active deadline, ServiceAccount fields, token automounting, runner image, runner command or arguments, or required security settings. It also rejects ephemeral containers, Pod resource claims or Pod-level resources, readiness gates, scheduling gates, `overhead`, custom `schedulerName`, direct `nodeName`, hostname/subdomain overrides, `hostNetwork`, `hostPID`, `hostIPC`, `hostUsers`, shared process namespace, sysctls, SELinux or Windows security options, custom seccomp or AppArmor profiles, privileged mode, privilege escalation, capability additions, custom process masks, and projected service-account tokens. Every user field not explicitly allowed by the table is prohibited even when it is not named in this summary. For an accepted template, SM constructs the effective Job by copying only the allowed values and then applying CBSE-owned fields.

The effective Pod sets `restartPolicy: Never`, `automountServiceAccountToken: false`, `runAsNonRoot: true`, and `RuntimeDefault` seccomp. Every runner, auxiliary regular container, and init container receives `privileged: false`, `allowPrivilegeEscalation: false`, and a capability set that drops `ALL`; user-provided positive UID/GID values and `readOnlyRootFilesystem` are retained. The accepted runner digest always replaces the custom template's `runner` image. The image must work with the built-in template; user customization supplies optional integration and scheduling concerns, not missing executable behavior.

The Operator's internal function has the conceptual contract `ValidateAndNormalizeJobTemplate(*batchv1.JobTemplateSpec) (*batchv1.JobTemplateSpec, field.ErrorList)`, using `k8s.io/apimachinery/pkg/util/validation/field.ErrorList`. An absent template returns an absent copy and no errors. A present template is deep-copied before inspection; neither success nor failure may mutate the CR or its nested maps, slices, pointers, or quantities. The function collects every detectable validation failure in one pass. Every error is rooted at `spec.runner.jobTemplate`, identifies the precise field path and reason, and must not include environment values or other potentially sensitive template contents. Any error moves the experiment to provisioning `Error` without allowing it to reach `InProgress` or SM runner-start admission.

Validation happens before normalization. The nested alpha4 surface and known-field semantic behavior are fixed to Kubernetes `v1.30.0`, independently of the repository-selected `k8s.io/*` module versions. Within a composite field listed in the allow-list above, only nested members present in the external Kubernetes `v1.30.0` `batch/v1` and `core/v1` types are eligible, subject to every narrower alpha4 prohibition. A nested member introduced after 1.30 remains prohibited even when the repository's current Go structs expose it. The normative behavioral references are the Kubernetes `v1.30.0` files `pkg/apis/core/validation/validation.go`, `pkg/apis/batch/validation/validation.go`, `pkg/apis/core/v1/defaults.go`, and `pkg/apis/batch/v1/defaults.go`. Function names from those files in the matrix below describe required behavior only; implementation must not import `k8s.io/kubernetes` or its internal API types.

The Operator implements the matrix over external `corev1` and `batchv1` objects using the named public `k8s.io/apimachinery` helpers plus explicit local CBSE checks. A “local equivalent” reproduces only the relevant Kubernetes `v1.30.0` checks for alpha4-allowed fields; it does not copy or invoke the complete native Pod or Job validator. Validation examines the persisted typed object without mutating it, registering or invoking a Kubernetes defaulting scheme, or constructing a defaulted validation object. A Go zero value that typed decoding cannot distinguish from omission is treated as omitted unless the matrix marks that member as required. A non-nil pointer or present list entry remains observably present, and required members such as container, volume and referenced-object names, auxiliary images, ports, and handler actions cannot use the zero-value rule to evade validation. Kubernetes-defaultable zero values are accepted without materializing their defaults; a supplied non-zero value must pass the pinned rules. When a cross-field check depends on an omitted server-defaulted value, the local check may consult the exact Kubernetes 1.30 default as an immutable comparison constant but must not write that value into any validation or normalized object.

Backward-compatibility allowances for historically invalid selectors or values are disabled. Native-sidecar structure is validated locally as defined below, but live-cluster feature-gate availability is not. Referenced ConfigMaps, Secrets, PVCs, PriorityClasses and RuntimeClasses; admission webhooks; optional feature gates; and cluster policies remain final effective-Job `CREATE` concerns. Operator acceptance therefore does not promise that a later live `CREATE` will be admitted. If a repository-selected public helper later diverges from the pinned Kubernetes 1.30 fixtures, the implementation adds a local compatibility wrapper instead of changing alpha4 behavior; a `k8s.io/*` module upgrade must not silently change this matrix. In the helper column, `api/validation` means `k8s.io/apimachinery/pkg/api/validation`, `api/validation/path` means `k8s.io/apimachinery/pkg/api/validation/path`, `metav1/validation` means `k8s.io/apimachinery/pkg/apis/meta/v1/validation`, `util/validation` means `k8s.io/apimachinery/pkg/util/validation`, and `resource` means `k8s.io/apimachinery/pkg/api/resource`.

A repository-selected helper is an implementation mechanism, while this matrix and its pinned fixtures are the alpha4 behavior contract. The Operator does not import the complete `k8s.io/kubernetes` native Job validator, create or dry-run a validation Job, or issue any other server-side validation request.

Only after the copy passes validation may the function normalize that private copy. Normalization collapses nil and empty maps or slices to the documented canonical nil representation, treats the documented Go zero values as omitted, and sorts duplicate-free collections explicitly defined as set-like. For this branch, user-supplied `imagePullSecrets` is the only set-like list; every other user list, including `supplementalGroups`, preserves its submitted order. Normalization never trims or changes a scalar, fixes capitalization or spelling, guesses a name or reference, removes a duplicate, drops an invalid known value, supplies a Kubernetes default, or otherwise turns invalid user input into valid input. The normalized copy is used only by Operator validation tests and internal checks; it is not persisted, handed to SM, or exposed through an alpha4 field, status value, annotation, or other handoff artifact. Because `spec.runner.jobTemplate` is immutable from admission and SM admits runner work only for a live, non-deleting `InProgress` experiment, SM treats the persisted template as Operator-validated and neither imports nor repeats this validator.

`JobTemplateSpec.metadata.labels` and `.annotations` become desired Job metadata; `spec.template.metadata.labels` and `.annotations` become desired Pod-template metadata inside the Job specification. As a separate construction concern rather than template policy validation, SM builds the scenario-specific effective Job from the original persisted template, normalizes empty maps and slices to nil, sorts only `imagePullSecrets`, and retains every other list in its defined desired order. Operator validation has already rejected duplicate user pull-Secret entries. When the duplicate-free user pull-Secret list contains `cbse-registry-auth` once, SM coalesces that entry with its protected addition; otherwise it appends the protected reference, then sorts the effective set. This required-field merge is not correction of a user duplicate. SM then applies every other CBSE protected field. This normalization is part of effective-Job construction and does not materialize Kubernetes API-server defaults. Job or Pod `name`, `generateName`, namespace, owner references, finalizers, reserved metadata keys, status, and server metadata are never accepted from the template. Identity-reserved metadata means every key under `experiment.cbse.terministic.de/` plus Kubernetes Job controller identity keys `controller-uid`, `job-name`, `batch.kubernetes.io/controller-uid`, and `batch.kubernetes.io/job-name`. Pod-template annotations also reserve the five exact keys or prefixes enumerated by the validation matrix because they can express mirror-Pod, scheduling, seccomp, or AppArmor behavior that CBSE owns or prohibits. Other non-reserved user labels and annotations remain permitted integration settings.

Kubernetes admission is part of the trusted cluster boundary and owns the final live Job. Admission may default or mutate the Job specification and non-identity metadata after SM submits it. A successful Kubernetes Job `CREATE` is authoritative: SM does not validate or compare any field in the returned Job, including namespace, name, UID, owner references, reserved labels, specification, or non-identity metadata, and it does not invoke the ownership verifier on this path. SM immediately attempts the guarded `StartingRunners -> InProcessing` transition. It retains only the returned UID, process-locally and only for the duration of that runner-start workflow, so it can perform UID-preconditioned deletion if lifecycle-gate closure races the successful create; the UID is not persisted. This contract relies on a conformant API server and a trusted admission chain to preserve CBSE-owned identity fields. SM does not apply an API-server defaulting scheme.

Only when a deterministic named Job already exists, is later observed, or is considered for ordinary destructive cleanup does SM verify ownership before using or deleting it. This ownership verification never applies to the object returned by a successful create. The Job must have the expected namespace and deterministic name; the exact controller owner reference with `apiVersion: experiment.cbse.terministic.de/alpha4`, `kind: SimulationExperiment`, the live experiment's name and full UID, `controller: true`, and `blockOwnerDeletion: false`; and the exact Job-label values for project name, full experiment UID, scenario ID, and translation attempt. Other Job specification and metadata values are not part of this check. Cluster admission must preserve these ownership fields because recovery, observation, and ordinary destructive cleanup depend on them. If trusted admission violates that prerequisite, a later ownership-checked path applies its ordinary mismatch behavior; successful-create handling adds no separate detection or remediation.

An `AlreadyExists` result is an expected recovery case when Kubernetes accepted Job creation but SM restarted, lost the subsequent Core DB transition, or another SM replica created the same deterministic Job. SM accepts the existing Job when the ownership check passes, regardless of admission-added or admission-mutated specification and non-identity metadata. An ownership mismatch is a collision. SM never adopts, rewrites, or deletes a mismatching `AlreadyExists` Job.

Principals allowed to create Jobs in experiment namespaces are trusted not to forge CBSE deterministic Job names, controller owner references, or reserved identity labels. Untrusted Job creators in those namespaces are unsupported.

## Failure and retry behavior

Template rejection is a provisioning failure before `InProgress`; the grouped classification remains in the root [Configuration validation and failure classes](../FEATURE.md#configuration-validation-and-failure-classes).

## Security boundaries

The protected-field and non-root rules in the allow-list are authoritative. Effective Job creation and live admission are owned by [Slice 06](06-runner-job-orchestration.md).

## Acceptance tests

All Job-template allow-list, normative validation-matrix, non-root security, zero-value, and template-level normalization fixtures in this section are Operator tests. Use table-driven fixtures with at least one accepted and one rejected case for every validation-matrix row, including boundary cases for every enum, numeric range, union, declared-object reference, uniqueness rule, and cross-field rule named by that row. Pass an absent template and a valid template containing at least one value from every allow-list group. Require validation to return a distinct deep copy without changing the CR or sharing mutable nested state. Reject missing or invalid required names, duplicate names and duplicate user pull-Secret entries, broken volume references, malformed union/source objects, invalid metadata, enums and numeric ranges, incompatible cross-field combinations, malformed ports, probes and lifecycle actions, invalid DNS and scheduling values, invalid resources, and representative invalid values from every allow-list group. Include rejection of any resource quantity that would change under Kubernetes milli-precision rounding. Every rejected fixture must identify its precise `spec.runner.jobTemplate...` path.

Reject each protected Pod-template annotation independently: `kubernetes.io/config.mirror`, `scheduler.alpha.kubernetes.io/tolerations`, `seccomp.security.alpha.kubernetes.io/pod`, one key under `container.seccomp.security.alpha.kubernetes.io/`, and one key under `container.apparmor.security.beta.kubernetes.io/`. Accept a syntactically valid benign non-reserved integration annotation. Prove that newer fields exposed by the repository's current Go types remain default-denied beneath otherwise allowed parents, including `VolumeSource.image`, Pod-level `resources`, and `PodSecurityContext.supplementalGroupsPolicy`. Maintain a reflection-based field-census test beginning at `batchv1.JobTemplateSpec`: follow struct fields plus pointer, slice, and array element types; treat scalars, maps, and standard leaf value types such as `resource.Quantity`, `intstr.IntOrString`, and `metav1.Time` as terminal; and track visited Go types to terminate recursive graphs. Every discovered JSON field path must be classified as alpha4-allowed or prohibited, so a newly added Go field fails the test until it is explicitly classified. Maintain pinned Kubernetes-1.30 golden fixtures for helper boundaries and local-equivalent behavior; a helper change or module upgrade must use a compatibility wrapper when necessary and must not update those fixtures without an explicit alpha4 specification change.

For every invalid template class, require a field-path-specific, value-safe error, move the experiment to `Error` without reaching `InProgress`, and prevent SM runner-start admission. Verify that the error does not contain an environment value or full template serialization. Prove typo-like known errors are rejected without trimming, case correction, name generation, value replacement, field removal, or default insertion. Test normalization separately: only nil/empty representation and duplicate-free set ordering may change; scalar values and ordered lists remain identical. Duplicate validation must run before sorting, while one user occurrence of `cbse-registry-auth` must merge with the protected effective-Job reference exactly once.

Exercise the generated CRD schema with raw API requests. Submit an unknown Job-template field and a duplicated known field with `fieldValidation=Strict` and require API rejection for each. Repeat with `Warn` and `Ignore`; verify the API server drops the unknown field, retains only the last duplicate occurrence, and persists the resulting typed object. Prove the Operator neither recreates nor interprets discarded request data and validates only that persisted object. Assert that the Job-template subtree is complete and structural and that neither it nor an ancestor enables `x-kubernetes-preserve-unknown-fields` for that data.

Keep `ValidateAndNormalizeJobTemplate` under the Operator's `internal` boundary, use only the validation matrix's repository-selected public Kubernetes helpers plus explicit local checks over external `corev1` and `batchv1` objects, and treat the named Kubernetes `v1.30.0` internal validation functions only as behavioral references. Assert that its implementation does not import `k8s.io/kubernetes` or internal Kubernetes API types, copy or invoke the complete native Pod or Job validator, register or invoke a Kubernetes defaulting scheme, construct a defaulted validation object, or create or dry-run a validation Job. Assert that the helper choices, compatibility wrappers, field census, and pinned fixtures preserve the matrix without requiring API semantics newer than Kubernetes 1.30 merely because the build uses newer Go modules. Assert that Scenario Manager has no shared-package or direct dependency on the validator. Scenario Manager effective-Job tests use only templates accepted by the Operator validator; they cover protected-field merging, effective-Job normalization, authoritative successful-create handling without returned-object classification, ownership-only `AlreadyExists` recovery, and ownership-checked observation rather than template-policy validation. Assert that Scenario Manager does not register or invoke Kubernetes defaulting functions. Inject an unexpected SM effective-Job construction failure and verify a permanent scenario failure without a Job create or a call to template-policy validation.

## Completion and handoff

Every validation-matrix row has accepted and rejected fixtures. Pinned Kubernetes 1.30 fixtures pass, no native `k8s.io/kubernetes` validator is used, and no Kubernetes defaulting is invoked.
