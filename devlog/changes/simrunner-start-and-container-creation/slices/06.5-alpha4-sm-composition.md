# Slice 06.5: Alpha4 Scenario Manager composition

## Goal

Compose the transport-neutral alpha4 Scenario Manager library delivered by Slices 01 through 06 into a single runnable binary entry point, so that Slice 07 only has to switch the active import, CRD/scheme, and smoke manifests. This slice writes the missing composition layer — the alpha4 experiment informer, the concrete NATS adapters, the translation-request selection loop, the translator-ready workflow, and the startup/shutdown composition — as additive alpha4 code that is not yet wired into `cmd/main.go`. It does not change any active alpha3 scheme, import, fixture, manifest, or smoke path.

This slice exists because Slices 04 through 06 deliberately delivered the alpha4 SM as a transport-neutral library with no composition entry point, and the alpha4 code documents that composition belongs to the cutover (for example `scenario-manager/internal/alpha4/lifecycle/nats_adapter.go` and `projectstore.go` both state they are "constructed in the alpha4 wiring (Slice 07)"). The cutover checkpoint in [`../FEATURE.md`](../FEATURE.md#alpha4-cutover-checkpoint) permits additive alpha4 work before Slice 07; this slice is that additive work, separated from the thin Slice 07 cutover so neither is rushed.

The `scenario-manager/internal/alpha4/` subtree is a **temporary** placement. Alpha4 is the only served version and alpha3 is deleted at the cutover, so a permanent version-prefixed directory has no meaning. This slice writes its new packages under `alpha4/` only so the active alpha3 binary, CRD, schemes, and smoke path stay unchanged until the integration checkpoint; Slice 07 owns the fold that moves every `alpha4/` package to its final `internal/` home, merges this slice's composition into `internal/core` and `internal/nats`, deletes the dead alpha3 code, and removes the `alpha4/` directory. No code written by this slice is expected to remain under `alpha4/` after Slice 07, and it must be written so the move is a mechanical rename (no package-private coupling that would block it).

## Files and components owned

All package paths below are **temporary**. Slice 07 moves each to its final `internal/` home (`app`/`informer`/`selection`/`lifecycle` → `internal/core`; `natsadapter`/`messaging` → `internal/nats`; `ready` → `internal/core` or a dedicated package), merges the composition in place, and removes the `alpha4/` directory. See Slice 07's repository fold obligation.

10. `scenario-manager/internal/alpha4/app/` — the composition entry point. `RunScenarioManager(ctx)` mirrors `internal/core.RunScenarioManager` for alpha4: it performs startup validation in the exact order required by the [SM startup failure class](../FEATURE.md#configuration-validation-and-failure-classes), connects to NATS and JetStream, reconciles streams and consumers, constructs the experiment informer, the NATS adapters, the selection loop, and the runner-start and observation schedulers, starts them, emits the existing `Scenario Manager is ready` log only after every component has started, blocks on `ctx`, and joins on shutdown. It owns no domain logic; it only constructs and starts the other owned components.

11. `scenario-manager/internal/alpha4/informer/` — the alpha4 experiment informer and lifecycle dispatch. A cluster-wide controller-runtime cache over `experiment-operator/api/alpha4.SimulationExperiment` (no `SCENARIO_MANAGER_WATCH_NAMESPACE` narrowing), with add/update handlers that re-get the live object, require the namespace/name/UID to match the event, close the per-incarnation lifecycle gate, and dispatch `lifecycle.DispatchAction`: `Error`/`Failed` to `lifecycle.RunTerminalAction`, `Completed` to `lifecycle.RunCompletedAction`, and a present `deletionTimestamp` to `lifecycle.RunDeletionCleanup` with precedence over phase. Add handlers register the project (idempotent namespace/name) and install the SM finalizer before registration, then re-get. Failed terminal or cleanup actions retry on the fixed five-second cadence with no backoff or limit. The informer does not write `SimulationExperiment.status`. It is the alpha4 equivalent of `internal/core/simexp_informer.go`.

12. `scenario-manager/internal/alpha4/natsadapter/` — concrete NATS adapters over `nats.go` that implement the three `communication` interfaces plus the EDS-batch JetStream consumer and the Core NATS availability responder:
    - `TranslationRequestPublisher` — publishes on the exact `cbse.<namespace>.<project>.trans.request` subject and returns only after a JetStream PubAck.
    - `EDSAvailabilityResponder` — Core NATS subscribe on `cbse.*.*.eds.scenarios.available`, parse the subject with `subject.ParseIdentity`, validate identity, fetch the experiment, apply `lifecycle.AdmitExperiment`, and reply `ready` with the exact batch subject or `error` with no batch subject.
    - EDS batch consumer — JetStream durable `scenario-manager-eds-consumer`, queue group `scenario-manager-eds`, filter `cbse.*.*.eds.scenarios`, explicit ACK; parse and validate with `communication.ValidateBatchIdentity` and `ValidateBatchReps`, apply the gate, and insert via `persistence.InsertScenarioBatch`.
    - `TranslatorReadyConsumer` — JetStream durable `scenario-manager-translator-ready`, queue group `scenario-manager-translator-ready`, filter `cbse.*.*.trans.*.ready`, explicit ACK; parse and validate subject and payload, apply the gate, and delegate to the `ready` workflow's `TranslatorReadyHandler`.
    The adapters own transport-level ACK/NAK/poison semantics and subject parsing only; all domain decisions belong to `lifecycle`, `communication`, `registry`, `persistence`, and `ready`. This is the package the Slice 07 worker removed as out-of-scope; it is in scope here.

13. `scenario-manager/internal/alpha4/ready/` — the translator-ready handling workflow exposed as a `communication.TranslatorReadyHandler`. For a non-empty image it validates the digest with `registry.ValidateDigestImage`, normalizes and requires the repository to equal `spec.translator.repository` via `registry.RepositoryFromDigest`, and applies `persistence.MarkScenarioStartingRunners`. For an empty image it applies the existing attempt-consuming recovery path (`persistence.MarkScenarioTranslationPublishFailed` → `Created` retry or `Failed` at the limit). A stale translation attempt or an identity mismatch is poison. It returns `TranslatorReadyHandled` (adapter ACKs) or `TranslatorReadyRetry` (adapter NAKs).

14. `scenario-manager/internal/alpha4/selection/` — the alpha4 selection loop (the BSL equivalent) plus the additive selection discovery queries. A single serial worker runs recovery-first: it discovers stale unpublished claims and calls `persistence.RecoverUnpublishedTranslationClaim`, then discovers the next `Created` scenario, claims it with `persistence.ClaimScenarioForTranslation`, re-applies `lifecycle.AdmitExperiment` on the live experiment, calls `persistence.MarkTranslationPublishStarted`, publishes via `TranslationRequestPublisher`, and applies `persistence.MarkScenarioTranslationRequestPublished` on success or `persistence.MarkScenarioTranslationPublishFailed` on failure; a pre-publish gate rejection calls `persistence.CancelUnpublishedTranslationClaim`. Each iteration has a bounded timeout and a fixed delay. The loop does not handle `StartingRunners` (owned by the `runnerstart` scheduler) or `PostProcessing` (a boundary no-op in this branch). The additive discovery queries `NextCreatedScenarioForTranslation` and `NextStaleUnpublishedTranslationClaim` are added to `scenario-manager/internal/alpha4/persistence/` by this slice because no existing package owns them.

## Required behavior

### S06.5-M1 — Startup composition and validation

`app.RunScenarioManager(ctx)` performs startup validation in the exact order and classification of the [SM startup failure class](../FEATURE.md#configuration-validation-and-failure-classes) and fails fast before starting any informer, consumer, selector, or scheduler:

1. `config.RunnerStartWorkers()` — reject a malformed, zero, negative, or greater-than-64 value as a fatal startup error.
2. `messaging.ValidateTemplatesFromEnv()` and `messaging.ValidateStreamNamesFromEnv()` — reject a non-canonical subject template or a non-canonical stream name when a legacy variable is present.
3. `persistence.EnsureSchema(ctx, db)` — reject an incompatible Core DB schema before any business processing starts.
4. `rbac.Verify(ctx, k8s)` — reject a denied required cluster-wide Kubernetes authorization check, reporting the exact verb/resource.
5. Reject a malformed Core DB DSN, a NATS URL containing user information, or a non-empty legacy `SCENARIO_MANAGER_NATS_USER`/`SCENARIO_MANAGER_NATS_PASSWORD`.
6. Connect to NATS through `SCENARIO_MANAGER_NATS_URL` with no credentials, acquire a JetStream context, and call `messaging.ReconcileStreamsAndConsumers(js)` to reconcile the two streams and two SM-owned consumers before any business processing starts.
7. Construct the informer, the four NATS adapters, the selection loop, and the `runnerstart` and `observation` schedulers (with `jobadapter.NewAdapter(k8s)` as both adapters and the worker count from step 1), start them in the order that satisfies every dependency, and only then emit the existing `Scenario Manager is ready` log. The smoke harness continues to use this log as the application-start signal.

A syntactically valid but unavailable NATS server or Kubernetes API is a retryable dependency failure, not a startup configuration error. Shutdown is context-driven: `RunScenarioManager` blocks on `ctx`, then joins every started component that owns a join handle, mirroring `internal/core.RunScenarioManager`.

### S06.5-M2 — Alpha4 experiment informer and lifecycle dispatch

The informer is cluster-wide: it watches `SimulationExperiment` in every namespace and does not read `SCENARIO_MANAGER_WATCH_NAMESPACE`. It uses the alpha4 scheme (`experiment-operator/api/alpha4.AddToScheme`) and built-in Kubernetes schemes, built from an in-cluster REST config.

- On add: for a non-deleting experiment, call `lifecycle.EnsureFinalizer`, re-get the object, and if still non-deleting register the project idempotently with `persistence.RegisterProject(ctx, db, namespace, name)`; if the re-get shows deletion has begun, run deletion cleanup instead and do not register.
- On update: re-get the current object and require namespace, name, and full UID to match the event; a stale event for an old UID neither closes nor cleans a replacement. Close the per-incarnation lifecycle gate synchronously. If `deletionTimestamp` is present, queue only `lifecycle.RunDeletionCleanup` (deletion takes precedence over phase). Otherwise dispatch `lifecycle.DispatchAction`: `Error` or `Failed` to `lifecycle.RunTerminalAction`, `Completed` to `lifecycle.RunCompletedAction`. Do not write `SimulationExperiment.status`.
- On delete: no action; deletion is driven by the `deletionTimestamp` update event while the SM finalizer keeps the object readable. Removing the finalizer in `RunDeletionCleanup` is what allows the delete to complete.

A failed terminal action or deletion cleanup retries on the fixed five-second `lifecycle.RetryCadence` with no exponential backoff and no retry limit; one delayed action cannot block another experiment. The informer shares no per-project unsubscribable state; closing one project's gate does not disrupt another.

### S06.5-M3 — NATS adapters and messaging contract

The four adapters implement the exact alpha4 subject grammar and JetStream consumer contract from [Slice 04](04-sm-messaging-and-lifecycle.md#s04-m2--namespace-aware-messaging-contract). Stream and consumer reconciliation is delegated to `messaging.ReconcileStreamsAndConsumers` at startup; the adapters attach to the reconciled SM-owned durables for EDS batch and Translator-ready, and use a fresh JetStream publish for translation requests. The adapters parse every subject with `subject.ParseIdentity`/`subject.Parse`, validate identity with `subject.ValidateIdent`, and reject a payload `project` that disagrees with the subject token via `communication.ValidateBatchIdentity`.

ACK/NAK/poison semantics follow [Slice 04](04-sm-messaging-and-lifecycle.md#s04-m2--namespace-aware-messaging-contract): an invalid subject shape, invalid tokens, subject/payload disagreement, a batch with a `number_of_reps` outside `1..100000`, or a ready message identifying no matching project is permanent poison — the adapter ACKs the JetStream delivery (or replies `status=error` for availability) and performs no database mutation, attempt consumption, or Job creation. A transient database, Kubernetes lookup, or NATS failure is retryable: the adapter NAKs a JetStream delivery or returns an availability error. The lifecycle gate (`lifecycle.AdmitExperiment` on the fetched experiment) is applied before publishing a translation request, replying to availability, or performing domain processing for an EDS batch or Translator-ready message: only a live, non-deleting `InProgress` experiment is admitted; `Pending`/`Provisioning`/empty phase are unavailable (NAK or availability `error`); `Error`/`Failed`/`Completed` and deletion are terminal (ACK-and-discard, no mutation). The `TranslationRequestPublisher` returns only after a JetStream PubAck so the caller's `MarkScenarioTranslationRequestPublished` reflects a durably accepted message. Two experiments in different namespaces share the two streams and the two SM queue-group consumers while each Translator consumes only its exact request subject.

### S06.5-M4 — Translator-ready workflow

The `ready` workflow implements `communication.TranslatorReadyHandler`. For a non-empty image it validates the digest with `registry.ValidateDigestImage`, resolves the repository with `registry.RepositoryFromDigest`, normalizes it and `spec.translator.repository` with the same OCI reference parser, and requires an exact match; a digest from another repository is permanent poison (ACK, do not persist, do not create a Job). On a match it applies `persistence.MarkScenarioStartingRunners(ctx, db, scenarioID, containerImage)`. For an empty image it applies the existing attempt-consuming path through `persistence.MarkScenarioTranslationPublishFailed` (below `SCENARIO_MANAGER_TRANS_MAX_ATTEMPTS` the row returns to `Created`; at the limit it moves to `Failed`) and never refunds the attempt. A stale translation attempt is poison. The workflow returns `TranslatorReadyHandled` for a terminal semantic outcome (transition, duplicate, or poison) and `TranslatorReadyRetry` for a transient dependency failure; the adapter maps these to ACK and NAK.

### S06.5-M5 — Alpha4 selection loop

The selection loop is one process-local serial worker. Each iteration runs recovery-first: it discovers stale unpublished claims with a new `persistence.NextStaleUnpublishedTranslationClaim(ctx, db, claimedBefore)` query and applies `persistence.RecoverUnpublishedTranslationClaim`; then it discovers the next `Created` scenario with a new `persistence.NextCreatedScenarioForTranslation(ctx, db)` query and, if one exists, claims it with `persistence.ClaimScenarioForTranslation`, re-applies `lifecycle.AdmitExperiment` on the live experiment, calls `persistence.MarkTranslationPublishStarted`, publishes via `TranslationRequestPublisher`, and applies `persistence.MarkScenarioTranslationRequestPublished` on success or `persistence.MarkScenarioTranslationPublishFailed` on failure. A pre-publish gate rejection calls `persistence.CancelUnpublishedTranslationClaim` and does not call NATS. The two new queries are the only persistence additions in this slice; they are additive and covered by focused tests. Each iteration has a bounded timeout (mirroring `internal/core`'s 30s) and a fixed delay (mirroring `internal/core`'s 5s); cancellation and deadline errors are normal workflow control. The loop owns `Created -> Scheduled` only. It must not handle `StartingRunners` (the `runnerstart` scheduler owns `StartingRunners -> InProcessing`) or `PostProcessing` (a boundary no-op in this branch). The loop holds no row lock, queue, leader flag, or cross-replica coordination state; database guarded transitions remain the durable ownership mechanism.

### S06.5-M6 — Runner-start and observation composition

`app.RunScenarioManager` constructs `jobadapter.NewAdapter(k8s)` once and uses it as both the `scheduler.RunnerStartAdapter` and `scheduler.ObservationAdapter`. It constructs `runnerstart.NewScheduler(runnerstart.PersistenceStore{DB}, adapter, runnerstart.Config{Workers: config.RunnerStartWorkers()})` and `observation.NewScheduler(observation.PersistenceStore{DB}, adapter, observation.Config{Workers: 4})` and calls `Start()` on both as part of startup. The schedulers' own discovery/dispatch loops (already implemented by Slice 06) are not modified. Shutdown joins both schedulers. This milestone only wires existing schedulers; it does not change their behavior.

## Failure and retry behavior

Startup configuration failures fail fast in the order and classification of the [SM startup failure class](../FEATURE.md#configuration-validation-and-failure-classes). Runtime dependency failures (NATS, Kubernetes API) are retryable and are not relabeled as startup errors. Poison messages, transient delivery failures, publication ambiguity, terminal actions, and deletion cleanup use the exact classifications and cadences from [Slice 04](04-sm-messaging-and-lifecycle.md#failure-and-retry-behavior): permanent poison is ACKed with no mutation; transient failures NAK or return availability `error`; terminal and cleanup actions retry on the fixed five-second cadence with no backoff or limit.

## Security boundaries

NATS remains authentication-free for alpha4: no user information in URLs, no credential settings, no credential mounts. The adapters use exact subjects, ownership metadata, live UID checks, finalizer sequencing, and ownership verification as correctness boundaries, not broker ACLs. The composition does not introduce new credentials, secrets, or registry access; it reuses the `registry` and `rbac` surfaces already delivered.

## Acceptance tests

### S06.5-A1 — Startup validation and ordering

Test that `RunScenarioManager` fails fast for each startup failure class in isolation — a malformed `SCENARIO_MANAGER_RUNNER_START_WORKERS`, a non-canonical subject template, an incompatible Core DB schema, a denied `rbac.Verify` check, a credential-bearing NATS URL, and a non-empty legacy NATS username/password — and that it reports the exact setting or denied verb/resource before starting any informer, consumer, selector, or scheduler. Verify that the `Scenario Manager is ready` log is emitted only after `messaging.ReconcileStreamsAndConsumers` and every component start succeed. Verify that the informer is cluster-wide and that `SCENARIO_MANAGER_WATCH_NAMESPACE` has no effect on alpha4 subjects or discovery.

### S06.5-A2 — Informer and lifecycle dispatch

Test add (register idempotent namespace/name, `EnsureFinalizer` before registration, re-get, and deletion-before-registration cleanup), update (re-get identity match; `Error`/`Failed` to `RunTerminalAction`; `Completed` to `RunCompletedAction`; `deletionTimestamp` to `RunDeletionCleanup` with precedence over phase), stale-UID rejection, the fixed five-second retry for a failed terminal or cleanup action, and that no handler writes `SimulationExperiment.status`. Verify that closing one project's gate does not disrupt another project.

### S06.5-A3 — NATS adapters and messaging contract

Test the exact subjects and wildcards, that `messaging.ReconcileStreamsAndConsumers` is called at startup, subject/payload mismatch and out-of-range `number_of_reps` poison ACK, availability `ready` with the exact batch subject for an admitted experiment and `error` with no batch subject otherwise, the lifecycle gate before publish/consume, ACK-and-discard for terminal experiments, NAK for unavailable experiments, that `TranslationRequestPublisher` returns only after a PubAck and that `MarkScenarioTranslationRequestPublished` follows it, and that two projects in different namespaces share the two streams and two SM queue-group consumers.

### S06.5-A4 — Selection loop and ready workflow

Test recovery-first ordering, the claim → gate re-check → `MarkTranslationPublishStarted` → publish → `MarkScenarioTranslationRequestPublished` sequence, `CancelUnpublishedTranslationClaim` on a pre-publish gate rejection, the attempt-limit failure path, ready-image digest and repository match, empty-image recovery, stale-attempt poison, that the selection loop does not handle `StartingRunners` or `PostProcessing`, and that shutdown joins every started component.
