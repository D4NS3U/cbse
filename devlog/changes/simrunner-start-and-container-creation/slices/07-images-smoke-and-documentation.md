### Immutable image inputs and repository-built outputs

Every digest below is the platform-specific OCI image-manifest digest, not the digest of a multi-platform image index. ### Smoke registry cleanup

The smoke test components and shared runner base are published under `registry.unibw.de/i31bdase/cbse-test`, the reference Detail DB image under `registry.unibw.de/i31bdase/cbse-test/scenario-detail-database`, and generated runner images only under `registry.unibw.de/i31bdase/cbse-test-runner`. The repositories may be absent on a fresh registry and are then created implicitly by their respective first pushes; existing repositories are supported and the cleanup adapter creates none of them. Each normal shared-image build pushes its canonical tag even if that tag already exists, relying on ordinary registry tag replacement rather than deleting an existing tag or calling a repository-management API. The rendered alpha4 experiment sets `spec.translator.repository` to the exact runner repository, copies the validated `DETAIL_DB_IMAGE` digest to `spec.detailDatabase.image`, sets `spec.translator.registryAuthSecretRef.name` to `cbse-registry-auth`, copies `TRANS_IMAGE` and `RUNNER_BASE_IMAGE` from generated `images.env`, and copies `BUILDER_IMAGE` and `POSTGRES_IMAGE` from the checked-in source lock. The Operator copies that Secret name into the image-based Detail and Result DB Deployment Pod templates as `imagePullSecrets`; only Translator and BuildKit mount the referenced Docker configuration read-only. Translator uses the configured runner base to generate scenario-specific images on demand; there is no prebuilt scenario-specific runner smoke image. The full smoke path uses the reference Translator's basic SimPy generator and rootless Builder sidecar, not the synthetic Translator mock.

The cleanup adapter is part of the shell harness and uses the already-required `curl` and `jq`; no separate registry CLI or credential store is introduced. Its API base URL is `https://registry.unibw.de/api/v2.0`, and it authenticates with the protected basic credentials resolved from the Docker configuration. It lists runner artifacts through `GET /projects/i31bdase/repositories/cbse-test-runner/artifacts`, resolves a tag or digest and reads its digest, tags, and OCI annotations through `GET /projects/i31bdase/repositories/cbse-test-runner/artifacts/<reference>`, and deletes a verified artifact only by digest through `DELETE /projects/i31bdase/repositories/cbse-test-runner/artifacts/<digest>`. Listing must follow Harbor pagination until all artifacts are examined. The adapter must not call Harbor project, project-metadata, or whole-repository deletion or update endpoints, and it does not use the OCI Distribution deletion endpoint. Registry cleanup removes Harbor artifact records and tags; Harbor's later physical blob garbage collection is external to this feature.

The harness records the full experiment UID and every exact runner tag and digest observed during the smoke run. The deterministic `runner-<UID-prefix>-s<scenario-id>-a<attempt>` prefix may discover a push that completed before the harness recorded its digest, but prefix match alone never authorizes deletion. Before deleting any discovered or recorded manifest, the cleanup adapter resolves the tag and digest, reads the manifest, and requires all three framework OCI identity annotations to match the full experiment UID, scenario ID, and attempt encoded by that exact expected tag. A missing or mismatched annotation fails cleanup for that candidate without deleting it. Harbor artifact deletion by digest removes every tag attached to that digest, so the adapter must inspect the complete tag set before deletion. Any attached tag other than the exact expected deterministic runner tag makes the candidate unsafe: cleanup fails for that candidate and must not issue its DELETE request. An artifact with no additional tag may be deleted after its identity checks pass. If both the expected tag and recorded digest are already absent when cleanup begins, that candidate is already clean and counts as success without a DELETE request; absence is therefore idempotent. If only one reference is absent while the other still resolves, the adapter must inspect the remaining artifact and apply the same annotation and complete-tag-set checks rather than treating it as absent. After deletion, the adapter requires both the exact tag and digest to be absent. An unconditional exit trap attempts every verified candidate whether smoke succeeds, fails, or retains Kubernetes resources and never targets `cbse-test`, `cbse-test/scenario-detail-database`, or any shared Operator, SM, Builder, base, PostgreSQL, EDS, or Translator image.

Smoke preflight requires a Kubernetes API server whose parsed `gitVersion` has major version `1` and minor version at least `30`, the built-in cleanup adapter, a readable protected Docker configuration, the `cbse-registry-auth` source Secret, the exact component, reference Detail DB, and runner repository names, at least one qualifying `amd64` Node as defined above, and the exact checked-in source-image lock. It accepts ordinary distribution suffixes and every later minor and applies no upper-version comparison. It rejects an older or unparsable server version, a source-image environment override, or a lock mismatch. A normal smoke run builds and pushes all three repository-owned outputs and validates `TRANS_IMAGE`, `RUNNER_BASE_IMAGE`, and `DETAIL_DB_IMAGE` from current build metadata; a skip-build run instead requires all three explicitly supplied output values and validates their exact repositories and digest forms. All version and image validation happens before cluster or registry mutation. Preflight then sends an authenticated Artifact List request for `i31bdase/cbse-test-runner`. HTTP `200` is accepted when the repository already exists; Harbor repository-not-found HTTP `404` is also accepted before the first generated-runner push because `cbse-test-runner` is intentionally not pre-provisioned. HTTP `401`, `403`, or any other result fails preflight. The accepted initial `404` establishes only that the repository is absent, not that Artifact List is authorized. The first generated-runner push must create the repository, after which the harness requires Artifact List to return `200`; this post-push list and the first annotation-verified cleanup are the authoritative verification of Artifact List, Read, and Delete. A denied list, read, or deletion fails cleanup. Credential material is never a source-code or specification input and is supplied only through the protected runtime sources defined above. Cleanup attempts every candidate even when one deletion fails. Cleanup failure is written to run artifacts without request headers, tokens, credential values, or credential paths and fails an otherwise successful smoke run; on an already-failed run it is reported in addition to the original failure. There is no unresolved external image-digest input: the four source digests are fixed by `test/e2e/images.lock.env`, and the three repository-owned output digests are produced by the build or supplied together for a validated skip-build run. Full feature acceptance remains blocked only until the implementation and mandatory smoke suite pass with the protected registry-auth runtime input.

## Failure and retry behavior

All preflight validation occurs before registry or cluster mutation. The unconditional registry cleanup trap attempts every verified candidate and reports cleanup failure without exposing credentials.

## Security boundaries

Source credentials remain outside the repository, TLS verification is mandatory, cleanup is annotation- and tag-verified, and no shared image repository or Kubernetes shared namespace is deleted.
