# FEATURE.md — Experiment-phase aggregation: `InProgress → Finished | Failed` via field-level ownership

**Foundation:** [notes/component-reports-and-field-ownership.md](notes/component-reports-and-field-ownership.md) — the architectural pattern this feature implements (per-field object ownership; the Status subresource as the component-report channel; Node/Pod/Service precedents). That note is normative background for every worker dispatched under this spec. The scenario-level machinery this builds on (terminal scenario states, verdict application, the evaluation loop) is landed and cluster-proven per the [post-processing-service feature record](../post-processing-service/IMPLEMENTATION_HANDOFF.md).
**Normative for every worker dispatched under it. Read-only for workers.** On contradiction between this spec and live code that repository inspection cannot resolve: stop and ask via the ask channel.

## 1. Title and mission

The `SimulationExperiment` custom resource gains its terminal phases. Today the Experiment Operator writes exactly one phase, `InProgress` (controller:831 `patchPhase`; the single literal `alpha4PhaseInProgress`), and the experiment never terminates — "terminality" exists only as the Scenario Manager's deletion-cleanup action. This feature closes the loop's last level, using exactly the methodology of the design note: **the SimulationExperiment becomes a multi-writer object in the sense of the Node** —

- the **Scenario Manager** — the only component that knows scenario outcomes (its Core Database, which no other component reads) — owns and writes one new status field: `status.scenarioManagerVerdict`, holding the verdict value (`Finished` | `Failed`);
- the **Experiment Operator** — the CR's owning controller — reads that report, derives, and exclusively owns `status.phase`, transitioning the experiment to **`Finished`** when every scenario finished, or **`Failed`** when any scenario failed, with terminal stickiness (a terminal phase never regresses to `InProgress`).

Judgment is delegated (the SM reports the ground truth); authority is retained (the operator alone writes its phase) — the same discipline the PPS verdict flow established one level down. **Ruling (2026-09-30, revised): both branches are implemented** — the SM writes `Failed` as soon as any scenario fails (fail-fast), and `Finished` when every scenario finished successfully. Both writes are absorbing and mutually exclusive (a failure before completion pre-empts `Finished`; nothing can fail after all-Finished), so the field remains monotone and staleness-free.

**The existing phase machine (verified 2026-09-30):** the operator already implements `Pending → Provisioning → InProgress` with `Error` as its failure terminal — `validateExperiment` failure moves the experiment to `Error` *before any component is created*; `provisionComponents` failure moves it to `Error` with partial children; the reconcile's phase switch **parks** on `InProgress` and `Error` ("not Operator-owned beyond provisioning" — the code's own comment). `Error` is absolutely sticky today (recovery = delete + recreate). This feature adds exactly two verdict-derived terminals — `Finished`/`Failed` — completing the five-phase vocabulary, and they inherit the existing park semantics rather than inventing a new stickiness flavor.

## 2. Scope

- **In scope:** (a) the alpha4 API surface — an additive, optional `scenarioManagerVerdict` string field (enum: `Finished` | `Failed`) with documented field ownership; (b) the SM's aggregation pass — a scheduler-cadence pass mirroring the existing SM passes: per admitted experiment, an SQL aggregation over `scenario_status`; **fail-fast**: any scenario in the `Failed` state → write `Failed`; else if **total > 0 and every scenario is `Finished`** → write `Finished`; idempotent status patches; plus the RBAC delta (`simulationexperiments/status` `patch` in the stack Role and the `rbac.Verify` startup checks); (c) the operator's derive branch — value validation, `patchPhase` to `Finished`/`Failed`, stickiness, and a Kubernetes Event on the transition; (d) an e2e smoke spec proving the live Finished chain: all scenarios `Finished` → `status.scenarioManagerVerdict == "Finished"` → experiment phase `Finished` (the Failed derivation is proven at envtest level; the live failure-chain e2e is a future increment — see D10).
- **Out of scope:** any change to the landed scenario-level machinery (states, rounds, verdict application, the evaluation loop); any NATS surface (none — the report channel is the CR itself); the annotation/child-CR/NATS alternatives (rejected in the design note §6); the **live failure-chain e2e** (a deterministically failing scenario driving `stop_unmet → scenario Failed → verdict Failed → phase Failed` on the cluster — a future increment; the Failed *derivation* is proven at envtest level in this feature); experiment deletion or retry semantics; any new component image (the set stays seven).
- **Breaking changes / compatibility:** the status field is additive and optional (string with `omitempty`) — served alpha4, no conversion, old objects lack it harmlessly; the CRD schema regeneration is additive (enum validation: `Finished` | `Failed`); `zz_generated.deepcopy.go` and the CRD yaml regenerate via the repo's `controller-gen` flow (`make verify-generated` proves byte-stable generation). The smoke's `InProgress` spec is unaffected. Field ownership (SM owns `scenarioManagerVerdict`; operator owns `phase`/`message`) is enforced by convention + RBAC + API comments, per the design note §4. **Optionality semantics (ruling 2026-09-30):** `omitempty` here is purely temporal-schema: the field is **absent until the SM writes its first verdict** — absence means *not yet reported* (or, for zero-scenario experiments under D3, never), **never** an opt-out or an alternative phase-transition path. Status fields are never user input (the enabled status subresource discards user-supplied status on create/update); the report is **the sole mechanism** of the terminal phase transition (D1).
- **Compatibility boundaries:** Kubernetes >= 1.30; alpha4-only API; merge-patch disjointness makes the two writers conflict-free by construction (the operator's patch carries only `phase`/`message`; the SM's only `scenarioManagerVerdict`).

## 3. Workflow decisions (concern → decision)

| # | Concern | Decision for this feature |
|---|---|---|
| D1 | The report channel | **The Status subresource, per the design note** — a dedicated, SM-owned `status.scenarioManagerVerdict` field; the operator derives `phase` from it. Ruled by the user's methodology choice ("this exact phase transition methodology"). The annotation handshake is documented as the pragmatic cousin and is NOT used. |
| D2 | Report shape | **A plain string enum** — `scenarioManagerVerdict: "Finished" | "Failed"` — the minimal shape that carries exactly what the SM knows and the ExOp needs (ruling 2026-09-30, closing Q1: no `metav1.Condition` list — array-merge mechanics between two writers outweigh the standardized rendering; no struct — the counts and generation stamp of the earlier draft were observability garnish the verdict does not need; typed data fields would follow the same ownership discipline if a future report grows richer). The field's absence is the *pre-verdict* temporal state (see §2). |
| D3 | Aggregation rule (both branches, ruling 2026-09-30 revised) | Per admitted experiment, per pass: if the verdict is already written → no-op (absorbing). Else if **any scenario's state is `Failed`** → write `Failed` (**fail-fast** — the experiment's failure is decided by the first failing scenario; remaining scenarios continue but cannot change the verdict). Else if **total > 0 and every scenario's state is `Finished`** → write `Finished`. Else → no verdict yet. An experiment with zero scenarios never aggregates. The two writes are mutually exclusive and each absorbing, so the field stays monotone. |
| D4 | Value validation | The operator trusts a report **only if** the value is a known verdict: `Finished` or `Failed` (both implemented; unknown values ignored for forward compatibility). No generation gate is needed: both reported conditions are absorbing — once written, the verdict stays true for the life of the object, and a new object starts with empty status — so staleness is structurally impossible. |
| D5 | Drive mechanism (SM) | **A scheduler-cadence aggregation pass** mirroring the existing SM passes (runner-start, observation, evaluation publication): per **admitted** experiment — and admission is gated by the landed `AdmitExperiment` gate, which admits **only `InProgress`** experiments (Pending/Provisioning/"" → `AdmitUnavailable`; terminal phases → `AdmitTerminal`; unknown → conservatively terminal; verified 2026-09-30) — one SQL aggregation; the D3 rule; **write-if-absent** (the verdict is absorbing — once written it never changes); no post-transition hooks — the verdict handler stays untouched; the pass is idempotent and self-healing; latency is one cadence tick. **The gate makes the provisioning race structurally impossible** (user-verified 2026-09-30): no scenario flow exists for a Pending/Provisioning experiment, so no verdict can ever precede `InProgress`. |
| D6 | Derive + stickiness (ExOp) | The reconcile's phase switch gains an explicit `InProgress` case (today it falls into the parked default): read `scenarioManagerVerdict` — `Finished` → `patchPhase("Finished", message)`; `Failed` → `patchPhase("Failed", message)`; unknown values ignored (D4) — then **park** (return without requeue, exactly like every non-provisioning phase today). New literals `alpha4PhaseFinished`/`alpha4PhaseFailed`. **Stickiness is inherited, not invented:** terminal phases park in the switch's default case exactly as `InProgress` and `Error` do today — `Error`'s existing absolute stickiness (recovery = delete + recreate) is the precedent the terminals follow; no generation-scoped recovery is introduced. **Report-only semantics, corrected to the park architecture (ruled 2026-09-30):** on any terminal phase the operator's complete action set is the phase+message patch and (Q4) the Event — **nothing else by design**: no scenario interference (the SM owns runner Jobs), no teardown, no retries, no auto-cleanup, and *no child healing* — the operator parks beyond provisioning per its existing architecture; children persist unhealed and results are preserved for inspection until the user deletes the experiment (the GC cascade). Future-increment slots recorded, not built: TTL-style auto-cleanup policies; the inverse ExOp→SM signal if remaining scenarios should ever stop on a `Failed` experiment. |
| D7 | Observability | The operator emits a Kubernetes **Event** on the terminal transition (`kubectl describe` visibility — the design note's "garnish"). The SM logs its report writes in its established `operation=` style. |
| D8 | RBAC | The SM's stack ClusterRole (`test/e2e/manifests/base/stack.yaml`) and the `rbac.Verify` startup checks (`scenario-manager/internal/rbac/rbac.go:83-86`) gain `simulationexperiments/status` `patch`. A denied check remains a fatal startup error (existing semantics). |
| D9 | Ownership partition | Documented in the API type comments: `scenarioManagerVerdict` — *"written by the Scenario Manager; consumed by the Experiment Operator"*; `phase`/`message` — owned by the operator. The two writers' merge patches are field-disjoint by construction. |
| D10 | e2e scope | The smoke proves the **Finished** path live (all four scenarios Finished → verdict `Finished` → experiment phase `Finished`). The **Failed derivation** is proven at the operator's envtest level (a synthetic `scenarioManagerVerdict: "Failed"` → phase `Failed` + stickiness). The **live failure-chain e2e** (a deterministically failing scenario: tiny ε + capped replications → `stop_unmet` → scenario `Failed` → verdict `Failed` → phase `Failed` on the cluster) is a future increment — the experiment-wide `-max-replications` cap couples all scenarios of one experiment, so a clean live failure profile needs its own design pass (a second experiment profile or careful cap tuning); recorded as the follow-up. |
| D11 | Terminal-vocabulary alignment (SM gate) | The landed `AdmitExperiment` gate pre-defines the terminal vocabulary as `Error \| Failed \| Completed` (`scenario-manager/internal/lifecycle/lifecycle.go:62-67`) — but no writer of `Completed` ever existed, and this feature's ruled success-terminal is **`Finished`**. The gate's constant aligns: `PhaseCompleted = "Completed"` → `PhaseFinished = "Finished"` (constant, gate switch case, tests, doc comments). Zero behavior change today (the case was never exercised); the SM then **explicitly** recognizes the operator's success-terminal instead of falling into the conservative unknown-phase default, and once the operator writes `Finished` the informer drops the experiment from the admitted set — the pass stops iterating it, which is exactly correct for an absorbing verdict. **User-confirmed 2026-09-30 (implementation go).** |
| D12 | CRD `phase` vocabulary (dispatch-prep amendment 2026-09-30) | The `Phase` field's enum marker (`Pending;Provisioning;InProgress;Completed;Failed;Error`) gains **`Finished`** — additively — so P3's `patchPhase("Finished", …)` passes API-server schema validation (without it the terminal status patch is enum-rejected). The never-written `Completed` value **stays**: removing it would be a schema breaking change, violating §2's additive rule; the status doc comment lists the full vocabulary. The `scenarioManagerVerdict` field carries its own enum (`Finished;Failed`). |

## 4. Design patterns (Gang of Four)

| # | Concern | Pattern | Concrete application | Why the simpler composition is not enough |
|---|---|---|---|---|
| 1 | SM reports; operator consumes | **Observer** | The CR's Status is the blackboard: the SM writes its slice; the operator's existing watch delivers the report as a reconcile trigger — no direct coupling, no new transport | A direct call would couple the SM to the operator's liveness and bypass the owner's reconcile; the report must survive component gaps and trigger exactly the owner's existing machinery |
| 2 | The experiment's phase machine gains terminal states | **State** | `InProgress → Finished \| Failed` as absorbing states with stickiness (D6); `patchPhase` is the only transition edge | Two writers on one object require absorbing terminal semantics — without stickiness, the operator's periodic reconcile would fight the terminal phase |
| 3 | The SM's aggregation pass | **Template Method** | The new pass reuses the established scheduler-pass skeleton (per-tick scan → gate → guarded idempotent action → no-op), like runner-start/observation/evaluation publication | A bespoke one-off loop would drift from the proven pass discipline (bounded cadence, no hot loops, idempotent no-ops) and lose its test shape |

*Deliberately not used:* Mediator (the CR itself mediates — field-level ownership makes the shared blackboard safe), Strategy (the aggregation rule is fixed policy, not an interchangeable algorithm), any speculative pattern without a requirement row.

## 5. Global constraints (per worker, verbatim discipline)

- **Obey `AGENTS.md`.** `make test-fast` after every Go/CRD change; `make test-smoke` additionally after operator-reconciliation, API/CRD, or SM integration changes (the settlement smoke is the manager's consolidated gate per the standing serialized-worker policy).

- **Scope discipline:** exactly the slice's ownership partition; no unrelated cleanup; discovered gaps stop-and-ask.
- **Test integrity:** never weaken, delete, skip, or rewrite a test to conceal a failure; the e2e suite grows a spec, none is modified beyond what a slice names.
- **Field ownership is the contract:** the SM never writes `phase`/`message`; the operator never writes `scenarioManagerVerdict` — enforced per D9.
- **Secrets hygiene; verification honesty; runtime attestation** (`printf '%s/%s\n' "$PI_PROVIDER" "$PI_MODEL"` at the first checkpoint, expected `ai.forge/qwen3.8-27b-nvfp4`, mismatch → stop and report failed) **; no commits; read-only specs.**

Implementation workers may commit **to that branch only** (never `main`), every commit carrying the traceability trailer `[orchestration: task <task-id> dispatch <dispatch-id>]`; the merge to `main` is **one user-approved event at settlement** (the regenerated CRD manifests are protected paths). Spec and devlog documents remain manager-authored on `main`; specs stay read-only for workers.
- **Serialization policy:** one dispatched worker at a time (standing provider constraint — the LAPI/CrowdSec incidents).
