# FEATURE.md — Experiment-terminal-e2e: live proof of the `Error` and `Failed` terminal branches

**Foundation:** [notes/terminal-paths-and-triggers.md](notes/terminal-paths-and-triggers.md) — the code-verified route analysis (the two Error flavors, the readiness park contract, the three scenario-Failed writers, the cap semantics). That note is normative background for every worker dispatched under this spec. The terminal phase machine itself is landed and cluster-proven (experiment-phase-aggregation, merged `c993078`).
**Normative for every worker dispatched under it. Read-only for workers.** On contradiction between this spec and live code that repository inspection cannot resolve: stop and ask via the ask channel.

## 1. Title and mission

The landed terminal phase machine is proven live only for the `Finished` chain (the 7th smoke spec). This feature proves the remaining terminal branches live on the cluster, in the same harness discipline: **both `Error` flavors** (user ruling 2026-10-01) — the Validation-Error (pre-creation gate, zero children) and the Provisioning-Error (mid-sequence failure, partial children persist) — and, pending ruling F1, the **`Failed` chain** (a deterministically failing scenario → `stop_unmet` → verdict `Failed` → phase `Failed`). The operator's contracts under test are the ones the recon verified: the validation gate, the fixed provisioning order, the absorbing stickiness, the report-only persistence of partial children, and the GC cascade over them on user deletion.

## 2. Scope

- **In scope:** (a) e2e specs creating red experiments in the smoke namespace (spec-created CRs via the suite's `k8sClient`; the operator is multi-experiment by design); (b) pending F1: the `PostProcessingSpec.MaxReplications` CR field and the PPS `-max-replications` arg wiring (API surface + CRD regen + validation + envtest); (c) pending F1/M: the eds-mock red-batch capability (project-name-keyed, env-driven).
- **Out of scope:** any change to the landed terminal phase machine (the derive, the stickiness, the aggregate pass); the green experiment's profile (the 2×2 batch, fleet sizes, ε values stay exactly as landed); the harness's cluster/registry machinery; **EDS provisioning — the required-but-inert `experimentalDesignService` field stays as-is per the user ruling 2026-10-01; the EDS reference component (template image + `reconcileEDS`) is ruled the next feature after this one** (the finding and disposition are documented in the design note).
- **Breaking changes / compatibility:** the (pending) `MaxReplications` field is additive and optional (absent = the PPS flag default, 10000) — old objects are unaffected; the CRD regen is additive; the mock change is test-infrastructure only.

## 3. Workflow decisions (concern → decision)

| # | Concern | Decision for this feature |
|---|---|---|
| D1 | The Error coverage | **Three flavors are tested (user rulings 2026-10-01).** Flavor 1 — Validation-Error: a red experiment with a non-digest `translator.image` → `Error` before any component exists; assert phase+message, stickiness, and **zero children**. Flavor 2 — Provisioning-Error, creation variant: a blocker Service holds a NodePort, the red experiment's PPS requests it → API-server rejection mid-sequence → `Error` with the databases + translator + their Services/Secrets already present; assert phase+message, stickiness, **the partial children persist** (report-only semantics), and the GC cascade over the partial set on deletion. Flavor 3 — Provisioning-Error, readiness variant (the watchdog, T2): a well-formed, digest-pinned, **nonexistent translator image** (the translator is in the readiness gate; the PPS is not — a nonexistent PPS image would stall at the scenario level instead) → the Deployment creates, the pull fails observably, the watchdog collects the inventory across three retries → `Error` with the per-retry aggregation as the message; assert phase+message (naming the component and its failure), stickiness, and the full-but-not-ready child set. |
| D2 | Red experiments' placement | Spec-created CRs in the smoke namespace alongside the green experiment — the multi-experiment SM (cluster-wide listing, per-project subjects) already serves this shape; no harness changes to the green profile. |
| D3 | The readiness watchdog (ruling R) | **Provisioning does not go on indefinitely (user rulings E2-exception + R, 2026-10-01): an operator-level bounded-retry watchdog.** Creation failures → `Error` immediately (already the code's behavior). Readiness: **three retries allowed**; each evaluation collects the not-ready component inventory (component + observed failure: probe error, absent Deployment, `0/1` ready, pod failure reason where available); the third still-not-ready retry transitions the experiment to **`Error` without further retry**, the final message aggregating the per-retry inventories (the concrete cause: the component(s) that did not become ready and their failures at each retry). Parameters: watchdog evaluations spaced ~60s (the 5s requeue cadence would false-Error the green experiment, which readies <90s observed); counter + inventories in-memory keyed by UID (operator restart resets the budget — documented; no API surface change); the readiness set extends to the **PPS** (ruling G, 2026-10-01: the gate checks the two DBs' probes + the translator's **and the PPS's** `ReadyReplicas` — the `InProgress` message "All components provisioned and ready" becomes true, and a broken PPS converts from a silent scenario-level stall into a bounded, diagnosed `Error`). Scenario-level response deadlines remain absent. Implemented as slice T2. |
| D4 | The Failed coverage | **One route: F-crash (user ruling revised 2026-10-01 — the spec's subject is the Failed phase transition; how a scenario fails is not relevant, so a single deterministic route suffices).** F-crash — the operational path, zero platform change: the red batch carries a recipe whose simulation exits nonzero → the runner Job exhausts its backoff (`globalBackoffLimit = 4`, ≈3–4 min) → `JobFailed` → `ObservationFailed` → the guarded `InProcessing → Failed` → verdict `Failed` (fail-fast) → phase `Failed` (+ Event, sticky). The earlier both-routes ruling is superseded: **F1 (`stop_unmet` via the `MaxReplications` CR wiring) is dropped from this feature** — the cap wiring's platform merit (the CR as the user surface of the PPS's "user-defined maximum") is recorded to the backlog as its own potential feature. The design note's fault model stands: observed failures route to `Failed`; silent faults stall by design. |
| D5 | The red profile's richness | **Ruled (2026-10-01): one scenario per red experiment.** The F-crash experiment carries exactly the crashing scenario — the spec's subject is the Failed *phase transition*, and how the failure comes to pass is not relevant to it; the fail-fast/absorbing timing proofs (the sibling shape) are dropped per the ruling. The F1 experiment likewise carries one scenario (the loop profile). |
| D6 | The red batch source | **Open ruling M.** The eds-mock serves a red batch keyed by the project-name convention (a licensed-mock extension, env-driven, zero operator changes) — versus env plumbing through the EDS spec (more machinery for a mock). |
| D7 | Observability | Each spec persists its terminal evidence (phase, message, verdict, the partial-children inventory) to the artifact directory per the suite's triage discipline. |

## 4. Design patterns (Gang of Four)

| # | Concern | Pattern | Concrete application | Why the simpler composition is not enough |
|---|---|---|---|---|
| 1 | Red experiments in the shared namespace | **Builder** | Each spec assembles its red CR from the green experiment's spec (same databases/translator/PPS contracts) with exactly the one red delta (image, nodePort, or cap) | Hand-written full CRs would drift from the real spec shape and test configuration accidents rather than the intended failure |
| 2 | The NodePort blocker | **Fixture setup** (test-side) | The spec creates the blocker Service before the red CR and removes it in teardown | The conflict must pre-exist the provisioning attempt to be deterministic; the operator's own machinery stays untouched |

*Deliberately not used:* no mocking of the operator or SM (the point is the live behavior); no test doubles for the API server (envtest already covers unit-level; the cluster's real rejection semantics are the subject).
