# Deterministic Random Streams in CBSE

## Human-readable thesis background and design explanation

> **Document purpose:** This text explains the random-stream problem and the
> proposed CBSE solution in a narrative form intended for thesis work and human
> review. It is not the normative implementation specification. The normative
> engineering design is maintained in [`FEATURE.md`](FEATURE.md).
>
> **Maintenance rule:** This document should be updated whenever the accepted
> seed derivation, component responsibilities, runtime contract, persistence
> model, or replay behavior changes. Statements about the current implementation
> and statements about the proposed design must remain clearly separated.

## 1. Why random-number handling matters

A discrete-event simulation appears to be random because it repeatedly samples
values such as interarrival times, service durations, component failures,
customer patience, or routing decisions. In software, however, these values are
usually generated by a deterministic pseudo-random number generator. The
sequence produced by such a generator is determined by its initial state, which
is commonly initialized from a seed.

This has two important consequences.

First, separate simulation replications need different random-number streams.
If every replication used the same seed, they would usually produce the same
sequence and therefore would not be statistically independent observations.
Running the same replication thirty times would then add no information.

Second, the seed and random-number algorithm form part of the scientific
provenance. If the same model, parameters, software environment, and random
stream are used again, the simulation should be able to reproduce the same
result. If the seed is unknown or tied to an ephemeral infrastructure detail,
exact computational replay becomes difficult even when the model itself has not
changed.

CBSE therefore needs to satisfy two goals that may initially appear to conflict:

1. each logical replication should receive a distinct stream; and
2. that stream should remain stable and reconstructible when the logical
   replication is retried or replayed.

A deterministic stream-allocation scheme satisfies both goals. “Deterministic”
does not mean that all replications receive the same values. It means that the
mapping from a logical replication to its random stream is explicit and stable.

## 2. How CBSE currently executes replications

A CBSE experiment consists of one or more scenarios. A scenario describes a
specific model configuration, for example a queue with a particular arrival
rate, service rate, and run duration. The Experimental Design Service supplies
those scenarios and the requested initial number of replications.

The relevant execution flow is:

1. **Experimental Design Service (EDS):** defines scenarios and their initial
   replication counts.
2. **Translator:** translates a scenario into an immutable simulation-runner
   container image. The generated image contains the model runner and the
   scenario-specific model parameters.
3. **Scenario Manager (SM):** creates a Kubernetes Indexed Job for the scenario.
4. **Kubernetes:** creates one runner Pod for every Job completion index.
5. **Runner containers:** execute isolated model replications and write their
   results to the Result Database.
6. **Post-Processing Service (PPS):** evaluates all results currently available
   for the scenario. If the confidence interval is still too wide, PPS requests
   another wave of replications.
7. **Scenario Manager:** starts a new round-specific Indexed Job containing only
   the additional replications requested by PPS.

The containers do not share memory and do not need to communicate while
sampling random values. This isolation is desirable: each replication can run
independently, and Kubernetes can schedule the Pods in parallel.

## 3. The current seed mechanism

The current reference runner does not use wall-clock time as its seed. Instead,
it combines two values:

- the scenario's `seed_policy`; and
- the runtime container hostname, which normally corresponds to the Kubernetes
  Pod name.

The effective seed is derived as follows:

```text
effective_seed = first 63 bits of SHA-256(seed_policy + ":" + pod_hostname)
```

The runner then initializes a local Python generator:

```python
rng = random.Random(effective_seed)
```

The effective seed is included in the result written by the runner. This is an
important existing strength: after a successful replication, CBSE can inspect
which effective seed was used.

Because different Pods normally have different names, they normally receive
different effective seeds. The mechanism therefore avoids the obvious error of
starting every parallel replication with the same seed.

## 4. Why additional PPS rounds do not normally repeat the first wave

A natural concern is that Indexed Job completion indices restart at zero for
each new Job. Suppose the first Job executes thirty replications and PPS asks
for forty additional replications. The second Job will again use completion
indices beginning at zero. If the index alone determined the seed, indices 0 to
29 would repeat.

That specific problem is currently avoided because Scenario Manager gives each
runner round a different Job name. A simplified example is:

```text
round 1: simrun-<experiment>-s7-a1
round 2: simrun-<experiment>-s7-a1-r2
round 3: simrun-<experiment>-s7-a1-r3
```

Kubernetes derives Pod identities from the Job identity. A Pod in round 2
therefore has a different hostname from the Pod at the corresponding completion
index in round 1. Since the hostname is part of the current seed derivation, the
rounds receive different effective seeds.

It is also important that the second Job contains forty *additional*
replications. It does not rerun the original thirty and add ten more. PPS and
Scenario Manager maintain a cumulative count across rounds while each Job's
completion count describes only the current wave.

The current design therefore does not normally duplicate seeds merely because
completion indices restart in the next runner round.

## 5. The actual weakness: Pod identity is not replication identity

Although distinct round-specific Pod names avoid the immediate collision, the
underlying design still connects statistical randomness to Kubernetes
infrastructure identity.

A Pod name describes one execution attempt. It does not describe the scientific
replication that the Pod is intended to compute.

This distinction becomes visible in two situations.

### 5.1 Infrastructure retries

Suppose Kubernetes starts the Pod responsible for completion index 7. If that
Pod fails and Kubernetes creates a replacement, the replacement may receive a
different Pod name. Under the hostname-derived scheme, it then receives a
different effective seed.

Statistically, however, it is still supposed to be completion index 7. The
infrastructure is retrying the same logical unit of work, but the model may
silently execute a new random stream.

### 5.2 Experiment recreation

If a completed experiment is created again, Kubernetes generates new Jobs and
Pods. Even when the model parameters and `seed_policy` are identical, the Pod
hostnames differ. The recreated experiment therefore uses different streams.

The old effective seeds can be read from the previous results, but the normal
production runner has no input through which those seeds can be supplied to the
new Pods. The system knows the streams afterward but cannot reconstruct them in
advance through the standard orchestration path.

The core design problem can therefore be stated as follows:

> CBSE currently derives statistical stream identity from transient
> orchestration identity.

For reliable replay, the relationship should be reversed. A logical replication
should have a stable statistical identity, while any Pod executing that
replication should receive the stream assigned to that identity.

## 6. The proposed deterministic stream descriptor

The proposed solution assigns every logical replication a stream descriptor
constructed from explicit experimental coordinates. The descriptor contains:

1. an experiment root seed;
2. a stable scenario stream identifier;
3. a global replication index; and
4. a versioned seed-derivation algorithm.

Conceptually:

```text
stream descriptor =
    (root seed, scenario stream ID, replication index, derivation version)
```

The effective seed is a deterministic function of this descriptor:

```text
effective seed = derive(stream descriptor)
```

Pod name, hostname, node name, scheduling order, start time, and wall-clock time
are intentionally absent.

## 7. Experiment root seed

The root seed identifies the experiment's overall randomization. It may be
provided explicitly by the user or generated once by the control plane.

A fixed mode could look conceptually like:

```yaml
randomness:
  mode: fixed
  rootSeed: 123456789
  derivation: cbse-v1
```

A generated mode could look like:

```yaml
randomness:
  mode: generated
  derivation: cbse-v1
```

In generated mode, CBSE must generate the value exactly once and persist it
before any runner starts. Otherwise a controller restart could change the root
seed halfway through an experiment.

The root seed is not a password. It is scientific provenance and should be
exported with the experiment results. A researcher who wants to reproduce the
same streams must be able to reuse it.

The final API location remains a design decision. It could be part of the
`SimulationExperiment` resource, the experimental design, or a dedicated
experiment configuration. Regardless of location, it must be durable,
immutable once execution starts, and available to Scenario Manager.

## 8. Stable scenario stream identifier

The root seed alone is insufficient because an experiment can contain several
scenarios. Each scenario needs a stable stream namespace.

For example:

```text
baseline-lambda-4-mu-5
high-load-lambda-8-mu-5
```

This identifier should express the scenario's scientific role rather than its
current database row number. Database IDs may change when an experiment is
created again.

A scenario stream ID could be supplied by the user or generated
deterministically by EDS. It should be persisted in Core DB and included in the
exported experiment design.

An explicit stream identifier also supports an important statistical choice.
Two scenarios with the same parameter values may need independent streams, or
they may intentionally share related streams as part of a common-random-number
design. That relationship should be declared rather than occurring accidentally
because two internal IDs happen to match.

## 9. Global replication index across multiple waves

Every scenario replication needs an ordinal that remains stable across PPS
waves. Scenario Manager already knows how many replications were completed
before it starts another round.

For each round it can supply:

```text
replication_offset = number of replications completed before this round
```

Kubernetes supplies the completion index within the current Indexed Job:

```text
completion_index = index within the current round
```

The global replication index is:

```text
global_replication_index = replication_offset + completion_index
```

For the example of thirty initial and forty additional replications:

| Round | Replications completed before the round | Current Job indices | Global replication indices |
|---:|---:|---:|---:|
| 1 | 0 | 0–29 | 0–29 |
| 2 | 30 | 0–39 | 30–69 |

If PPS later requests ten more:

| Round | Replications completed before the round | Current Job indices | Global replication indices |
|---:|---:|---:|---:|
| 3 | 70 | 0–9 | 70–79 |

This provides **wave-partition invariance**. Seventy replications executed in
one Job receive the same logical indices 0 to 69 as seventy replications
executed as a first wave of thirty and a second wave of forty. The precision
stopping behavior can alter when work is scheduled without changing which
streams correspond to the first seventy observations.

## 10. Versioned seed derivation

A concrete derivation must convert the root seed, scenario stream ID, and global
replication index into a seed accepted by the runner's RNG.

A possible first contract is:

```text
effective_seed = first 63 bits of HMAC-SHA-256(
    key     = encoded root_seed,
    message = "cbse-v1:" + scenario_stream_id + ":" + global_replication_index
)
```

HMAC is useful here as a deterministic pseudorandom function. Nearby replication
indices do not produce visibly related integer seeds, and the root seed acts as
the derivation key.

The exact contract must specify more than the algorithm name. It must define:

- how integers are encoded;
- whether text is UTF-8;
- how fields are separated or length-prefixed;
- byte order;
- which hash bytes are retained;
- how the result is converted to an integer;
- the permitted ranges of all inputs.

These details should be protected by published test vectors. A Go, Python, R,
or Java implementation should derive the same effective seed from the same
descriptor.

The version name is equally important. Once `cbse-v1` has produced scientific
results, its behavior must not be changed. An improved future derivation becomes
`cbse-v2` rather than silently modifying old experiments.

## 11. Why Scenario Manager and Translator share responsibility

It is tempting to place all randomization logic either in Scenario Manager or
in the user-provided Translator. Neither option is sufficient on its own.

### Scenario Manager's role

Scenario Manager knows the runtime structure of the experiment. It knows the
current scenario, runner round, cumulative completed count, and current Job. It
can expose the Indexed Job completion index to the runner and can calculate the
replication offset.

It is therefore the correct component to establish **which logical replication
is running**.

Scenario Manager should inject a framework-owned runtime contract, conceptually
including:

```text
CBSE_RANDOMNESS_CONTRACT=cbse-v1
CBSE_ROOT_SEED=123456789
CBSE_SCENARIO_STREAM_ID=baseline-lambda-4-mu-5
CBSE_REPLICATION_OFFSET=30
CBSE_COMPLETION_INDEX=7
```

The exact representation may use environment variables, a mounted file, or
both. Environment-variable names should be reserved so a custom Job template
cannot override framework-owned values.

### Translator's role

The Translator knows the user model and its programming environment. It knows
whether the model expects Python's `random.Random`, a NumPy `Generator`, an R
RNG, a Java generator, or several separate stochastic inputs.

It is therefore the correct component to establish **how the assigned stream is
consumed by the model**.

The generated runner reads the CBSE stream coordinates, applies the versioned
derivation, initializes a local RNG, and passes that RNG to the model. A custom
Translator may choose a model-appropriate RNG while still respecting the
framework's logical replication identity.

### Why the split is useful

The framework remains independent of a specific simulation language or RNG
library, while user models cannot accidentally redefine which replication they
are executing. Scenario Manager supplies identity; Translator supplies model
integration.

## 12. Stable behavior during Pod retries

Consider round 2 with an offset of 30. The Pod for completion index 7 represents
global replication 37:

```text
30 + 7 = 37
```

If Kubernetes replaces that Pod, the replacement still receives offset 30 and
completion index 7. It therefore reconstructs the same stream descriptor:

```text
(root seed, scenario stream ID, replication 37, cbse-v1)
```

The effective seed remains identical even though the Pod hostname changes.
The infrastructure retry now matches the statistical meaning: it retries the
same replication.

This also reveals a storage requirement. If the first Pod wrote its result but
failed before Kubernetes recorded successful completion, the replacement might
write the same logical result again. Result insertion should therefore be
idempotent by stable replication identity. A uniqueness key could contain:

```text
(scenario stream ID, global replication index)
```

or an equivalent experiment-scoped identifier. A retry must not cause PPS to
count one replication twice.

## 13. Local RNGs remain preferable to a central RNG service

The deterministic design does not require a shared service that sends random
numbers to every runner. Such a service would introduce several problems:

- results could depend on the order in which concurrent Pods request numbers;
- network retries could consume values twice or skip values;
- the service would become a throughput bottleneck;
- a service failure could block every simulation;
- exact replay of a concurrent request order would be difficult;
- model-specific random distributions would become harder to support.

Independent local generators avoid these problems. The framework only needs to
ensure that each local generator starts from the correct deterministic stream.

## 14. Choice of random-number generator

The initial reference implementation may continue to initialize Python's
standard generator from the effective seed:

```python
rng = random.Random(effective_seed)
```

That is simple and compatible with the existing reference model. It should not
necessarily be the only supported choice.

Models with stronger statistical requirements may use generators with explicit
stream splitting, jumping, or counter-based construction, such as PCG variants
or Philox. A NumPy-based runner might use:

```python
rng = numpy.random.Generator(
    numpy.random.PCG64DXSM(effective_seed)
)
```

Hashing distinct replication identities into distinct seeds makes accidental
seed equality extremely unlikely. It does not mathematically prove that the
resulting generator subsequences never overlap. The appropriate guarantee
therefore depends on the selected RNG. CBSE should record the RNG algorithm and
software environment, allowing a thesis or result bundle to state exactly what
was used.

## 15. Named substreams inside a replication

A simulation commonly uses randomness for several processes. An Erlang-A queue,
for example, may sample:

- customer interarrival times;
- service durations;
- customer patience times.

Using one sequential generator is possible, but it couples these processes. If
the model is changed to draw one additional arrival-related value, every later
service and patience draw can shift.

A more structured runner can derive named substreams from the replication
stream:

```text
replication 37 / arrivals
replication 37 / service
replication 37 / patience
```

Each process then receives its own deterministic generator. Changes to one
process do not automatically perturb the random sequence of another process.
This can make debugging, sensitivity analysis, and model evolution easier.

Named substreams can also support common random numbers. For example, two
service policies may intentionally use corresponding arrival streams so that
the comparison is less affected by unrelated input noise. Such a design must be
explicit and its statistical analysis must account for paired observations.

Substreams are therefore a valuable extension, but they should follow the basic
experiment/scenario/replication identity contract rather than replace it.

## 16. Required result provenance

A replication result should contain enough information to reconstruct the
assigned stream. A conceptual result fragment is:

```json
{
  "randomness_contract": "cbse-v1",
  "root_seed": 123456789,
  "scenario_stream_id": "baseline-lambda-4-mu-5",
  "replication_index": 37,
  "effective_seed": 8072139487123,
  "rng_algorithm": "python-random-mt19937"
}
```

The complete reproducibility record should also retain:

- the immutable simulation-runner image digest;
- model and dependency versions;
- the scenario parameters;
- the experiment design;
- the root seed and its fixed/generated mode;
- the seed-derivation version;
- the substream convention, if used;
- all effective seeds or enough information to reconstruct them;
- the result-storage identity used for retry idempotency.

The container image is essential. Identical seeds do not guarantee identical
results if the model implementation or distribution algorithms have changed.
Exact computational replay means reusing both the random stream and the
software environment.

## 17. Reproducibility terminology

Different disciplines use “repeatability,” “reproducibility,” and
“replicability” differently. For the thesis, it may be useful to state the
intended meanings explicitly.

One practical distinction is:

- **computational repeatability:** the same software environment and stream
  descriptor produce exactly the same simulation output;
- **computational reproducibility:** an exported experiment manifest can be
  used to reconstruct the same model, parameters, and streams in a recreated
  execution environment;
- **statistical replication:** a new experiment uses fresh independent streams
  and is expected to support the same scientific conclusion, without producing
  identical individual observations.

The deterministic stream feature primarily targets computational repeatability
and reproducibility. It should also permit intentional generation of a new root
seed when a statistically independent replication of the study is desired.

The repository directory currently uses the name `experiment-replicatability`,
but thesis prose should use whichever technical terms are defined and applied
consistently in the final methodology chapter.

## 18. What the proposed design guarantees

If implemented and tested correctly, the design should guarantee that:

1. the same root seed, scenario stream ID, replication index, and derivation
   version produce the same effective seed;
2. changing Pod name, node, scheduling time, or execution order does not change
   the stream;
3. a Kubernetes retry of the same completion index repeats the same logical
   replication;
4. additional PPS waves continue with new global replication indices;
5. dividing a fixed number of replications into different wave sizes does not
   change their stream assignments;
6. an exported experiment can reconstruct the same streams after recreation;
7. the model remains free to use an appropriate local RNG implementation;
8. the result record identifies the randomization and software environment.

## 19. What the proposed design does not guarantee by itself

The design does not automatically guarantee that:

- every RNG algorithm has formally non-overlapping subsequences;
- different model implementations produce equal results from the same seed;
- floating-point behavior is identical across architectures;
- parallelism inside one model is deterministic;
- external services or files read by the model remain unchanged;
- common-random-number comparisons are analyzed correctly;
- a logically duplicated result cannot be counted twice unless storage
  idempotency is also implemented.

These are separate reproducibility concerns and should be documented alongside
the stream-allocation contract.

## 20. Suggested implementation sequence

A safe incremental implementation would proceed in four stages.

### Stage 1: define stable identities

Add the experiment root seed, stable scenario stream ID, derivation version,
and global replication-index semantics. Persist these values before runners
start.

### Stage 2: carry identities into runner Pods

Have Scenario Manager inject the cumulative offset and expose the Indexed Job
completion index. Reserve the runtime fields so custom templates cannot replace
them.

### Stage 3: update the reference Translator and result contract

Replace hostname-derived seeding with the versioned deterministic derivation.
Record the full stream descriptor and RNG algorithm. Add byte-exact test vectors
and prove that Pod-name changes do not affect the output.

### Stage 4: add replay and stronger statistical support

Add experiment replay from an exported manifest, idempotent result insertion,
named model substreams, and adapters for RNGs with stronger stream guarantees.

## 21. Thesis-oriented summary

CBSE currently achieves practical variation between parallel simulation
replications by deriving each runner's seed from a scenario seed policy and the
Kubernetes Pod hostname. This avoids identical streams during normal execution,
and the effective seed is retained in the result. However, it binds the random
stream to a transient infrastructure object. A retried Pod or recreated
experiment can therefore execute a different stream even when it represents the
same logical replication.

The proposed design replaces infrastructure-derived randomness with an
explicit deterministic stream descriptor. An experiment root seed defines the
overall randomization, a stable scenario stream ID separates scenarios, and a
global replication index identifies one observation across all adaptive PPS
waves. Scenario Manager supplies these stable orchestration coordinates, while
the user-provided Translator derives the effective seed and integrates an
appropriate local random-number generator into the model. The resulting design
retains container isolation and model flexibility while making retries,
experiment replay, provenance, and statistical reasoning explicit.

The key architectural principle is:

> Kubernetes identifies where and when a replication executes; CBSE's
> experiment design must identify which statistical replication it is.
